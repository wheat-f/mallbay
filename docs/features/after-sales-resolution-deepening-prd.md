| 项目 | 内容 |

## 2. 需求背景

`AfterSalesService` 同时处理售后创建、派单、责任判定、施工证据、照片上传、关闭、成本记录和红冲。状态条件、指派关系、OSS 适配、成本权限、审计和并发更新散落在多个 public 方法中，controller 需要理解 implementation 细节。

本期深化“售后处置”，明确它与退货执行、订单履约、现金事实和库存流水的 ownership 差异。

## 3. 产品目标

- 售后列表/详情成为稳定读取投影。
- 所有售后状态和处置动作进入统一 command seam。
- 证据追加、成本红冲、审计和权限规则获得 locality。
- 旧 `AfterSalesService` 不再作为 module public export。

## 4. 本期范围与非目标

### 包含

- 读取：售后列表、详情、能力和审计事件。
- 处置：创建、派单、责任判定、证据提交、照片上传、关闭、成本记录、成本红冲。
- 现有 controller 迁移、contract test、删除测试和回归。

### 不包含

- 销售退货或采购退货状态；退货继续由 `ReturnsWorkflow` 拥有。
- 订单最终交付或履约状态；继续由 `OrderLifecycle` 拥有。
- 直接写现金事实或库存流水；分别由 `CashFactWriter`、`InventoryLedger` 拥有。
- 新增未经确认的售后状态、换货流程或退款审批流程。

## 5. 核心对象与状态

| 对象 | 定义 | 关键事实 |
|---|---|---|
| 售后单 | 记录订单售后问题及责任处置过程 | 订单、客户、门店、描述、责任和处置说明 |
| 售后指派 | 售后单与施工人员的处理关系 | 指派人、施工人员、门店范围 |
| 售后证据 | 售后问题、施工后和补充证据的追加记录 | 阶段、URL、上传人、时间、备注 |
| 售后成本 | 售后成本或追偿记录 | 类别、方向、金额、状态、红冲原因 |

状态保持：`OPEN → ASSIGNED → RESOLVED → CLOSED`。

## 6. 业务规则

### 6.1 创建与派单

- 订单存在且访问主体具有售后写能力时，创建售后单并记录问题证据与审计。
- 售后处于 `OPEN` 或 `ASSIGNED` 时可重新派单；施工人员必须属于当前门店且岗位有效。
- 派单成功后状态为 `ASSIGNED`，重复指派不产生重复关系。

### 6.2 责任判定与证据

- 只有 `ASSIGNED` 售后可完成责任判定。
- 责任判定前必须存在施工后照片证据；补充证据可以同时追加。
- 证据只追加，不覆盖既有记录；当前视图可展示有效记录，审计保留完整历史。
- 责任判定可产生处罚记录，但不直接改变订单最终交付。

### 6.3 关闭与成本

- 只有 `RESOLVED` 售后可关闭；已关闭重复关闭返回原结果。
- 成本写入按类别执行门店管理或财务权限校验。
- 已确认成本只能红冲一次；红冲必须记录原因，不能静默修改原成本。
- 若成本关联现金事实，售后处置只引用既有记录或编排对应 owner，不直接写 `PaymentRecord`。

## 7. 权限与数据范围

| 角色 | 读取 | 处置 |
|---|---|---|
| 销售 | 本人销售订单对应售后 | 按既有规则提交售后 |
| 施工员/学徒 | 已指派给本人的售后 | 提交本人处理证据 |
| 店长/排班员/客服 | 授权门店售后 | 创建、派单、责任判定、关闭 |
| 财务 | 授权门店售后成本 | 财务类别成本记录和红冲 |

全部授权使用 `AccessContext` 与实体指派关系，禁止旧 `PermissionPolicy`、岗位字段 fallback。

## 8. 异常与边界

- 对象不存在或超出范围：稳定拒绝，不泄露越权对象信息。
- 状态已被其他操作改变：拒绝本次转换，不覆盖新状态。
- 重复证据上传：按既有照片/操作幂等规则返回原结果或拒绝冲突输入。
- OSS 上传成功但数据库写入失败：执行对象清理，不能留下不可追踪照片。
- `RESOLVED` 前无施工后证据：拒绝责任判定。
- 已关闭售后、已红冲成本再次操作：返回稳定业务错误，不产生新记录。

## 9. 验收标准

- Given 售后处于 `OPEN`，When 合法管理者派单，Then 创建指派关系并变为 `ASSIGNED`。
- Given 售后处于 `ASSIGNED` 且无施工后照片，When 提交责任判定，Then 请求拒绝且状态不变。
- Given 售后处于 `ASSIGNED` 且已有施工后照片，When 完成责任判定，Then 售后变为 `RESOLVED`，证据、责任和审计均可追溯。
- Given 施工人员只被指派到售后 A，When 上传售后 B 的证据，Then 请求被拒绝。
- Given 售后处于 `RESOLVED`，When 合法用户关闭，Then 变为 `CLOSED`；重复关闭返回原结果。
- Given 成本处于 `CONFIRMED`，When 首次红冲，Then 新增红冲关系并保留原成本；再次红冲被拒绝。
- Given 生产源代码扫描，When 检查现金/库存直接写入，Then 售后 implementation 不直接创建 `PaymentRecord` 或库存事实。

## 10. 阶段门

1. 读取投影和处置 command contract test 覆盖状态、证据、权限、成本、幂等和错误。
2. controller 与售后页面迁移到新 seam。
3. `AfterSalesModule` 不再 exports `AfterSalesService`，静态引用与 deletion test 通过。
4. API typecheck、Nest build、全量 API tests 和售后代表页面验收通过。

## 11. 待确认事项

无业务阻塞项。本期沿用当前售后状态和成本类别；新增状态或退款审批须另立需求与评审。
