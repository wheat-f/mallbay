## 3. 首轮高风险问题（已关闭）

### 问题 1：事务上下文的读取能力被定义为可选

- 严重程度：S1
- 所在位置：第 8.2 节、第 10 节；当前实现 `CashFactTransaction.paymentRecord.findFirst` 为可选字段
- 问题描述：PRD要求按 `storeId + idempotencyKey` 先读取再判断重放，但当前接口允许没有 `findFirst` 的事务上下文继续执行 create。此时同键重放无法在应用层识别，唯一约束只能在重复写入后报错，不能满足“同输入重放返回原记录”的统一 seam 契约。
- 影响：调用方可通过不完整 adapter 绕过幂等语义；测试可能只验证 create，而真实调用方和兼容 mock 的行为不一致。
- 修改建议：将 `findFirst` 设为必需能力；删除“缺少 findFirst 仍可写入”的兼容行为；更新测试 fake，明确所有生产/测试 adapter 都必须提供查询和创建两项能力。
- 待确认角色：研发
- 是否阻塞研发：是

### 问题 2：`reversalOfId` 的文档规则与实现不一致

- 严重程度：S1
- 所在位置：第 8.2 节、第 12 节；当前实现 `assertReplay` 未比较 `reversalOfId`
- 问题描述：PRD把反向关系字段列为幂等冲突比较字段，但实现只比较类型、方向、金额、账户、来源、操作人和发生日期。未来同一幂等键被复用到不同被冲销事实时，可能被错误判定为重放。
- 影响：退款/冲销来源关系可能错误，财务追溯和反向关系完整性受损。
- 修改建议：将 `reversalOfId` 纳入比较，并增加“同键但反向关系不同”的冲突测试；当前 Returns 仍不迁移，但 writer 契约应先正确。
- 待确认角色：研发/财务
- 是否阻塞研发：是

### 问题 3：并发唯一冲突的责任和验收结果不够具体

- 严重程度：S1
- 所在位置：第 8.2 节、第 11 节、AC-03/AC-05
- 问题描述：PRD同时要求“同键重放返回原记录”和“并发唯一冲突由调用端按既有策略重试”，但没有明确第一次并发失败如何映射、由哪个 workflow 重试整笔事务、重试后返回什么结果。当前 writer 的 find-then-create 在竞争时可能直接收到数据库唯一约束异常。
- 影响：测试无法判断并发失败是允许的临时错误、业务冲突还是必须自动重放；不同调用方可能形成不同处理方式。
- 修改建议：明确首期契约：数据库唯一约束冲突不得产生第二条记录；当前事务必须回滚；writer/调用 workflow 将竞争结果归类为可安全重试的现金事实幂等冲突，并以相同业务幂等键重新执行整个业务事务后返回原业务结果。增加至少一个并发测试或明确标注真实 PostgreSQL 为阶段门。
- 待确认角色：研发/测试
- 是否阻塞研发：是

## 4. 一般问题与优化建议

| 编号 | 等级 | 问题 | 影响 | 修改建议 |
|---|---|---|---|---|
| R4 | S2 | 金额校验写成“沿用调用方”，writer 自身是否拒绝非法金额不够明确 | 未来新调用方可能绕过订单层校验写入负数或非整数金额 | 明确 writer 只负责现金事实字段和幂等；金额业务边界由各 owning workflow 校验，并在 writer 测试中验证非法输入不会被本期入口产生 |
| R5 | S2 | `occurredAt` 的“事实发生日期”与 Finance 兼容入口对缺省日期的处理未完全说明 | 收款冲销、返利支付若无业务发生时间，可能使用写入时间导致口径漂移 | 明确兼容入口未提供日期时，按“动作发生时刻”显式补值；后续新增入口必须要求调用方提供实际发生日期 |
| R6 | S3 | 产品负责人、业务确认人和线上指标目标尚未指定 | 不影响当前技术实现，但影响上线责任和运营复盘 | 在进入正式业务评审前补齐负责人；指标目标可作为后续运营任务 |

## 5. 业务流程评审

- 流程起点：订单收款、订单创建定金或既有 Finance workflow 打开业务事务。
- 流程终点：订单事实与现金事实一同提交，或全部回滚。
- 关键判断节点：业务权限/金额校验、业务幂等重放、现金事实幂等重放/冲突、事务提交。
- 缺失分支：需要补充并发唯一冲突的错误归类与整事务重试边界。
- 异常处理：单事务失败回滚已明确；历史订单现金事实缺失不自动修复已明确。
- 当前问题：writer 事务上下文契约仍允许缺少查询能力。

## 6. 状态流转评审

本期不新增状态机。`PaymentRecord` 的追加事实生命周期已闭环：不存在 → 创建；已存在且同输入 → 重放；已存在且异输入 → 冲突；事务失败 → 不落库。并发竞争的错误归类需按问题 3 补全。

## 7. 权限与数据范围评审

| 角色/模块 | 查看范围 | 操作权限 | 当前缺失或冲突 |
|---|---|---|---|
| Orders workflow | 既有订单访问范围 | 写订单事实并调用现金事实 seam | 无新增权限；需保持调用方负责授权 |
| Finance workflow | 既有财务门店范围 | 通过 FinanceService 写现金事实 | 无新增权限；writer 不应自行扩权 |
| CashFactWriter | 不面向用户开放 | 仅接受内部事务上下文 | 需禁止不完整事务上下文绕过幂等 |
| Returns | 既有退货范围 | 本期保持三处既有直写 | 已明确为后续阶段，不应新增同类路径 |

## 8. 数据与字段评审

| 字段或指标 | 当前定义 | 问题 | 建议 |
|---|---|---|---|
| `storeId + idempotencyKey` | 现金事实唯一身份 | 业务规则明确，接口能力需强制查询 | 强制 `findFirst`，增加竞争测试 |

## 9. 异常与边界评审

| 场景 | 当前是否覆盖 | 风险 | 建议规则 |
|---|---|---|---|
| 同键同输入重放 | 是 | 查询能力可选时会退化 | 查询能力强制存在 |
| 同键异输入 | 是 | 反向关系字段漏比对 | 补入 `reversalOfId` |
| 并发同键写入 | 部分 | 失败和重试语义不统一 | 明确唯一冲突→当前事务回滚→整 workflow 重试 |
| 订单现金事实部分成功 | 是 | 已有回滚目标 | 保持同事务，禁止补偿双写 |
| 历史缺失现金事实 | 是 | 不自动修复可能需要运营处理 | 保持非目标，后续另立数据修复任务 |

## 10. 验收标准评审

### 已可直接验收

- AC-01：普通收款同时产生 `OrderPayment` 和 `PaymentRecord`。
- AC-02：初始定金与订单创建原子提交。
- AC-03：同键同输入不重复创建。
- AC-05：后续失败全部回滚。
- AC-06：Finance 兼容入口委托 writer。
- AC-07：订单与 Finance 生产源码不直接写表。

### 需要改写后验收

| 原描述 | 问题 | Given / When / Then 改写建议 |
|---|---|---|
| “并发唯一冲突由调用端按既有重试/重放策略重新读取业务结果” | 未定义哪个调用端、重试几层、错误如何分类 | Given 两个事务使用同一门店和现金事实幂等键；When 同时提交；Then 最多一条 PaymentRecord，竞争事务整体回滚，并按同一业务幂等键重新执行整个 workflow 后返回同一业务结果 |
| “反向关系字段参与冲突比较” | 当前实现未满足 | Given 同键已有 reversalOfId=A；When 使用 reversalOfId=B 写入；Then 返回 CASH_FACT_IDEMPOTENCY_CONFLICT 且原记录不变 |

## 11. 风险与依赖

- 技术风险：Prisma 唯一约束竞争发生在事务内，不能仅依赖 catch 后继续使用已失败事务；应以整事务重试作为边界。
- 数据风险：历史现金事实缺失不自动补造，需后续核验/修复计划。
- 兼容风险：FinanceService 的旧返回 `{ id }` 必须保持，避免 workflow 误解。
- 依赖：现有 `PaymentRecord` 唯一约束和 OrderPayment 幂等约束必须继续存在。

## 13. 二次评审结论

### 是否可以进入研发

可以进入研发。

### 进入研发前必须完成

- 线上现金事实写入成功/冲突/重试指标。
- Returns 三处直写的后续迁移。
