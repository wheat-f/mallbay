| 等级 | 数量 | 说明 |

## 3. S1 高风险问题

### S1-01：配置“发布原子性”与独立校验入口的关系不清

- 所在位置：配置版本 PRD「状态规则」「业务流程」。
- 问题：文档同时保留独立校验和“发布内必须校验”，没有说明发布是否重新执行校验、独立校验结果是否可复用、校验结果过期后如何处理。
- 影响：研发可能实现为先调用 validate 再 publish 的两次写入，无法保证发布时使用的 payload 与校验结果一致。
- 建议：明确独立校验是预览/记录结果；发布必须在同一事务内对当前 payload 重新校验并完成条件状态变更，不能信任旧校验结果。
- 确认角色：研发、测试。
- 是否阻塞研发：是。

### S1-02：配置缓存失败不能简单要求数据库事务回滚

- 所在位置：配置版本 PRD「异常与边界」。
- 问题：缓存通常不是数据库事务资源，文档将缓存失败与审计失败混写为“业务事务回滚”。
- 影响：研发会把不可回滚的缓存操作塞进事务，或在缓存失败时错误回滚已完成的配置事实。
- 建议：审计与配置状态同事务；缓存采用提交后失效，失败记录可观测事件并短暂禁止旧缓存命中，不回滚已提交事实。
- 确认角色：研发。
- 是否阻塞研发：是。

### S1-03：字典来源无关 interface 与现有 `kind` 路由兼容缺少映射规则

- 所在位置：字典治理 PRD「interface 与 seam 约束」。
- 问题：目标要求调用方不理解来源，但现有路由和参数仍含 `kind`；未规定兼容 adapter 如何将旧路由映射到新 interface，也未规定返回结构如何保留只读能力事实。
- 影响：迁移时容易同时修改前端和后端契约，或出现新旧路径双写。
- 建议：明确旧 controller 只做兼容映射，新 module 是唯一写入 seam；`kind` 只作为兼容输入，不进入内部治理规则；返回结果保留 readOnly/inherited 等能力事实。
- 确认角色：研发、测试。
- 是否阻塞研发：是。

### S1-04：成员通知后置缺少持久化补偿对象

- 所在位置：成员邀请 PRD「业务规则」「异常与边界」。
- 问题：文档要求通知失败可重试，但没有定义重试记录的来源、唯一键、状态和关闭条件。
- 影响：业务事实提交后可能丢失通知，或重试重复发送。
- 建议：把通知意图作为同事务持久化的通知投递记录/现有可复用通知对象，由 notification adapter 负责幂等投递、重试和终态；发送不回滚成员事务。
- 确认角色：研发、产品。
- 是否阻塞研发：是。

### S1-05：运营报表 2000 条上限的结果语义未定义

- 所在位置：运营报表 PRD「业务口径」「异常与边界」。
- 问题：文档同时使用“上限”“截断/限制”，没有明确是否返回截断标记、总数、可继续查询游标，或仅返回前 2000 条。
- 影响：前端和测试无法判断结果是否完整，使用者可能把部分明细当成全量。
- 建议：保持现有接口行为并在结果中明确完整性事实；若当前没有游标，本期不新增游标，但必须返回可测试的 capped/truncated 事实和总量口径。
- 确认角色：产品、研发、测试。
- 是否阻塞研发：是。

### S1-06：四个 module 的迁移删除顺序和回滚点未写入 PRD

- 所在位置：四份 PRD「依赖与风险」。
- 问题：虽然写了 contract test 先行和 no dual-write，但没有明确旧入口何时删除、如何确认没有调用方、失败时回滚到哪个兼容 adapter。
- 影响：可能出现旧路径与新 seam 并存，或迁移中断后无法判断哪个路径是权威路径。
- 建议：补充每个 module 的迁移阶段：锁定 contract test → controller/任务单向切换 → 静态搜索确认旧写入为零 → 删除旧路径 → 回归测试；禁止保留第二条权威写入路径。
- 确认角色：研发。
- 是否阻塞研发：是。
