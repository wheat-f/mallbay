## 2. 背景与目标

当前发票模块将跨订单申请与分摊、开具、作废、重开、发送和部分读取组合在 `InvoicesService` 中；列表读取已经由 `FinancialDocumentQuery` 承担，但命令仍直接依赖宽实现。发票状态、可开票额度、完工/收款前置条件和发票日志需要在一个 workflow seam 内保持 locality。

本期目标：

- 建立 `InvoiceWorkflow` 命令 seam，集中发票执行状态推进与业务规则。
- 保持 `FinancialDocumentQuery` 作为读取和来源解释契约。
- 明确跨订单分摊、重复操作、文件生成失败和日志一致性。
- 保持现有路由、数据结构和发票结果兼容。

## 3. 范围与非目标

### 本期范围

- 发票申请及多订单金额分摊。
- 发票开具、作废、重开、发送。
- 状态转移、权限、额度、完工/收款校验和发票日志。
- controller/module 依赖迁移、workflow contract tests 和现有财务回归。

### 非目标

- 不改造 `FinancialDocumentQuery` 的读取语义。
- 不引入新的电子发票外部系统或 PDF adapter。
- 不新增发票表字段或迁移。
- 不将收款事实写入发票 workflow。

## 4. 角色与数据范围

| 角色 | 可查看 | 可操作 | 数据范围 |
|---|---|---|---|
| 有财务写入能力的访问主体 | 本权限范围内的发票和日志 | 申请、开具、作废、重开、发送 | 本人/门店权限范围 |
| 财务单据读取者 | 权限范围内的发票列表和来源订单 | 只读 | `FinancialDocumentQuery` 计算出的范围 |

每个命令都必须通过 `AccessContext` 判断访问能力和门店/本人范围；不得使用请求中的历史岗位或 `isAuditor` 字段绕过权限。

## 5. 核心对象与状态

| 对象 | 定义 | 状态 |
|---|---|---|
| 发票 | 针对一个或多个同门店、同客户订单的开票记录 | APPLIED、ISSUED、VOIDED、REISSUED |
| 发票分摊 | 发票金额在订单之间的明确分配 | 创建后随发票保留，不允许重复订单分摊 |
| 发票日志 | 记录申请、开具、作废、重开和发送结果的不可缺失审计记录 | 随命令追加 |

## 6. 状态流转

| 原状态 | 触发条件 | 新状态 | 结果 |
|---|---|---|---|
| 无 | 订单满足可开票条件且额度合法 | APPLIED | 创建发票、分摊和申请日志 |
| APPLIED | 文件准备成功且命令有权限 | ISSUED | 保存发票编号/文件地址并追加日志 |
| ISSUED/REISSUED | 合法作废请求 | VOIDED | 更新状态并追加日志 |
| VOIDED | 重新开具请求 | REISSUED | 重新生成/指定文件、更新状态并追加日志 |
| ISSUED/REISSUED | 文件存在且发送请求合法 | 原状态 | 追加发送日志，不改变状态 |

## 7. 核心业务规则

### 7.1 申请与分摊

- 订单必须存在，且所选订单属于同一门店、同一客户；多订单合并仅支持企业客户。
- 每笔订单必须已完成或达到现有完工条件，且未收金额为零。
- 发票金额不得超过所选订单的剩余可开票额度。
- 明确分摊时每个订单最多出现一次，分摊合计必须等于发票金额，且单笔不超过剩余额度。
- 未提供分摊时按订单顺序分配，无法覆盖金额时拒绝创建。

### 7.2 文件与状态事务

- 开具/重开先准备文件；文件生成失败时不改变发票状态。
- 文件准备成功后，在事务中更新发票状态并追加日志；写入失败时允许重新执行，不产生“已开具但无日志”的业务结果。
- `InvoicePdfService` 保留为 implementation 内部依赖，不把文件生成抽象为不存在第二实现的泛化 adapter。

### 7.3 幂等与重试

- 已处于目标状态的重复状态操作返回当前结果或幂等成功，不重复破坏状态。
- 非法状态跃迁明确拒绝，例如非 `VOIDED` 发票不能重开、未开具发票不能发送。
- 发送允许重复重试；每次实际发送请求追加一条发送日志，发票状态不变。
- 并发状态推进必须带原状态条件，最多一个请求成功改变状态；其他请求读取当前结果并按幂等或非法跃迁规则返回，不得重复生成最终状态。
- 重开成功后最终状态为 `REISSUED`，必须追加 `REISSUED` 日志；文件生成或事务失败不得追加该最终状态日志。

## 8. Seam 与实现约束

- `InvoiceWorkflow` 是所有发票命令的唯一外部 seam；状态 helper、订单额度校验、分摊计算、日志写入属于 implementation 内部。
- `FinancialDocumentQuery` 继续负责列表查询，不通过 workflow 反向拼装读取。
- 先通过 token/interface 接入现有 `InvoicesService`，再逐步物理拆分；不新增双写和数据库迁移。
- 测试通过 workflow seam 覆盖业务规则，而不是依赖 controller 到 Prisma 的调用链。

## 9. 验收标准

- Given 两笔同门店同企业客户订单均已收齐，When 申请金额不超过合计剩余额度，Then 创建一张发票、正确分摊并追加申请日志。
- Given 订单属于不同门店或不同客户，When 合并申请，Then 拒绝且不创建发票。
- Given 发票申请已存在，When 文件生成失败，Then 发票仍为 `APPLIED`，无开具状态日志。
- Given 文件准备成功，When 开具事务完成，Then 发票为 `ISSUED`，包含发票编号/文件地址和对应日志。
- Given 发票为 `VOIDED`，When 重开成功，Then 发票为 `REISSUED`；其他状态重开拒绝。
- Given 发票为 `ISSUED` 或 `REISSUED` 且有文件，When 发送两次，Then 状态不变且产生两条发送日志。
- Given 两个请求同时开具同一张 `APPLIED` 发票，When 只有一个请求满足原状态条件，Then 只有一个请求成功进入 `ISSUED`，另一个请求不重复生成最终状态。
- Given 发票为 `VOIDED`，When 重开事务完成，Then 存在 `REISSUED` 状态日志；When 文件生成或事务失败，Then 不存在该最终状态日志。
- Given 访问主体不具备门店财务写入能力，When 执行任一命令，Then 拒绝且不写入发票业务数据。
- API typecheck、Nest build、发票/财务/权限相关测试和全量 API tests 通过。

## 10. 指标与待确认

- 技术指标：状态转移和分摊规则可通过 workflow contract tests 验证；无新增迁移和双写。
- 业务指标：开票失败重试成功率、非法状态操作数暂无基线，标记为上线后补充。
- 待确认：真实外部电子发票系统接入不在本期；若后续引入，再单独设计 adapter seam。
