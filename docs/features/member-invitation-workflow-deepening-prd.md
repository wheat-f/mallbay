# MemberInvitationWorkflow（成员邀请执行）深化 PRD

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 目标 | 将门店成员邀请与成员关系迁移收拢为可测试的 workflow module |
| 目标角色 | 门店经理、被邀请用户、门店治理人员 |
| 设计依据 | `apps/api/src/members/members.service.ts`、`members.controller.ts`、`StoreGovernance` 词汇 |
| 本期原则 | 不接管门店/经理生命周期；保持既有邀请状态和路由契约 |

## 2. 背景与目标

成员邀请包含搜索可邀请用户、创建邀请、接受、拒绝、移除和通知。接受邀请还会把用户从冻结门店成员关系迁移到当前门店，涉及唯一成员关系与事务一致性。当前 controller 直接依赖 implementation，访问主体检查还保留 fallback，容易让状态和权限规则穿过 seam。

本期形成 `MemberInvitationWorkflow` module：统一邀请状态、重复邀请、成员迁移、权限检查、审计和通知 adapter。`StoreGovernance` 继续拥有门店及经理生命周期，本 module 不负责经理任命或门店冻结/发布。

非目标：不新增岗位体系；不改变门店治理状态；不建设通用消息中心；不允许经理岗位通过普通邀请流程产生。

## 3. 核心对象与状态

邀请对象包含 storeId、invitedById、invitedUserId、position、status、创建/处理时间和审计信息。状态保持 `PENDING`、`ACCEPTED`、`REJECTED`、`CANCELLED`。

规则：

1. 经理只能邀请非 `MANAGER` 岗位；被邀请用户必须存在且满足门店成员规则。
2. 同一门店、同一用户只能保留一个有效 `PENDING` 邀请；重复邀请先取消旧邀请，再创建新邀请。
3. 只有被邀请用户可以接受或拒绝；接受只能发生在 `PENDING`。
4. 接受邀请时，冻结门店成员关系迁移、创建当前成员关系、更新邀请状态必须在同一事务内完成。
5. 同一用户在同一门店最多一个有效成员关系；并发接受只能成功一次。
6. 移除成员不能移除门店经理，也不能改变门店治理状态。
7. 通知在业务事务提交后由 notification adapter 发送；失败进入重试/补偿，不回滚成员事实。

通知意图必须作为同一业务事务内持久化的投递记录或现有可复用通知对象，至少包含唯一键、接收人、类型、payload、投递状态、重试次数、最近错误和关闭时间。notification adapter 只能处理投递，不得重新决定成员状态。

## 4. 权限与数据范围

- 邀请、取消旧邀请和移除成员需要当前访问主体拥有目标门店的成员治理能力。
- 接受、拒绝只允许邀请接收人操作。
- 搜索可邀请用户只返回当前门店规则允许的用户，不返回其他门店敏感成员关系。
- 门店冻结、经理任命和门店生命周期由 `StoreGovernance` 决定，本 module 只读取其结果。

## 5. 异常与边界

| 场景 | 结果 |
|---|---|
| 用户不存在 | 拒绝邀请，不写邀请或通知 |
| 邀请岗位为 MANAGER | 明确拒绝 |
| 店长或访问主体无效 | 拒绝操作，不泄露成员信息 |
| 邀请已被处理 | 接受/拒绝返回状态冲突，不重复写入 |
| 并发接受 | 只有一个事务成功，另一个收到状态冲突 |
| 冻结成员迁移失败 | 整个接受事务回滚，邀请保持待处理 |
| 通知发送失败 | 成员事实保持，通知可重试并可观测 |
| 移除最后一个经理 | 拒绝，门店经理不变量不被破坏 |

## 6. interface 与 seam 约束

- controller 只通过 workflow interface 调用邀请和成员关系动作。
- Prisma、访问主体解析、StoreGovernance 读取和通知投递均为内部 adapter。
- 不在 interface 暴露“直接冻结/迁移成员”的数据库细节。
- contract test 以 workflow interface 验证状态机、唯一性、权限、事务和通知后置。
- 成员移除审计必须记录操作者、门店、目标用户、原因、前后成员状态和关联邀请（如有）。

## 7. 验收标准

- Given 经理邀请非经理用户，When 邀请有效，Then 产生一个 `PENDING` 邀请并在事务提交后发送通知。
- Given 同门店同用户已有 `PENDING` 邀请，When 再次邀请，Then 旧邀请变为 `CANCELLED`，只保留一个新的待处理邀请。
- Given 非接收人操作邀请，When 接受或拒绝，Then 被拒绝且邀请状态不变。
- Given 用户在冻结门店已有成员关系，When 接受新门店邀请，Then 冻结关系迁移与新关系创建原子完成。
- Given 两次并发接受同一邀请，When 同时提交，Then 只有一次成功，不能产生重复成员关系。
- Given 通知 adapter 失败，When 接受事务已提交，Then 成员关系保持且产生可重试通知记录。
- Given 目标用户为门店经理，When 普通移除成员，Then 操作被拒绝。

## 8. 迁移与删除顺序

1. 先锁定邀请状态、并发接受、成员唯一性和通知投递记录的 contract test。
2. controller 单向切换到 workflow seam，保留原有输入输出兼容 adapter。
3. 静态搜索确认没有其他邀请/成员关系写入路径后，删除旧的直接写入路径。
4. 迁移失败时回滚到兼容 adapter，不恢复第二条权威写入路径。

## 9. 依赖与风险

- 依赖 `StoreGovernance` 的门店/经理事实、成员表、邀请表、通知 adapter 和访问能力。
- 风险：通知后置会出现业务成功而消息延迟；通过幂等、重试和观测降低风险。
- 不采用 dual-write；先让 contract test 锁定 workflow interface，再迁移 controller。
