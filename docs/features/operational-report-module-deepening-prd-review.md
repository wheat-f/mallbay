## 2. 结论摘要

### 总体结论

PRD 已达到研发和测试可执行标准，可以进入研发。核心 interface、业务日期口径、在途订单、成本完整度、权限、错误语义、结果状态、明细规模和验收条件已经明确；没有 S0 阻塞项。

研发开始前仍必须完成第 17 节技术评估，评估结果不得改变已确认的业务语义；如果技术方案需要改变结果口径，必须回到 PRD 和 ADR 重新评审。

## 3. 已修正的高风险问题

### 3.1 服务端认证上下文未明确

- 原问题：流程曾写成页面提交当前用户上下文，容易造成把用户身份交给前端的越权风险。
- 修正：改为页面只提交 `OperationalReportFilters`，服务端从认证上下文取得用户身份和权限。

### 3.2 在途订单毛利边界不够精确

- 原问题：在途订单是否一律不能计算毛利存在歧义。
- 修正：在途订单可以计算完整实际或标准成本对应的毛利，但必须显式标记成本来源；不完整成本的毛利为 `null/待补齐`，在途订单不进入不适用的完工指标分母。

### 3.3 日期错误码未区分

- 原问题：日期逆序和日期范围超限可能复用同一错误码，测试和页面无法稳定处理。
- 修正：日期格式错误或结束早于开始使用 `REPORT_DATE_RANGE_INVALID`；超过 366 天使用 `REPORT_DATE_RANGE_TOO_LARGE`。

### 3.4 局部状态和不可比原因未闭环

- 原问题：`partial`、`unavailable`、`error` 和 comparison 不可比原因没有明确判定规则。
- 修正：PRD 已定义三类状态的适用条件，并要求 `unavailable/error` 提供原因；新增 `comparison.reason` 枚举。

## 4. 业务流程评审

- 流程起点：用户进入 `/reports` 或修改筛选条件。
- 流程终点：页面展示统一结果，或按明确错误/分析区状态反馈。
- 关键判断节点：权限、日期范围、主日期口径、成本完整度、历史可比性、明细是否超过 2,000 行。
- 异常处理：无权限、非法日期、超限、空数据、局部失败和导出失败均已定义。
- 结论：流程起点、主流程、分支和错误出口闭环。

## 5. 状态流转评审

Operational Report 为只读结果，不引入新的订单或财务状态。分析区状态已定义为：

`ready` → 正常可用
`partial` → 结果可用但存在数据缺失
`unavailable` → 当前条件无法计算
`error` → 处理失败，可重试

结论：状态不改变业务对象生命周期，终态和重试语义清楚；summary 失败为整次请求失败，其余分析区允许局部降级。

## 6. 权限与数据范围评审

| 角色 | 查看范围 | 操作权限 | 评审结论 |
|---|---|---|---|
| 店长 | 当前门店 | 筛选、钻取、导出 | 已明确 |
| 财务 | 当前门店 | 筛选、钻取、导出 | 已明确 |
| 销售 | 仅本人相关数据 | 查看和导出个人视图 | 后端裁剪已明确 |
| 审计/管理员 | 现有授权范围 | 沿用现有权限 | 不新增权限模型 |

结论：PRD 已明确前端不能替代权限控制，服务端认证上下文是唯一权限依据；无权限时清理旧结果。

## 7. 数据与指标评审

已确认：

- 订单金额和订单数按订单集合统计。
- 实际收款按收款实际发生日期统计。
- 在途订单进入经营金额、实际收款和待收。
- 成本完整时允许使用实际或标准成本计算毛利，并展示成本来源。
- 成本不完整时毛利为 `null/待补齐`，不按 0 计算。
- 订单和收款可进入不同趋势期间，不强行合并。
- comparison 无法比较时返回 `unavailable` 和 `reason`。
- 明细最多返回 2,000 行，但摘要、趋势和洞察保持完整。

结论：主要指标口径已闭环，且与 `CONTEXT.md` 和 ADR-0001 一致。

## 8. 异常与边界评审

| 场景 | 覆盖情况 | 结论 |
|---|---|---|
| 无数据 | 已覆盖 | 不生成洞察，展示空状态 |
| 成本缺失 | 已覆盖 | 待补齐，不伪造 0 |
| 在途订单 | 已覆盖 | 计入经营金额，不进入不适用完工分母 |
| 日期逆序 | 已覆盖 | `REPORT_DATE_RANGE_INVALID` |
| 日期超限 | 已覆盖 | `REPORT_DATE_RANGE_TOO_LARGE` |
| 无权限 | 已覆盖 | 后端拒绝并清理旧结果 |
| 局部失败 | 已覆盖 | 分析区状态和重试入口 |
| 明细超限 | 已覆盖 | `rowCount` + `truncated` |
| 历史数据缺失 | 已覆盖 | 保留缺失状态，不自动回填 |
| 重复筛选请求 | 已覆盖 | 最新查询结果优先 |

## 9. 验收标准评审

### 已可直接验收

- 在途订单金额、实际收款和待收计算。
- 订单日期与收款日期分开进入趋势期间。
- 成本待补齐时毛利为 `null`。
- 销售角色无法扩大数据范围。
- 日期非法和超限使用不同错误码。
- comparison 状态和原因枚举。
- 洞察证据、目标视图和筛选条件。
- 版本、生成时间、分析区状态、明细行数和截断标记。
- `summary` 兼容消费者不被迫迁移。

### 需要技术验证但不改变业务规则

| 项目 | 验证内容 | 负责人 | 阻塞级别 |
|---|---|---|---|
| 明细规模 | 证明明细截断不影响摘要、趋势和洞察，并确认查询计划 | 后端 | S2，研发合并前完成 |
| 局部降级 | 验证 trend/insights/details 失败时 summary 仍可用 | 前后端 | S2，代表页面验收前完成 |
| 真实数据回归 | 验证在途订单、跨月收款、待补齐成本 | 后端/测试/业务 | S2，上线前完成 |

## 10. 风险与依赖

- 技术风险：当前实现仍集中在单个 ReportsService implementation，需要按 PRD 逐步深化，避免一次性大规模拆分。
- 性能风险：2,000 行是结果上限，不自动等同于数据库查询上限；后端必须验证实时查询的内存和响应时间。
- 数据风险：历史数据缺失不能通过回填或 0 值掩盖，必须保留缺失状态。
- 兼容风险：`summary` 旧消费者必须继续通过原 interface 工作。
- 领域依赖：若未来引入第二个真实数据来源，再重新评估 adapter seam；本期不提前建设。

## 12. 最终结论

### 是否可以进入研发

可以进入研发，附技术评估前置条件。

### 进入研发前必须完成

- 研发确认 `comparison.reason`、日期错误码和局部状态字段落地。
- 技术验证明细截断不影响摘要、趋势和洞察。
- contract tests 继续作为 Operational Report module 的 test surface。

### 可以后续优化

- 查询快照、预聚合或第二个数据 adapter。
- 更细的完工指标和目标体系。
- 跨门店集团级分析。
- 复杂自定义报表设计器。
