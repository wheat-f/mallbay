## 2. 需求背景

### 2.1 业务背景

报表分析中心已经从单纯的统计展示扩展为包含摘要、周期对比、趋势、经营洞察和明细的经营分析能力。多个页面和导出场景需要使用同一套金额、收款、成本、权限和日期口径。

### 2.2 当前问题

当前 Operational Report module 同时承担查询范围、权限裁剪、Prisma 查询、趋势聚合、成本计算、期间对比、经营洞察和各 Tab 明细投影。它的 implementation 复杂，但 interface 的业务契约尚未完整表达以下规则：

- 在途订单应进入经营金额、实际收款和待收，但不能伪造不适用的完工指标；只有成本完整时才允许计算对应毛利，否则必须待补齐。
- 订单日期与收款日期是不同业务事实，不能在趋势中强行归属到同一期间。
- 成本不完整时，毛利必须为待补齐，而不是 0。
- 无可比期间、局部分析不可用、权限不足和输入错误需要被调用方区分处理。
- 报表页面和导出不能各自重新解释同一指标。

### 2.3 需求依据

- 报表页面反馈：当前页面只有统计信息，缺少分析和行动。
- 已确认的报表分析中心 PRD：明确指标日期口径、成本完整度、洞察规则、权限和性能边界。
- ADR-0001：确认 Operational Report module 的职责、interface 形状和实现取舍。
- 现有 contract tests：已覆盖在途订单金额、实际收款、成本待补齐和无权限语义。

## 3. 产品目标

### 3.1 业务目标

- 让报表页面、导出和后续消费者共享一套可追溯的经营分析结果。
- 让店长和财务能够区分经营金额、现金流、完工指标和成本完整度。
- 让经营洞察带有证据和动作入口，不由前端猜测或拼接。

### 3.2 研发目标

- 形成一个小而稳定的 Operational Report interface，将复杂实现隐藏在 module 内。
- 将权限、主日期口径、在途订单、成本完整度和期间对比规则固定在 module 内部。
- 以 interface 作为 test surface，先锁定 contract tests，再调整 implementation。
- 保留现有 `summary` 消费者，降低迁移风险。

## 4. 非目标

本期不包含：

- 不新增预算、销售目标、人员目标或绩效考核规则。
- 不新增订单、收款、成本结算、施工或售后状态。
- 不建设离线报表快照、ETL 或独立报表数据库。
- 不公开只有一个真实实现的 Prisma adapter interface。
- 不把每个报表 Tab 拆成独立的外部 interface。
- 不改造财务总账、发票、收款、成本结算和售后管理模块的业务归属。
- 不将页面视觉重写作为本需求的主要交付物。

## 5. 用户角色与权限

| 角色 | 使用场景 | 可查看内容 | 可执行操作 | 数据范围 |
|---|---|---|---|---|
| 店长 | 查看门店经营结果和风险 | 完整报表、趋势、洞察、明细 | 筛选、钻取、导出 | 当前门店 |
| 财务人员 | 核对收款、待收、成本和毛利 | 当前门店财务相关报表 | 筛选、钻取、导出 | 当前门店 |
| 销售人员 | 查看个人销售业绩 | 个人销售相关数据 | 查看允许条件、导出个人视图 | 仅本人相关销售数据 |
| 审计人员 | 复核授权范围数据 | 现有授权范围内的报表 | 筛选、钻取、导出 | 由现有审计权限决定 |
| 管理员 | 跨门店管理或复核 | 允许访问范围内的数据 | 筛选、钻取、导出 | 由现有权限策略决定 |

权限规则：

1. Operational Report module 必须在后端完成权限裁剪。
2. 销售人员不能通过修改 query 参数扩大到其他销售人员或门店。
3. 前端隐藏筛选项不是权限控制；导出结果必须与 interface 返回的数据范围一致。
4. 页面打开后权限被收回时，新的请求返回无权限结果，页面不得继续展示残留缓存。

## 6. 核心业务对象

| 对象 | 定义 | 关键字段 | 状态/口径 | 归属 |
|---|---|---|---|---|
| 报表查询范围 | 一次分析所使用的门店、角色、主日期口径、日期区间和筛选条件 | `storeId`、`dateFrom`、`dateTo`、`dateBasis`、人员及状态筛选 | 不持久化 | 当前请求 |
| Operational Report | 面向经营判断的完整分析结果 | `version`、`summary`、`comparison`、`trend`、`insights`、明细、`modules` | 只读、实时生成 | 当前用户和查询范围 |
| 分析区状态 | 摘要、趋势、洞察、明细等结果区域的可用状态 | `status`、`errorCode`、`rowCount`、`truncated` | `ready`、`partial`、`unavailable`、`error` | Operational Report |
| 在途订单 | 已进入订单流程但尚未满足完工或质保完成条件的订单 | 订单金额、已收金额、待收金额、成本完整度、完工状态 | 可进入经营金额，不自动进入完工指标 | 订单 |
| 已完工订单 | 已满足施工完工或规定的质保完成条件的订单 | 完工日期、确认成本、完工结果 | 可进入完工指标分析 | 订单 |
| 经营金额 | 反映订单商业价值或现金流的指标集合 | 订单金额、实际收款、待收金额 | 可包含在途订单 | 订单/收款 |
| 完工指标 | 需要已完工条件才有意义的指标 | 本期只约束适用分母，不新增完工率字段 | 在途订单不进入适用分母 | 订单 |
| 经营洞察 | 由确定性规则生成、带证据和行动方向的分析结果 | 标题、证据、动作、目标视图、筛选条件 | 只读，不改变业务状态 | Operational Report |

## 7. 产品方案与 interface 目标

### 7.1 External interface

Operational Report module 对外提供一个完整的 `operational` interface：

```text
输入：OperationalReportFilters + 当前用户上下文
输出：OperationalReport
错误：权限错误 / 输入错误 / 查询规模错误
```

输出固定包含以下五类结果：

1. `summary`：当前查询范围的订单、经营金额、收款、待收、成本完整度和毛利。
2. `comparison`：与同口径历史期间的比较结果。
3. `trend`：按日、周或月的时间序列。
4. `insights`：最多 3 条带证据和行动入口的经营洞察。
5. `details`：销售、施工、财务、项目和售后分析明细。

页面和导出只消费该 interface，不自行重新计算经营指标、周期对比或洞察。

### 7.2 兼容 interface

现有 `summary` interface 继续保留，供工作台等轻量消费者使用：

- `summary` 不迁移到完整 Operational Report 查询。
- `summary` 的现有字段和权限语义保持兼容。
- 新增字段必须向后兼容；破坏性变化升级 `OperationalReport.version`。

### 7.3 内部 implementation 与 seam

- Prisma 是当前唯一真实数据来源，保留在 Operational Report module 的 implementation 内。
- 查询、指标计算、趋势聚合和洞察规则可以拆为内部函数或内部 module，但不向页面和 controller 暴露。
- 当前不公开数据 adapter interface；当出现第二个真实数据来源或独立快照来源时，再重新评估 seam。
- contract tests 穿过 Operational Report interface；不把 Prisma 查询参数作为主要 test surface。

## 8. 业务流程

### 8.1 主流程

1. 用户进入 `/reports` 或修改筛选条件。
2. 页面提交 `OperationalReportFilters`；服务端从认证上下文取得当前用户身份，不接受页面提交的用户身份作为权限依据。
3. Operational Report module 解析门店、角色和报表查询范围。
4. module 校验权限、日期范围和筛选条件。
5. module 按主日期口径查询订单集合，并按业务日期查询收款、成本和售后事实。
6. module 计算摘要、期间对比、趋势、洞察和明细。
7. module 返回带 `version`、`generatedAt`、分析区状态和截断信息的结果。
8. 页面展示结果，导出使用同一结果和筛选摘要。

### 8.2 分支流程

- 查询范围无法形成有效历史期间：返回 `comparison.status = unavailable`，不显示 0% 或“无变化”。
- 某个分析区数据不足或计算不可用：保留其他分析区，目标分析区返回 `partial` 或 `unavailable` 及原因。
- 结果明细超过 2,000 行：摘要和趋势保持完整，明细限制为 2,000 行，并返回 `rowCount` 和 `truncated = true`。
- 当前用户为销售：module 将数据范围裁剪为本人，不允许页面参数覆盖。

### 8.3 异常流程

- 无权限：返回权限错误，页面清理旧结果并显示无权限状态。
- 日期范围非法或超过 366 天：分别返回明确输入/规模错误，不执行报表查询。
- 数据源查询失败：根据失败区域返回整体错误或分析区状态，禁止用 0 替代未知结果。
- 重复请求：页面以最新请求结果为准，不覆盖较新的筛选结果。

## 9. 功能需求

### 9.1 查询范围与权限

#### 功能规则

1. 当用户没有显式传入门店时，使用当前用户所属门店；管理员和审计人员沿用现有跨门店权限规则。
2. 当用户有销售角色限制时，系统强制使用当前用户作为销售人员筛选条件。
3. `dateBasis` 支持 `DEFAULT`、`ORDER`、`APPOINTMENT`、`CONSTRUCTION_COMPLETED`、`SETTLEMENT`。
4. 查询日期范围最多 366 天，日期结束早于日期开始时视为非法。
5. 完工日期口径下，没有完工日期的在途订单不得回退到订单创建日期。
6. 结果必须返回实际使用的 `dateBasis`，页面必须展示当前日期口径摘要。

#### 验收标准

- Given：销售人员请求当前门店并传入其他销售人员 ID。
- When：调用 `operational`。
- Then：返回结果只包含当前销售人员数据，且服务端查询条件不可被前端参数覆盖。

- Given：用户传入超过 366 天的日期范围。
- When：调用 `operational`。
- Then：返回 `REPORT_DATE_RANGE_TOO_LARGE`，不执行订单、收款和明细查询。

- Given：日期结束早于日期开始，或日期格式不符合 `YYYY-MM-DD`。
- When：调用 `operational`。
- Then：返回 `REPORT_DATE_RANGE_INVALID`，不执行订单、收款和明细查询。

### 9.2 经营金额与订单状态

#### 功能规则

| 指标 | 统计规则 | 在途订单 | 缺失处理 |
|---|---|---:|---|
| 订单数 | 命中报表查询范围的订单数量 | 计入 | 无订单返回 0 |
| 订单金额 | 命中订单的总金额 | 计入 | 金额缺失按数据缺失记录，不能静默伪造 |
| 实际收款 | 查询范围内实际发生的收款金额 | 计入 | 按收款入账日期统计 |
| 待收金额 | 命中订单的累计应收余额 | 计入 | 按订单集合计算 |
| 毛利 | 订单金额减完整的实际或标准成本 | 在途订单可在成本完整时计算，但不代表已完工结算 | 成本不完整时为 `null/待补齐` |
| 完工指标 | 仅对满足完工条件的订单计算 | 不计入适用分母 | 本期只要求分母语义，不新增字段 |

规则：

1. 在途订单金额为 ¥3,800、已收 ¥1,000、待收 ¥2,800 时，摘要必须分别返回 `380000`、`100000`、`280000` 分。
2. 成本不完整的订单可以进入财务明细，但 `grossProfitCents` 必须为 `null`，`costSource` 为“待补齐”。
3. 不允许用 0 代替缺失成本、缺失毛利或无法计算的完工指标；成本来源为“标准”时必须显式标注为标准成本。

### 9.3 日期口径与趋势

| 事实 | 统计日期 | 规则 |
|---|---|---|
| 订单金额、订单数 | 订单业务日期；默认使用订单创建/确认日期 | 由 `dateBasis` 决定订单集合 |
| 实际收款 | 收款实际发生/入账日期 | 不因订单日期口径改变 |
| 施工成本 | 成本确认或结算日期 | 缺失时标记成本不完整 |
| 售后费用 | 费用确认日期 | 缺失时标记数据覆盖不足 |

规则：

1. 订单 7 月创建、8 月收款时，查询 7 月订单日期范围，订单金额可以进入 7 月，8 月收款不归入 7 月收款趋势。
2. 趋势范围不超过 7 天按日，8–90 天按周，超过 90 天按月。
3. 周一为周起始日，日期边界使用 `Asia/Shanghai`。
4. 订单金额和收款可因业务日期不同落入不同趋势期间；结果不得强行合并为一个期间。
5. 毛利趋势在成本不完整时为 `null`，同时返回成本完整度和待补齐数量。

### 9.4 期间对比

| 当前查询范围 | 对比范围 |
|---|---|
| 完整自然月 | 上一个自然月 |
| 未结束自然月 | 上月同期天数 |
| 自定义日期范围 | 前一个等长周期 |
| 无法形成有效历史范围 | 不提供可比结果 |

结果规则：

- 上期为 0、本期大于 0：`status = new`。
- 当前值和对比值均为 0：`status = unchanged`。
- 可计算差异：返回 `status = comparable` 和 `changeBps`。
- 无有效历史范围或指标不可比：返回 `status = unavailable`、`changeBps = null`、`reason` 和原因枚举。

### 9.5 经营洞察

每条洞察必须包含：`severity`、`title`、`evidence`、`action`，可选 `targetView` 和 `filters`。

本期规则：

| 洞察 | 触发条件 | 必须包含的证据 | 行动入口 |
|---|---|---|---|
| 收款落后于订单金额 | 收款率低于 80% 且待收金额大于 0 | 订单金额、实际收款、待收金额 | 财务明细 + 部分收款筛选 |
| 成本数据待补齐 | 存在成本来源为“待补齐”的订单 | 待补齐订单数、成本完整度 | 财务明细 + 待补齐筛选 |
| 人员贡献集中 | 单人员金额占比至少 50%，且至少 3 单 | 人员金额、团队占比、订单数 | 销售分析 + 人员筛选 |
| 售后比例偏高 | 售后率至少 10%，且施工订单不少于 10 单 | 售后数、施工订单数、售后率 | 售后人员分析 |

规则：

1. 最多返回 3 条洞察。
2. 洞察不足以达到样本量或证据条件时不生成。
3. 本期所有洞察使用 `WARNING`，不引入主观等级。
4. 洞察点击由页面切换到 `targetView` 并应用 `filters`，不由页面根据标题猜测条件。

### 9.6 结果版本、分析区状态与明细规模

1. `OperationalReport.version` 当前为 `1`。
2. 新增字段应向后兼容；破坏性变更必须升级版本。
3. `modules.summary`、`modules.trend`、`modules.insights`、`modules.details` 至少返回 `status`。
4. `status` 可为 `ready`、`partial`、`unavailable` 或 `error`：`partial` 表示结果可用但存在数据缺失，`unavailable` 表示当前条件无法计算，`error` 表示处理失败；`unavailable/error` 必须提供 `errorCode` 或 `reason`。
5. `modules.details` 返回 `rowCount` 和 `truncated`。
6. 明细单次最多返回 2,000 行；摘要、趋势和洞察不能因明细截断而失真。
7. 返回 `generatedAt`，页面和导出显示同一查询结果的生成时间。

### 9.7 页面、导出与兼容

1. `/reports` 页面通过一个 `operational` 请求获取完整分析结果。
2. 页面不自行计算摘要、对比、趋势或洞察，只负责展示和筛选交互。
3. 导出使用页面当前的 Operational Report 结果，不重新查询另一套口径。
4. 导出必须包含当前筛选摘要、日期口径、生成时间、数据完整度、洞察和截断提示。
5. 现有 `summary` 消费者继续使用原 interface，不因本次深化被迫迁移。
6. 无数据、局部失败、权限失败和查询超限分别展示对应状态。

## 10. 数据与字段

### 10.1 查询字段

| 字段 | 含义 | 类型 | 必填 | 数据来源 | 规则 |
|---|---|---|---:|---|---|
| `storeId` | 目标门店 | string | 否 | 用户上下文或 query | 无值时按权限推断 |
| `dateFrom` | 日期开始 | YYYY-MM-DD | 否 | 页面筛选 | 与 `dateTo` 共同校验 |
| `dateTo` | 日期结束 | YYYY-MM-DD | 否 | 页面筛选 | 最多覆盖 366 天 |
| `dateBasis` | 主日期口径 | enum | 否 | 页面筛选 | 默认 `DEFAULT` |
| `salesPersonId` | 销售人员 | string | 否 | 页面筛选 | 服务端按角色裁剪 |
| `workerUserId` | 施工人员 | string | 否 | 页面筛选 | 只影响允许范围 |
| `constructionType` | 施工类型 | string | 否 | 页面筛选 | 使用真实订单值 |
| `productCategory` | 产品分类 | string | 否 | 页面筛选 | 使用真实产品分类 |
| `orderStatus` | 订单状态 | string | 否 | 页面筛选 | 不新增状态 |
| `costSource` | 成本来源 | enum | 否 | 页面筛选 | `实际`、`标准`、`待补齐` |
| `collectionStatus` | 收款状态 | enum | 否 | 页面筛选 | `已收清`、`部分收款`、`未收款` |
| `afterSaleStatus` | 售后状态 | string | 否 | 页面筛选 | 使用真实售后状态 |
| `afterSaleResponsibility` | 售后责任 | string | 否 | 页面筛选 | 使用真实责任值 |

### 10.2 结果字段

| 字段 | 含义 | 类型 | 规则 |
|---|---|---|---|
| `version` | 结果契约版本 | `1` | 破坏性变化升级 |
| `dateBasis` | 实际使用的主日期口径 | enum | 必须与查询结果一致 |
| `summary` | 当前范围汇总 | object | 在途订单计入经营金额 |
| `comparison` | 同口径历史对比 | object | 无法比较时 `unavailable`，必须包含 `reason` |
| `trendGranularity` | 趋势粒度 | enum | day/week/month |
| `trend` | 指标趋势 | array | 金额和收款按各自业务日期 |
| `insights` | 经营洞察 | array | 最多 3 条，必须有证据和动作 |
| `modules` | 分析区状态 | object | 支持局部状态和明细规模 |
| `generatedAt` | 结果生成时间 | ISO datetime | 由服务端生成 |
| `financeOrders` | 财务订单明细 | array | 最多返回 2,000 行 |

`comparison.reason` 使用以下枚举：

- `NO_PREVIOUS_PERIOD`：没有可形成的历史期间。
- `NO_COMPARABLE_DATA`：存在历史期间，但当前指标没有可比数据。
- `INCOMPLETE_METRIC`：成本或业务日期不完整，指标无法可靠比较。

## 11. 状态与错误流转

### 11.1 分析区状态

| 状态 | 含义 | 页面处理 | 是否终态 |
|---|---|---|---:|
| `ready` | 该分析区可正常使用 | 展示数据 | 否 |
| `partial` | 结果可用但存在明确缺失 | 展示结果和缺失原因 | 否 |
| `unavailable` | 当前条件下无法计算 | 展示原因和调整入口 | 否 |
| `error` | 分析区处理失败 | 展示重试入口 | 否 |

状态判定规则：成本缺失但摘要可计算时为 `partial`；没有可比较期间时仅 comparison 为 `unavailable`；某分析区处理异常时为 `error`；summary 失败时整次请求失败，trend/insights/details 失败时保留其他可用分析区。

### 11.2 错误语义

| 错误类型 | 触发条件 | 结果 | 页面反馈 |
|---|---|---|---|
| 权限错误 | 用户无报表查看权限或数据范围不允许 | 请求失败 | 清理旧数据并显示无权限 |
| 输入错误 | 日期格式错误或结束早于开始 | `REPORT_DATE_RANGE_INVALID` | 提示修正筛选 |
| 查询规模错误 | 日期范围超过 366 天 | `REPORT_DATE_RANGE_TOO_LARGE` | 阻止查询和导出 |
| 局部不可用 | 某分析区数据不足或计算失败 | 其余区域保留，目标区域返回状态 | 显示原因和重试/调整入口 |
| 数据为空 | 查询合法但无匹配数据 | 正常结果，数组为空 | 显示空状态，不生成洞察 |

## 12. 技术实施要求

1. 先补齐并稳定 contract tests，再拆分或重组 ReportsService implementation。
2. contract tests 必须覆盖：
   - 店长/管理员、财务和销售的数据范围。
   - 无门店权限、日期非法、日期超过 366 天。
   - 在途订单进入金额、收款和待收。
   - 订单日期与收款日期落入不同趋势期间。
   - 成本不完整时毛利为 `null`，不按 0 计算。
   - 期间对比 `new`、`unchanged`、`comparable`、`unavailable`。
   - 洞察的触发条件、证据、目标视图和筛选条件。
   - `version`、`generatedAt`、分析区状态、`rowCount` 和 `truncated`。
3. 报表页面和导出不得引入第二套指标计算。
4. Prisma 查询仍可作为 module 内部 implementation；只有第二个真实数据来源出现时才重新评估公开 adapter seam。
5. 明细限制不得影响摘要、趋势和洞察的完整性。
6. 查询参数、结果字段和错误码必须同步更新 `packages/shared` 类型及相关 API tests。

## 13. 异常与边界情况

| 场景 | 触发条件 | 系统处理 | 用户反馈 |
|---|---|---|---|
| 在途订单 | 订单未完工但已有金额或收款 | 计入经营金额，完工指标按适用分母处理 | 显示订单状态和成本完整度 |
| 完工日期筛选 | 订单没有完工日期 | 不回退到订单创建日期 | 结果说明被排除的在途数据 |
| 跨日期事实 | 订单与收款日期不同 | 各自进入对应趋势期间 | 页面显示按指标业务日期统计 |
| 成本待补齐 | 成本来源为待补齐 | 毛利为 null，完整度降低 | 显示待补齐订单数 |
| 无可比期间 | 没有有效历史周期 | comparison 为 unavailable | 显示暂无可比数据 |
| 明细超限 | 明细超过 2,000 行 | 保留完整摘要/趋势，截断明细 | 显示总行数和截断提示 |
| 重复请求 | 用户连续修改筛选 | 以最新查询结果为准 | 不展示过期筛选结果 |
| 导出失败 | 文件生成或下载失败 | 保留当前结果，可重试 | 显示明确失败反馈 |
| 权限变化 | 页面打开后权限被收回 | 后端拒绝后续请求并清理旧数据 | 显示无权限 |
| 历史数据缺失 | 旧数据缺少成本、日期或收款 | 保留缺失状态，不自动回填 | 显示待补齐/数据不完整 |

## 16. 验收标准汇总

### 16.1 Interface 与版本

- Given：用户具有当前门店报表权限。
- When：调用 `operational`。
- Then：返回 `version = 1`、`generatedAt`、固定五类结果和四个分析区状态。

### 16.2 在途订单

- Given：存在一笔订单金额 3,800 元、已收 1,000 元、待收 2,800 元且尚未完工的在途订单。
- When：查询命中该订单。
- Then：订单金额、实际收款、待收分别计入；成本不完整时毛利为 `null`，不得显示为 0。

### 16.3 日期口径

- Given：订单 7 月创建、8 月收款。
- When：查询订单日期为 7 月的范围。
- Then：订单金额进入订单趋势，8 月收款不进入 7 月收款趋势；结果明确显示业务日期口径。

### 16.4 成本完整度

- Given：查询范围内包含成本来源为“待补齐”的订单。
- When：查看摘要、趋势、财务明细和导出。
- Then：毛利为待补齐，成本完整度和待补齐数量可见，任何缺失毛利不得转换为 0。

### 16.5 期间对比

- Given：查询范围可形成前一等长周期。
- When：当前期间有数据而上一期间为 0。
- Then：对应指标返回 `status = new`，不返回无限大百分比。

- Given：无法形成有效历史期间。
- When：查看 comparison。
- Then：返回 `status = unavailable` 和可解释原因，不显示 0% 或无变化。

### 16.6 经营洞察

- Given：收款率低于 80% 且存在待收金额。
- When：Operational Report 完成计算。
- Then：返回收款落后洞察，包含订单金额、实际收款、待收证据、`finance` 目标视图和部分收款筛选。

### 16.7 权限

- Given：当前用户是销售人员。
- When：请求其他销售人员 ID 或修改门店筛选。
- Then：返回结果仍仅包含本人允许的数据，前端参数不能扩大数据范围。

### 16.8 规模与降级

- Given：明细结果超过 2,000 行。
- When：调用 `operational`。
- Then：摘要、趋势和洞察保持完整；明细最多返回 2,000 行，并返回真实 `rowCount` 和 `truncated = true`。

- Given：趋势分析区失败但摘要查询成功。
- When：页面展示结果。
- Then：摘要和可用明细继续展示；趋势区显示不可用原因和重试入口，不把趋势替换为 0。

### 16.9 兼容性

- Given：现有工作台消费者调用 `summary`。
- When：Operational Report implementation 重组完成。
- Then：`summary` 的现有字段、权限和结果语义保持兼容，无需同步迁移工作台。

## 18. 风险与回滚原则

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| module 重组引入指标口径变化 | 财务和经营判断不一致 | 先锁定 contract tests，保留 `summary`，使用真实数据回归 |
| 实时查询在大范围数据下变慢 | 页面加载和导出变慢 | 366 天上限、2,000 行明细限制、查询计划和索引评估 |
| 局部状态契约与前端处理不一致 | 用户误解数据可用性 | shared 类型、API tests 和页面状态联合验收 |
| 洞察规则被前端重复实现 | 结论不一致 | 页面只消费 `insights`，禁止标题推断和重复计算 |
| 旧消费者受影响 | 工作台回归 | `summary` 保持兼容并运行现有测试 |

回滚原则：如果 Operational Report 深化 implementation 影响现有报表页面或工作台，保留旧实现路径和 `summary` interface；回滚不得删除已确认的结果字段，不得将待补齐数据恢复为 0。
