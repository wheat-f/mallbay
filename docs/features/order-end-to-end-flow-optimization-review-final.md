## 2. 评审结论

最终 PRD 已形成完整闭环：

- 零定金订单可以进入库存和施工流程；
- 采购到货后由采购/店长人工确认锁库；
- 施工完工进入待质检；
- 质检不通过进入返工中，并复用施工记录与审计事件；
- 质检通过后可生成 `PENDING_ACTIVATION` 待生效质保卡；
- 尾款结清后系统自动最终交付；
- 若质保卡尚未生成，最终交付事务自动生成并同时生效；
- 最终交付事务将质保卡改为 `ACTIVE`，并把 `startDate` 写为最终交付日；
- 尾款待收使用站内待办和工作台；
- 历史缺少质检记录的数据不被自动改写。

## 4. 可执行性检查

- 流程起点为订单创建，终点为质检通过且尾款结清后的自动最终交付。
- 缺货采购、部分到货、人工锁库、返工、尾款未清和无质保卡均有明确处理规则。
- 履约阶段由现有订单状态、施工状态、质检、质保和收款数据派生。
- 采购/店长、施工主管、施工人员、销售和财务的数据范围与操作边界已定义。
- 收款、财务流水、库存、质保和最终交付均要求事务一致性和幂等。
- 验收标准覆盖正常流程、返工、人工锁库、自动生成质保、待办、历史数据、权限和重复操作。

## 5. 已确认研发约定

- API 使用统一 `workflow` 对象，前端只依据 `capabilities` 判断操作入口。
- 履约阶段按确认的优先级和组合规则派生。
- 返工复用 `ConstructionRecord` 与 `AuditEvent`，不新增 `ReworkRecord`。
- 历史待核验列表由店长/管理员处理，销售仅查看本人订单提示。
- 尾款待办按 `userId + orderId + todoType + stage` 去重，已读不等于处理，结清或取消关闭。
- 质保卡状态采用 `PENDING_ACTIVATION`、`ACTIVE`、`EXPIRED`、`VOIDED`；最终交付同事务生效。
