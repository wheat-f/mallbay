## 3. 已解决的原评审阻塞项

### 3.1 最终交付角色

- 决策：由订单归属门店的店长/管理员执行。
- 施工人员、销售、财务和售后只能完成各自前置动作。
- 跨店施工门店不能仅凭施工权限完成最终交付。
- 结果：权限、审计、页面按钮和验收场景均可确定。

### 3.2 质保生成入口

- 决策：质保只在最终交付事务中自动生成并激活。
- 本轮不新增独立人工生成入口。
- 结果：避免订单完成与质保激活出现双入口和半成功状态。

### 3.3 `PENDING_DELIVERY` 语义

- 决策：仅作为内部派生状态。
- 满足最终交付条件后订单统一进入 `COMPLETED`。
- 结果：页面和报表无需把该状态当成新的业务终态。

### 3.4 重复、前置条件和并发结果

- 已完成交付的重复请求：幂等成功。
- 前置条件不满足：业务错误，并返回阻塞原因。
- 状态版本冲突：冲突错误，不覆盖他人变更。

### 3.5 事务边界

- 上层应用用例开启事务并传入事务上下文。
- deep module 负责事务内业务原子性和一致性检查。
- 审计与核心事实同事务；通知在提交成功后派发并可重试。

## 5. 评审发现与处理

### 5.1 [S2] 各契约的具体字段和错误码需要技术拆解

- 所在位置：PRD 第 6、7、11 节。
- 问题描述：PRD 已明确输入输出的业务语义，但没有提前冻结全部 TypeScript 字段名、错误码字符串和 Prisma 事务类型。
- 影响：研发需要在 contract test 阶段统一命名，避免各模块自行发明结果结构。
- 处理方式：列为每个阶段的首项研发任务；不得在页面或 Controller 中临时定义第二套口径。
- 是否阻塞本 PRD：否。

### 5.2 [S2] 历史数据完整性和迁移基线需要各阶段盘点

- 所在位置：PRD 第 9、10 节。
- 问题描述：不同模块的历史记录完整度、旧 API 消费者和旧状态字段需要在实现前逐项盘点。
- 影响：可能影响兼容适配和回归范围，但不改变本 PRD 的目标和模块边界。
- 处理方式：每阶段先建立现有行为基线和迁移清单；历史数据不得自动补造。
- 是否阻塞本 PRD：否。

### 5.3 [S3] 可增加跨模块业务追踪视图

- 建议：后续在工作台或审计页面提供订单 → 库存 → 价格 → 收款 → 质保的统一追踪入口。
- 影响：提升运营排障效率，但不是本轮 deep module contract 的必要条件。

### 5.4 [S3] 可增加契约版本兼容矩阵

- 建议：当旧 API 适配层和新 module interface 并存时，维护版本、消费者和迁移状态矩阵。
- 影响：降低渐进迁移风险，列为工程治理项。

## 6. 流程与状态评审

### 6.1 关键流程

```text
身份解析 → 能力/数据范围判断 → 调用业务 module command
       → module 内校验前置条件 → 事务内写入事实与审计
       → 提交成功 → 通知派发/重试 → 页面消费结果
```

### 6.2 状态闭环检查

| 对象 | 已检查内容 | 结论 |
|---|---|---|
| 订单履约 | 施工完成不等于订单完成；最终交付进入 `COMPLETED`；重复和冲突有结果 | 通过 |
| 库存事实 | 预留、释放、收货、出库、调整均有流水和幂等键 | 通过 |
| 价格快照 | 决策版本和订单快照冻结，历史不回算 | 通过 |
| 财务事实 | 单据状态、审批动作、现金事实分离；冲正可追溯 | 通过 |
| 权限上下文 | 新请求使用最新能力；历史审计保留操作者 | 通过 |

## 7. 权限与数据评审

- 业务模块不自行解析 JWT、成员关系或门店范围，统一消费 `AccessContext`。
- 最终交付的门店归属规则已明确。
- 客户人工标签维护与系统标签分离，且按客户维护权限控制。
- 财务数据无权限时拒绝访问，不用空数据伪装无记录。
- 跨模块读取通过摘要/投影，不反向拥有其他模块的写入事实。

结论：权限与数据范围已达到研发拆解要求。

## 8. 异常与边界评审

PRD 已覆盖：

- 无权限、资源不存在、前置条件不满足。
- 重复提交、重复生成、幂等键和并发冲突。
- 跨店施工与订单归属门店不一致。
- 库存不足、未验收收货、数量调整和流水追溯。
- 定价输入缺失、规则冲突和历史快照。
- 现金冲正、单据未收款和来源追溯。
- 通知失败重试与核心事务回滚。
- 历史数据缺失和旧 API 兼容。

结论：不存在阻塞主流程的异常遗漏。

## 9. 验收标准评审

核心规则均已转换为可测试的 Given / When / Then，且统一验收覆盖：

- 成功和幂等成功。
- 业务拒绝、权限拒绝和并发冲突。
- 事务原子性和审计一致性。
- 事实来源、快照、流水和追溯。
- 旧 API 兼容和页面反馈。

结论：可以进入 contract tests 设计。

## 10. 风险与依赖

- 研发风险：大型 service 迁移期间可能存在新旧入口并存；以 contract tests 和适配层控制。
- 数据风险：历史数据缺失不能自动补造；各阶段需输出数据盘点结果。
- 兼容风险：旧 API 不得在消费者迁移完成前删除。
- 权限风险：所有 command 必须使用 `AccessContext`，禁止调用方自行放宽范围。
- 运营风险：通知失败不影响核心事实，但必须有可观察的重试状态。

这些风险已有处理原则和阶段门槛，不构成 PRD 阻塞项。

## 11. 进入研发前置条件

1. 以本 PRD V0.2 作为需求基线。
2. 第一阶段先建立 7 个契约的类型、错误类别和 contract tests。
3. 任何改变事实所有权、状态语义、权限角色或数据口径的发现，必须回到 PRD/ADR 重新评审。
4. 代码实现前完成现有行为基线和消费者迁移清单。
5. 本轮不提交业务代码，待 PRD 评审通过后再启动第一阶段实现。
