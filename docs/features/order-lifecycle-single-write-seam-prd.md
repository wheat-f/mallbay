## 2. 需求背景

### 2.1 业务背景

订单从创建、库存准备、派工、施工、质检、收款、最终交付到质保，需要多个业务事实共同推进。既有架构已引入 `OrderLifecycle`，但当前实现仍存在平行写入路径，尚未形成可通过 deletion test 的 deep module：

- `OrderLifecycle` 的关键依赖为 optional；订单和施工入口在缺少它时回退旧 implementation。
- 施工写入通过运行期 `registerConstructionHandler` 挂接，只有一个 adapter，属于 hypothetical seam。
- `OrdersModule` 同时导出 `OrderLifecycle`、`CreateOrderUseCase` 与 `OrdersService`，调用方可绕过正式 interface。
- 报价转订单直接调用 `CreateOrderUseCase`，报价认领、订单创建、报价关联与审计不在同一事务，存在重复建单窗口。
- 施工完工的提成快照、施工成本结算初始化和跨店通知在核心写入事务之后执行，失败时可能出现“已经完工但调用失败”。
- 派工、开工、完工、质检、取消和回退缺少统一的命令幂等与并发控制；不同命令可能覆盖已变化的履约事实。
- Web 仍能根据余额或原始状态回退推断履约能力与步骤；小程序的 `clientOperationId` 只回显、不持久化结果。
- 创建订单时的首次定金只形成订单收款明细，未同步形成现金事实。

V1.15 实施补充：施工证据上传和离线请假均持久化 `clientOperationId`，对象键可由命令标识稳定重放；已通过质检的订单禁止无新完工事实重复 PASS；历史核验查看权限拆分为 `verification_view`；订单、施工任务列表/详情在权威生命周期不可用时显示可恢复阻塞，不再回退到原始状态推断。

历史 PRD 将部分收口任务标记为完成，但本需求以当前生产代码路径和数据库约束为验收依据，不沿用与代码不符的完成状态。

### 2.2 核心问题

当前调用者无法只学习一个 interface 就安全推进订单履约；状态所有权、事务、权限、幂等、错误语义和测试分散在多个调用链中，造成：

1. 同一业务意图可能产生重复订单、重复质检证据或重复附属事实。
2. 并发命令可能形成订单状态、施工记录、库存、质保或跨店任务相互矛盾的事实。
3. 调用返回失败时，部分事实可能已经提交且无法安全重试。
4. 页面和测试需要理解内部状态组合，locality 和 leverage 均不足。
5. 旧 implementation 无法删除，ADR-0012 的 replace-don't-layer 原则未落实。

### 2.3 需求依据

- 近期提交热点持续集中在 `orders`、`construction`、创建订单和字典设置；订单与施工仍是高变更区域。
- `OrderLifecycle` 删除后，现有调用者已有完整 fallback，说明当前写入 interface 仍 shallow。
- 报价转单存在“订单已提交、报价关联失败、报价恢复可重试”的事实窗口。
- 施工完工的部分同步义务位于事务外，失败后顺序重试会被状态前置条件拒绝。
- 现有 PostgreSQL 并发门禁只覆盖库存幂等与容量超售，未覆盖订单履约命令。

## 3. 产品目标

1. 建立独立应用级订单履约闭环 module，唯一导出 `OrderLifecycle` 写入 interface。
2. 让订单创建、报价转单以及所有改变订单履约过程的命令只通过该 seam 执行。
3. 让每个履约命令具备稳定的履约命令标识、履约版本、原子事务、幂等重放和并发保护。
4. 让调用端只消费权威履约结果，不自行推断阶段、履约能力或阻塞原因。
5. 保持现有 HTTP 路径与成功业务含义；错误增加稳定错误码和最新权威履约结果。
6. 以 interface contract 和真实 PostgreSQL 并发测试替代 pass-through、fallback 与内部调用顺序测试。
7. 完成后删除 optional dependency、运行期注册、生产 fallback 与浅层写入导出，使 deletion test 成立。

### 3.1 上线验证方向

- 履约版本已变化但版本变更账本缺失：必须为 0；由履约命令产生的版本变化还必须关联命令记录。
- 施工完工但提成快照或施工成本结算初始化缺失：必须为 0。
- 同一报价关联多个订单：必须为 0。
- 同一履约命令标识产生多个业务结果：必须为 0。
- 其他指标基线与告警阈值在开发完成后的预发压测中采集，不在本 PRD 虚构目标值。

## 4. 本期范围

### 4.1 纳入范围

- 正式订单创建与普通下单幂等。
- 已批准报价转正式订单的强原子转换。
- 派工、开始施工、施工完工、质检、最终交付、订单取消、回退到待派单。
- 跨店施工任务接受、拒绝、取消、提交来源验收、来源门店验收。
- 权威履约结果查询与批量履约能力查询。
- 履约版本递增与命令结果持久化。
- 库存、现金、质保、履约待办等事实变化对履约版本的同步失效。
- 首次定金现金事实补齐。
- Web、施工 Web 调用端迁移；小程序保留现有兼容 adapter，本轮不纳入订单履约闭环发布门禁。
- 订单创建、订单详情、派工、施工任务、质检、跨店协作和离线队列的页面操作适配。
- 维护窗口迁移、历史核验、监控与发布门禁。

### 4.2 非目标

- 不拆微服务，不引入跨网络 port。
- 不引入事件溯源或将订单现有所有数据迁入单一聚合表。
- 不把库存流水事实、施工证据、现金事实、成本结算结果或质保事实的所有权移给订单履约闭环。
- 不把施工照片、材料领取、材料损耗、排班、请假、容量配置、成本确认与结算、跨店产品映射维护纳入外部履约 interface。
- 不重新设计订单页面视觉；不新增持久化的 `OrderStatus` 业务状态。允许补充能消除调用端推断的派生履约阶段，但派生阶段不得反向成为另一套写入状态机。
- 不要求用户手工填写或复制命令 ID、履约版本、请求指纹等技术字段；它们由调用端管理。
- 不允许旧新 implementation 双写核心事实。
- 不保留旧应用节点与新应用节点长期混跑。
- 不自动修复相互矛盾的历史事实。

### 4.3 本轮延期范围

按当前交付优先级，小程序真机联调、页面迁移和小程序专用 E2E 暂不纳入本轮订单履约闭环收口；小程序继续使用现有兼容 adapter，不改变 API/Web 唯一写入 seam。后续重新纳入时，需单独补齐小程序类型、离线关键路径、真机和预发门禁，并重新评审 AC-14/AC-18 的范围。

## 5. 用户角色与权限

权限继续由 `AccessContext` 和已发布权限数据决定；下表描述本需求不得突破的业务范围。

| 角色 | 数据范围 | 可发起履约命令 | 明确禁止 |
|---|---|---|---|
| 总部管理员 | 有效总部范围及授权门店 | 按现有全局能力执行门店级命令 | 不因总部身份绕过命令前置事实 |
| 归属门店店长 | 本门店订单 | 创建、派工、质检、最终交付、取消、允许的回退、跨店来源验收 | 不直接改写库存、现金或施工证据 |
| 销售 | 本人订单或现有授权范围 | 普通下单、本人报价转单、允许的未开工回退 | 不执行最终交付；不取消已有不可逆事实的订单 |
| 客服 | 本门店现有订单写范围 | 普通下单、允许的订单资料处理 | 不执行最终交付与施工命令 |
| 排班员 | 授权施工门店 | 派工、质检及现有施工管理权限允许的跨店命令 | 不执行归属门店最终交付 |
| 施工人员/学徒 | 本人已派工任务 | 开工、完工；通过离线队列重放本人命令 | 不执行派工、最终交付和非本人任务命令 |
| 财务 | 授权门店 | 记录现金事实；现金变化同步使履约版本失效 | 不以收款动作隐式最终交付 |
| 采购/库存人员 | 授权门店 | 写入库存预留/出库等事实；相关变化同步使履约版本失效 | 不直接改写订单履约状态 |

无权限时返回稳定 `FORBIDDEN`，不得用空结果隐藏写入拒绝，也不得泄露无权访问的订单最新结果。

命令级权限必须同时满足 capability、scope 和业务所有权，禁止仅按岗位字符串放行：

| 命令 | 必需 capability / scope | 附加所有权条件 |
|---|---|---|
| `CREATE_ORDER` / `CONVERT_QUOTE_TO_ORDER` | `orders:write` | 销售为 `OWN` 时，客户、报价及新订单销售归属必须为本人；门店级角色按授权门店 |
| `DISPATCH` / `QUALITY_CHECK` | 执行门店 `construction:write` | 无额外 owner bypass |
| `START_CONSTRUCTION` / `COMPLETE_CONSTRUCTION` | 执行门店 `construction:write`，或当前用户为工单有效 assignment | owner bypass 只允许本人已分配工单，不扩大到同岗位其他任务 |
| `FINAL_DELIVERY` | 归属门店 `orders.lifecycle:finalize`（`STORE`/`GLOBAL`） | 默认绑定归属门店店长和有效总部管理员；执行门店权限不能替代 |
| `CANCEL` | 归属门店 `orders.lifecycle:cancel`（`STORE`/`GLOBAL`） | 默认绑定归属门店店长和有效总部管理员 |
| `RETURN_TO_PENDING_DISPATCH` | 归属门店 `orders:write` | `OWN` scope 仅本人订单；门店 scope 可处理授权门店订单 |
| `RESOLVE_LIFECYCLE_VERIFICATION` | 归属门店 `orders.lifecycle:verification_resolve`（`STORE`/`GLOBAL`） | 默认绑定归属门店店长和有效总部管理员；必须命中订单当前 `OPEN` 核验单，发现人身份不能替代关闭权限 |
| 跨店接受/拒绝/提交验收 | 执行门店 `construction:write` | 必须命中任务的 `executionStoreId` |
| 跨店取消/来源验收 | 来源门店 `orders.lifecycle:cross_store_source_manage`（`STORE`/`GLOBAL`） | 默认绑定来源门店店长和有效总部管理员；必须命中任务的 `sourceStoreId`，执行门店 `construction:write` 不能替代 |

本需求新增以上四个 `orders.lifecycle` 细粒度 action，并在权限策略迁移中按默认角色绑定；它们不等同于宽泛的 `store:write`。当前 legacy 权限表未给门店店长 `store:write`，因此不得复用该 capability，否则会错误禁止店长履约。动态权限策略可在上述默认绑定上收紧，但不得把执行门店施工权限提升为归属门店终交/来源管理权限。权限策略版本、绑定和缓存失效必须在恢复写入前生效；不得在履约 implementation 中增加岗位字符串判断或 optional 权限回退。

## 6. 核心业务对象

| 对象 | 定义 | 唯一标识 | 关键数据 | 创建/关闭条件 | 归属 |
|---|---|---|---|---|---|
| 订单 | 客户购买商品与施工要求形成的业务单据 | `orderId`、`orderNo` | 原始状态、归属门店、执行门店、履约版本 | 下单/报价转单创建；取消或最终交付进入终态 | 订单 module |
| 履约命令 | 经权限、前置事实与事务校验后改变订单履约事实的业务动作 | `storeId + commandId` | 命令类型、操作者、目标、期望版本、请求指纹、最小输入摘要 | 调用端发起；业务成功或稳定拒绝后记录结果 | 订单履约闭环 module |
| 履约版本变更 | 一次已提交业务事务对权威履约结果造成的版本失效记录 | `orderId + afterVersion` | 来源类型、来源键、前后版本、最小来源引用 | 新建订单或相关事实事务提交时形成；不单独删除 | 订单履约闭环 module |
| 履约核验单 | 记录历史或运行期发现的跨事实矛盾及其处置状态 | `verificationCaseId` | 订单、稳定问题码、状态、检测/解决人和时间 | 迁移预检或对账发现时创建；事实纠正且复核通过后关闭 | 订单履约闭环协调，相关事实 owner 负责纠正 |
| 权威履约结果 | 阶段、能力、阻塞原因和版本的统一业务结果 | `orderId + lifecycleVersion` | 阶段、能力、阻塞原因、事实摘要、生成时间 | 查询或命令成功后生成 | 订单履约闭环 module |
| 履约待办 | 必须由后续业务动作完成或关闭的责任记录 | 待办标识/去重键 | 类型、责任人、订单、当前处理状态 | 相关履约事实产生；后续动作或终态关闭 | 订单履约闭环协调，通知 module 负责触达 |
| 施工证据 | 照片、材料、质检和现场记录 | 各事实 ID | 阶段、操作者、发生时间、撤销/补充关系 | 施工过程追加；不可静默覆盖 | 施工 module |
| 现金事实 | 实际收款、付款、退款、冲销及来源关系 | `paymentRecordId` | 方向、金额、来源、发生日期、幂等键 | 实际现金动作形成；反向事实更正 | 财务 module |
| 库存流水事实 | 库存数量、批次、单位和来源变化 | `movementId` | 数量、单位、批次、来源、幂等键 | 库存动作形成；不可静默覆盖 | 库存 module |

### 6.1 新增数据字段

#### Order

| 字段 | 类型 | 必填 | 默认值 | 规则 |
|---|---|---:|---|---|
| `lifecycleVersion` | Int | 是 | 新订单为 1；历史订单迁移为 1 | 每个改变权威履约结果的已提交业务事务恰好递增 1；同一事务改变多个相关事实仍只递增一次；只允许单调递增 |

#### OrderLifecycleCommandRecord

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `id` | String | 是 | 内部主键 |
| `orderId` | String? | 创建完成后是 | 创建/报价转单在事务开始占用命令标识时为空，订单生成后于同一事务回填；其他命令开始时必填 |
| `storeId` | String | 是 | 用于门店范围与命令唯一约束 |
| `commandId` | String | 是 | 调用端提供的履约命令标识 |
| `commandType` | Enum/String | 是 | 取本 PRD 定义的命令集合 |
| `actorId` | String | 是 | 命令标识绑定操作者 |
| `targetType` / `targetId` | String | 是 | `ORDER`、`QUOTE` 或 `ORDER_CREATION` 及其目标；普通创建以门店和创建意图为目标，不依赖尚未生成的订单 ID |
| `requestFingerprint` | String | 是 | 规范化请求的不可逆摘要，仅用于识别同一命令 ID 下输入是否被改变；不得把摘要当作命令 ID，也不得保存敏感原文 |
| `expectedVersion` | Int? | 创建命令否，其余是 | 命令所依据的履约版本 |
| `beforeVersion` | Int? | 成功写命令是 | 实际执行前版本 |
| `afterVersion` | Int? | 成功写命令是 | 实际执行后版本 |
| `status` | Enum | 是 | 仅持久化 `SUCCEEDED` 或 `REJECTED`；系统失败整体回滚，不留下半成品状态 |
| `inputSummary` | Json | 是 | 最小业务摘要，不保存联系方式、照片内容或完整敏感载荷 |
| `resultSummary` | Json? | 成功/拒绝后是 | 权威结果或稳定错误摘要 |
| `createdAt` / `completedAt` | DateTime | 是/否 | 记录处理时间 |

唯一约束：

- 普通命令：`storeId + commandId` 唯一。
- 同一 `commandId` 只能绑定一个 `actorId`、一个命令类型、一个业务目标和一个 `requestFingerprint`；任一不匹配时返回 `COMMAND_ID_CONFLICT`。
- 报价转单额外保证 `quoteId` 只能成功创建一个正式订单。
- 命令记录随订单履约事实保留，不单独物理删除。

命令执行协议：

1. 通过认证与数据范围校验后，在业务事务的第一步插入命令记录占位；创建命令此时允许 `orderId = null`。
2. 数据库唯一约束串行化同一 `storeId + commandId` 的并发请求。后到请求在前一事务提交后读取并重放结果；若前一事务回滚，则可重新占位并执行。
3. 业务前置条件不满足时，不抛出导致事务回滚的异常；事务仅提交 `REJECTED` 命令结果，不提交业务事实。
4. 成功时，业务事实、版本变更、审计、命令结果和创建命令的 `orderId` 回填同一事务提交。
5. 未分类系统错误回滚全部写入，不持久化 `FAILED`/`PROCESSING`；调用端可用同一命令 ID 安全重试。
6. `FORBIDDEN` 与不可见资源的 `ORDER_NOT_FOUND` 在占用命令标识前返回，不持久化结果，避免越权者抢占或探测命令标识。

#### OrderLifecycleVersionChange

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `id` | String | 是 | 内部主键 |
| `orderId` | String | 是 | 关联订单 |
| `beforeVersion` / `afterVersion` | Int | 是 | 新建订单为 `0 → 1`；其余必须为 `N → N+1` |
| `sourceType` | Enum/String | 是 | `COMMAND`、`INVENTORY`、`CASH`、`WARRANTY`、`TODO` 或经评审新增的权威事实来源 |
| `sourceKey` | String | 是 | 命令记录 ID、库存流水 ID、现金事实 ID等稳定来源键 |
| `sourceRefs` | Json? | 否 | 同一事务涉及多个相关事实时保存最小 ID 引用，不保存敏感载荷 |
| `createdAt` | DateTime | 是 | 数据库提交时间 |

唯一约束为 `orderId + afterVersion` 和 `sourceType + sourceKey`。命令事务改变多个相关事实只形成一条版本变更；外部事实拥有者的独立事务各自形成一条。事实写入、订单版本递增和版本变更记录必须同事务提交。

#### OrderLifecycleVerificationCase

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `id` | String | 是 | 内部主键 |
| `orderId` | String | 是 | 关联订单 |
| `issueCodes` | Json/Array | 是 | 稳定问题码集合，不只保存中文说明 |
| `status` | Enum | 是 | `OPEN` / `RESOLVED`；每个订单最多一个 `OPEN` 核验单 |
| `detectedAt` / `detectedBy` | DateTime/String | 是 | 迁移脚本使用固定系统 actor |
| `resolutionSummary` | Json? | 解决时是 | 关联实际纠正事实/审计 ID，不复制敏感载荷 |
| `resolvedAt` / `resolvedBy` | DateTime?/String? | 解决时是 | 有权限人员复核后填写 |

存在 `OPEN` 核验单或实时一致性校验发现矛盾时，普通履约命令必须阻断。核验单本身不得直接篡改订单、现金、库存、质保或施工事实；责任模块通过正常纠正/反向事实流程修复。关闭核验单前必须重新执行全部相关一致性校验，关闭事务递增履约版本、写版本变更和数据库审计。运行期新发现但尚无核验单的矛盾应立即告警，并由对账任务幂等创建核验单。

核验单查看权限沿用订单读取范围；相关事实只能由其既有写权限角色纠正；关闭核验单仅允许归属门店 `orders.lifecycle:verification_resolve`（默认绑定门店店长和有效总部管理员），并要求 `resolutionSummary` 至少引用一条纠正事实/审计 ID。发现人不能仅通过填写说明关闭核验单。该 action 与前三个 action 同批发布。

#### SalesQuote 页面幂等字段

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `idempotencyKey` | String? | 新版本创建是；历史记录否 | 报价创建业务意图标识；不展示给用户 |
| `idempotencyActorId` | String? | 新版本创建是；历史记录否 | 与创建操作者绑定 |
| `requestFingerprint` | String? | 新版本创建是；历史记录否 | 规范化报价输入摘要，不保存敏感原文 |

新唯一约束为 `storeId + idempotencyActorId + idempotencyKey`。历史报价保持为空，不回填虚构标识。相同键同指纹返回原报价，相同键不同指纹返回 `COMMAND_ID_CONFLICT`；报价创建、明细、审批记录和容量软占位仍须保持原有事务原子性。

## 7. Interface 与 module 范围

### 7.1 外部 interface

订单履约闭环 module 只提供三类能力：

```text
createOrder(actor, commandContext, input) -> LifecycleCommandResponse
executeCommand(actor, orderId, commandContext, command) -> LifecycleCommandResponse
getLifecycle(actor, orderId | orderIds) -> AuthoritativeLifecycleResult | map
```

批量 `getLifecycle` 必须逐订单返回可判别的成功结果或安全错误，不得因单个订单异常使整批失败；无权/不存在项不得返回该订单事实摘要。调用端可对失败项按原订单 ID 单独重试，但不得以原始状态回退计算阶段。

`commandContext` 至少包含：

- `commandId`
- `expectedVersion`（非创建命令必填）
- 调用来源（Web、施工 Web、小程序、报价转换、兼容 adapter）

`createOrder` 的 `input.source` 仅允许：

- `DIRECT`：普通下单，执行普通创建规则；
- `APPROVED_QUOTE`：必须携带 `quoteId`，在同一创建事务执行报价认领、订单创建、报价关联与审计。

不得另行导出 `CreateOrderUseCase` 或报价专用建单写入 interface。报价 service 只能把 transport/domain 输入适配到 `createOrder(source=APPROVED_QUOTE)`。

不得通过外部 interface 传递 Prisma transaction、数据库记录、内部 implementation 或任意状态目标。

`LifecycleCommandResponse` 为可判别结果：

| `outcome` | 含义 | 是否写业务事实 | 是否递增版本 | 必返内容 |
|---|---|---:|---:|---|
| `APPLIED` | 本命令首次实际应用 | 是 | 恰好 1 | 权威履约结果 |
| `ALREADY_SATISFIED` | 新命令 ID 到达时，目标已由其他成功命令满足 | 否 | 否 | 当前权威履约结果；持久化本命令结果，不新增业务审计/通知 |
| `REPLAYED` | 同命令 ID、同 actor/目标/类型/指纹重放 | 否 | 否 | 原始 `APPLIED`、`ALREADY_SATISFIED` 或 `REJECTED` 的完整可观察结果，并标记本次为重放 |
| `REJECTED` | 权限后的稳定业务校验或并发校验失败 | 否 | 否 | 稳定错误码、参数；有权时按错误规则附最新权威履约结果 |

transport adapter 将 `REJECTED` 映射为第 12 节 HTTP 响应；成功结果继续保持现有 endpoint 的兼容成功字段，并追加/映射权威结果。`FORBIDDEN` 与不可见资源的 `ORDER_NOT_FOUND` 在 interface 安全边界直接失败，不进入可重放结果。

### 7.2 内部 implementation

以下能力位于 implementation 内部，可接受同一 transaction-scoped context，但不得从 Nest module 导出：

- 创建订单及报价转单原子写入。
- 施工派工、开工、完工、质检的事实写入。
- 跨店任务状态写入。
- 施工完工时提成快照与施工成本结算初始化。
- 首次定金现金事实写入。
- 履约待办创建/关闭。
- 履约版本递增及事实来源记录。
- 数据库审计事实写入。
- 履约核验单重校验、关闭及其版本变更写入。

Prisma 属于 local-substitutable dependency，测试使用本地数据库/真实 PostgreSQL stage gate，不在 external seam 新增 port。

### 7.3 查询 module 约束

订单列表、订单详情、施工列表可继续属于各自查询 module，但必须：

- 从同一数据库快照读取履约所需事实；
- 使用订单履约闭环提供的权威解释；
- 返回与快照一致的 `lifecycleVersion`；
- 不再调用 `getEffectiveOrderStatus`、页面 `getOrderSteps` 或余额/状态 fallback 推断履约语义。

## 8. 命令通用规则

### R-COMMAND-01 命令标识与重放

- 条件：同一操作者、同一业务对象、同一命令类型再次提交相同 `commandId`。
- 动作：系统读取已持久化命令结果，不重复执行业务写入。
- 结果：返回第一次的成功或稳定拒绝结果；不追加审计、证据、待办或通知意图。
- 例外：同一 `commandId` 被其他操作者、其他命令类型或其他对象使用时返回 `COMMAND_ID_CONFLICT`。
- 系统失败不形成可重放的业务结果；事务全部回滚后，同一命令标识再次进入正常占位流程。
- `requestFingerprint` 由命令类型、业务目标和规范化业务输入计算；排除 trace ID、传输头和服务端时间，保留会改变业务结果的用户输入。相同 ID 但指纹不同必须冲突，不能“重放旧结果假装接受新输入”。

### R-COMMAND-02 履约版本并发控制

- 条件：非创建命令提交 `expectedVersion`。
- 动作：系统在同一事务内按 `orderId + lifecycleVersion + 允许的来源状态` 条件更新。
- 结果：`APPLIED` 后履约版本恰好递增 1 并返回最新权威履约结果；`ALREADY_SATISFIED`、`REPLAYED` 和 `REJECTED` 不递增。
- 例外：版本或来源状态不匹配时返回 `LIFECYCLE_VERSION_CONFLICT`、最新版本和最新权威履约结果；无权用户不返回最新结果。

### R-COMMAND-03 原子事务

- 条件：履约命令涉及多个同步事实。
- 动作：由订单履约闭环开启唯一数据库事务，内部 implementation 使用同一 transaction-scoped context。
- 结果：核心事实、数据库审计、履约待办、命令记录、版本变更账本和履约版本全部成功或全部回滚。
- 例外：外部通知投递与进程日志在提交后执行，失败不回滚核心事实。

### R-COMMAND-04 权威结果

- 条件：查询履约或命令成功。
- 动作：使用单条一致性查询，或在 PostgreSQL `REPEATABLE READ`（或更强）只读事务中读取订单、施工、库存、现金/金额、质保、跨店任务和履约待办；不得依赖默认 `READ COMMITTED` 下的多条查询拼接快照。
- 结果：返回阶段、能力、阻塞原因、履约版本、必要事实摘要和 `generatedAt`。
- 例外：事实矛盾时返回 `HISTORICAL_VERIFICATION_REQUIRED`，不得静默修复。

命令成功结果在同一写事务内由提交后的事实构造，并携带该事务写入的 `afterVersion`；transport 只有在事务提交成功后才能返回。若提交结果未知（连接在 commit 窗口中断），调用端使用同一命令 ID 重试，由命令记录判定是重放还是重新执行。

### R-COMMAND-05 履约版本失效

- 条件：订单状态、施工阶段、质检、库存预留/释放/出库、现金事实、质保或履约待办的变化会改变权威履约结果。
- 动作：事实拥有者在同一事务中调用仅供内部 implementation 使用的版本失效机制。
- 结果：该业务事务令 `lifecycleVersion` 恰好递增 1，并形成一条 `OrderLifecycleVersionChange`；同一事务内多个相关事实 ID 归入其 `sourceRefs`。
- 例外：只改变不参与履约解释的展示字段时不递增。

事实拥有者不得反向调用 public `executeCommand`，也不得直接更新 `Order.lifecycleVersion`。库存、现金、质保和待办 implementation 只能使用履约 module 提供的 transaction-scoped 内部版本失效函数；该函数接收已有事务、订单 ID、来源类型和稳定来源键，保证条件递增与账本同写。缺少来源键或重复来源键必须使事实事务失败，不能形成“事实已写、版本未变”。

### R-COMMAND-06 新命令 ID 到达已满足目标

新命令 ID 表示新的业务意图，不等同于网络重试。只有目标状态及不可变业务输入均已满足时才返回 `ALREADY_SATISFIED`；不能利用该结果静默接受不同输入：

| 命令 | 已满足时的处理 |
|---|---|
| `CREATE_ORDER` | 新 ID 始终是新建意图；通过正常校验后可创建另一订单，不按内容摘要跨 ID 去重 |
| `CONVERT_QUOTE_TO_ORDER` | 报价已关联订单时返回 `ALREADY_SATISFIED` 及该订单；报价与订单关系异常时进入历史核验 |
| `DISPATCH` | 已有工单且有效 assignments 与请求完全一致时返回 `ALREADY_SATISFIED`；人员集合不同则 `COMMAND_PRECONDITION_FAILED`，必须先走合法回退 |
| `START_CONSTRUCTION` | 已开工且请求未指定不同 `startedAt`（或时间一致）时返回 `ALREADY_SATISFIED`；不同时间不得覆盖 |
| `COMPLETE_CONSTRUCTION` | 已完工且提成、成本结算等同步义务齐全，请求未指定不同 `completedAt`（或时间一致）时返回 `ALREADY_SATISFIED`；义务缺失进入历史核验，不在重试中补写 |
| `QUALITY_CHECK` | 已存在质检结果不视为新命令目标已满足；同 ID 才重放。新 ID 必须满足“上次不通过 → 重新完工 → 复检”的前置事实，否则拒绝 |
| `FINAL_DELIVERY` | 已完整交付且质保/待办一致时返回 `ALREADY_SATISFIED`；事实不一致进入历史核验 |
| `CANCEL` | 已合法取消且关联待办/预留/任务已同步收口时返回 `ALREADY_SATISFIED`；收口不完整进入历史核验 |
| `RETURN_TO_PENDING_DISPATCH` | 已处于待派单且无残留 assignment/占用时返回 `ALREADY_SATISFIED`；有残留事实进入历史核验 |
| `RESOLVE_LIFECYCLE_VERIFICATION` | 核验单已关闭且纠正事实引用、解决说明与请求完全一致时返回 `ALREADY_SATISFIED`；输入不同或仍有矛盾时拒绝，不允许覆盖既有解决记录 |
| 跨店状态命令 | 当前任务已在目标状态且原因、备注等不可变输入一致时返回 `ALREADY_SATISFIED`；输入不同或已越过目标状态时拒绝，不倒退覆盖 |

所有 `ALREADY_SATISFIED` 均持久化本命令的成功结果，但不写业务审计、通知意图、版本变更或任何领域事实。

## 9. 业务流程

### 9.1 普通下单

1. Web 生成稳定 `commandId` 并提交订单输入。
2. 订单履约闭环校验权限、客户/车辆、产品单位、定价决策、容量与跨店映射。
3. 系统在同一事务创建订单、明细、价格/成本快照、容量预留、跨店任务、初始定金明细与初始定金现金事实。
4. 系统写数据库审计和命令成功结果，订单履约版本为 1。
5. 提交后发送非核心通知；返回权威履约结果。
6. 相同命令标识重试返回原订单结果。

### 9.2 报价转订单

1. 销售或店长对有效已批准报价发起转单，提交稳定 `commandId`。
2. 系统校验报价权限、有效期、车辆、成本完整度与冻结快照。
3. 同一事务内条件认领报价、创建订单及关联事实、写回 `convertedOrderId`、写数据库审计和命令结果。
4. 任一步骤失败整体回滚，报价保持可安全重试的原状态且不存在孤儿订单。
5. 相同报价无论使用新旧命令标识再次转单，都返回已关联订单，不创建第二个订单。

### 9.3 派工与开工

1. 排班员/店长基于最新履约版本派工。
2. 系统校验待派单阶段、执行门店权限、施工人员岗位、请假和跨店状态。
3. 同一事务创建施工记录和人员分配、更新订单/跨店任务、审计、命令记录并递增版本。
4. 已派工人员基于最新版本开工；系统条件更新订单、施工记录和跨店任务。
5. 并发取消、回退或重复开工只能有一个命令成功。

### 9.4 施工完工

1. 已派工人员基于最新版本提交完工命令。
2. 系统校验订单正在施工、施工前后照片、已锁材料均已领取。
3. 同一事务更新施工记录/跨店任务，形成提成快照，初始化施工成本结算，写审计、命令记录、通知意图并递增版本。
4. 任一同步义务失败整体回滚，订单仍可用相同命令标识安全重试。
5. 外部通知投递失败不改变完工结果，由投递意图重试。

### 9.5 质检与复检

1. 有权限角色基于最新版本提交质检命令。
2. 质检不通过必须提供返工原因和责任类型；系统追加质检历史并回到返工阶段。
3. 返工重新完工后，新的真实复检使用新的命令标识；系统追加新的质检历史。
4. 同一质检命令标识重试返回原结果，不追加历史、不递增返工次数。
5. 质检通过后，系统同步创建或更新余额履约待办，并递增版本。

### 9.6 收款与首次定金

1. 初始定金在订单创建事务中同时形成 `OrderPayment` 和 `PaymentRecord(ORDER_PAYMENT)`，并更新订单金额摘要。
2. 后续收款仍由现金事实拥有者写入，订单履约闭环不夺取现金事实所有权。
3. 后续收款、退款或冲销若改变支付状态、阻塞原因或履约能力，必须在同一事务递增履约版本。
4. 收款完成只解除余额阻塞，不自动最终交付。

### 9.7 最终交付

1. 归属门店店长/管理员基于最新版本发起最终交付。
2. 系统校验施工完工、质检通过、余额为零、历史事实一致以及现有质保状态允许。
3. 同一事务创建/激活质保、更新订单终态、关闭履约待办、写数据库审计与命令结果并递增版本。
4. 相同命令标识重试返回原结果；订单已经由其他成功命令最终交付时，新命令标识返回当前幂等结果，不新增质保或审计。

### 9.8 取消订单

1. 店长/管理员基于最新版本发起取消并填写原因。
2. 系统仅允许取消尚未形成不可逆事实的订单。
3. 同一事务将订单置为取消，关闭履约待办，释放尚未出库的库存预留和容量预留，取消尚未开始的施工/跨店任务，写审计与命令结果并递增版本。
4. 已出库、已开工、已有现金事实或已最终交付时拒绝直接取消，返回对应阻塞原因；后续必须走退货、退款或异常处理流程。

### 9.9 回退到待派单

1. 有权限销售/客服/店长基于最新版本发起回退并填写原因。
2. 仅在未开工、未出库、无不可逆现金/施工事实时允许。
3. 同一事务撤销施工分配、释放相应占用、更新订单/跨店任务、写审计与命令结果并递增版本。
4. 已开工订单不得回退到待派单，必须走返工或异常流程。

### 9.10 跨店施工

跨店接受、拒绝、取消、提交来源验收和来源门店验收均纳入履约 command 体系，使用订单履约版本和命令标识；跨店配置与产品映射维护不纳入。所有跨店命令必须同时校验来源门店、执行门店、当前跨店状态和操作者数据范围。

### 9.11 离线同步

1. 小程序现有 `clientOperationId` 直接作为履约命令标识或施工证据命令标识。
2. 服务端持久化每项离线操作结果；重复同步返回原结果。
3. 批次内一项失败不伪装其他项成功；每项返回稳定状态和错误码。
4. 照片等施工证据继续走施工证据 interface，并使用 `clientOperationId` 去重。

施工证据 implementation 必须持久化 `actorId + clientOperationId`、证据类型、工单/订单目标、请求指纹、证据结果 ID 和状态；唯一约束保证同 ID 同输入返回原证据 ID，同 ID 不同输入冲突。对象存储上传使用该命令标识生成稳定对象键，数据库失败后重试不得产生多个可见对象；孤儿临时对象由生命周期策略清理。该记录属于施工证据 module，不并入 `OrderLifecycleCommandRecord`。

## 10. 履约阶段与命令规则

### 10.1 权威履约阶段

| 阶段 | 含义 | 主要可执行命令 | 终态 |
|---|---|---|---:|
| `HISTORICAL_VERIFICATION` | 历史事实矛盾或缺失，不能可靠推进 | 历史核验专用流程 | 否 |
| `PENDING_INVENTORY_CONFIRM` | 尚无可解释的库存预留/出库事实 | 库存匹配 | 否 |
| `PENDING_OUTBOUND` | 已预留但尚未出库 | 出库/释放 | 否 |
| `PENDING_DISPATCH` | 已具备派工条件 | 派工、取消 | 否 |
| `PENDING_MATERIAL_PICKUP` | 已派工且存在尚未领取的锁定物料 | 领料、允许的回退/取消 | 否 |
| `READY_TO_START` | 已派工且无锁定物料，或锁定物料已全部领取，可由已分配施工人员开工 | 开工、允许的回退 | 否 |
| `IN_CONSTRUCTION` | 施工进行中或返工中 | 完工、追加施工证据 | 否 |
| `PENDING_QUALITY` | 施工完工，等待质检 | 质检 | 否 |
| `REWORKING` | 质检要求返工 | 返工完工、追加证据 | 否 |
| `PENDING_BALANCE` | 质检通过但余额未结清 | 收款 | 否 |
| `PENDING_WARRANTY` | 兼容历史数据中质检通过但质保事实尚未形成 | 最终交付自动创建/激活质保 | 否 |
| `PENDING_DELIVERY` | 最终交付条件已满足 | 最终交付 | 否 |
| `COMPLETED` | 最终交付已完成 | 售后/退货等独立流程 | 是 |
| `CANCELLED` | 订单已合法取消 | 无普通履约命令 | 是 |

`READY_TO_START`、`PENDING_WARRANTY` 与 `PENDING_DELIVERY` 均为派生阶段，不要求新增订单数据库枚举。`PENDING_WARRANTY` 只为历史兼容展示，不提供独立生成入口；质检通过且余额为零时直接进入 `PENDING_DELIVERY`，由最终交付事务负责质保形成/激活与订单终态。`READY_TO_START` 修复既有“已派工且已出库时回落为待派工”的错误解释，不改变施工记录状态。

### 10.2 允许的命令来源

| 命令 | 允许的主要来源阶段 | 关键前置事实 | 成功后的阶段方向 |
|---|---|---|---|
| `CREATE_ORDER` | 无 | 客户/车辆/产品/定价/容量有效 | 按库存与跨店事实派生 |
| `CONVERT_QUOTE_TO_ORDER` | 无 | 报价有效且未关联订单 | 按库存与跨店事实派生 |
| `DISPATCH` | `PENDING_DISPATCH` | 执行门店与人员可用 | `PENDING_MATERIAL_PICKUP` |
| `START_CONSTRUCTION` | `READY_TO_START` | 操作者为已派工人员；无锁定物料或锁定物料已全部领取 | `IN_CONSTRUCTION` |
| `COMPLETE_CONSTRUCTION` | `IN_CONSTRUCTION` / `REWORKING` | 前后照片与领料满足 | `PENDING_QUALITY` |
| `QUALITY_CHECK` | `PENDING_QUALITY` | 权限与质检输入完整 | `REWORKING` / `PENDING_BALANCE` / `PENDING_DELIVERY` |
| `FINAL_DELIVERY` | `PENDING_WARRANTY`（历史兼容）/ `PENDING_DELIVERY` | 质检通过、余额为零、事实一致 | `COMPLETED` |
| `CANCEL` | 未形成不可逆事实的非终态 | 原因必填 | `CANCELLED` |
| `RETURN_TO_PENDING_DISPATCH` | 已派工但未开工、未出库、无不可逆事实 | 原因必填 | `PENDING_DISPATCH` |
| `RESOLVE_LIFECYCLE_VERIFICATION` | 任意阶段且存在 `OPEN` 核验单 | 全部相关一致性校验通过，解决说明与至少一条纠正事实/审计引用完整 | 当前业务阶段不变，核验单关闭且履约版本递增 |
| `ACCEPT_CROSS_STORE_TASK` | `PENDING_ACCEPTANCE` | 执行门店 `construction:write`、版本一致 | `READY_TO_DISPATCH` |
| `REJECT_CROSS_STORE_TASK` | `PENDING_ACCEPTANCE` | 执行门店 `construction:write`、原因必填、版本一致 | `REJECTED` |
| `CANCEL_CROSS_STORE_TASK` | `PENDING_ACCEPTANCE` / `READY_TO_DISPATCH` / `DISPATCHED` | 来源门店 `orders.lifecycle:cross_store_source_manage`、未开工、原因必填、版本一致 | `CANCELLED` |
| `SUBMIT_CROSS_STORE_ACCEPTANCE` | `DISPATCHED` / `IN_CONSTRUCTION` | 执行门店 `construction:write`、完工证据满足、版本一致 | `PENDING_SOURCE_ACCEPTANCE` |
| `ACCEPT_CROSS_STORE_BY_SOURCE` | `PENDING_SOURCE_ACCEPTANCE` | 来源门店 `orders.lifecycle:cross_store_source_manage`、版本一致 | `COMPLETED` |

跨店配置、产品映射和只读查询不属于履约命令。跨店任务的 `version` 与订单 `lifecycleVersion` 在同一命令事务内各自条件递增；任何一个条件更新失败均整体冲突回滚。现有未使用的 `ACCEPTED` 枚举不作为可达业务状态，不得新增写入路径。

## 11. 权威履约结果

返回结果至少包含：

| 字段 | 类型 | 规则 |
|---|---|---|
| `orderId` | String | 订单标识 |
| `lifecycleVersion` | Int | 与本次快照一致的履约版本 |
| `currentStage` | Enum | 第 10.1 节阶段之一 |
| `capabilities` | Object | 当前操作者对每个动作的权限与业务可用性判定集合 |
| `blockingReasons` | Array | 稳定阻塞码及可展示参数 |
| `actionImpactSummaries` | Object | 按当前操作者可执行的高风险动作返回结构化影响摘要；至少覆盖终态/质保、释放/关闭事实、撤销人员/占用，不含无权查看的敏感事实 |
| `paymentStatus` | Enum | `UNPAID` / `PARTIAL` / `PAID` |
| `inventoryStatus` | Enum | `NONE` / `LOCKED` / `OUTBOUND` |
| `qualityStatus` | Enum | `NOT_CHECKED` / `PASSED` / `FAILED` |
| `warrantyStatus` | Enum | 现有质保状态或 `NONE` |
| `crossStoreStatus` | Enum? | 跨店订单返回；普通订单为空 |
| `generatedAt` | DateTime | 权威结果生成时间 |

`capabilities` 必须基于操作者权限和业务事实共同产生；页面按钮 disabled/hidden 只能以该结果为依据。阻塞原因不得只返回自由文本。

### 11.1 页面能力字段

`capabilities` 至少按页面实际操作提供以下动作判定；履约写动作对应 public command，收款、证据等事实拥有者动作对应其既有受控入口，不允许页面再以原始状态拼装。为避免 `false` 无法区分无权限和业务阻塞，每个字段使用统一结构 `{ visible, enabled, blockingReasonCodes }`：`visible=false` 表示无权或动作不适用，应隐藏；`visible=true, enabled=false` 表示用户有操作入口但业务条件未满足，应禁用并展示所列阻塞原因；`visible=true, enabled=true` 才允许提交。

| 字段 | 对应操作 |
|---|---|
| `dispatch` | 派工 |
| `startConstruction` | 正式开始施工 |
| `completeConstruction` | 提交施工完工 |
| `qualityCheck` | 质检/符合条件的复检 |
| `collectBalance` | 记录后续收款入口 |
| `finalDelivery` | 最终交付 |
| `cancel` | 取消订单 |
| `returnToPendingDispatch` | 回退待派单 |
| `acceptCrossStore` / `rejectCrossStore` | 执行门店接单/拒绝 |
| `cancelCrossStore` | 来源门店取消协作 |
| `submitCrossStoreAcceptance` | 执行门店提交来源验收 |
| `acceptCrossStoreBySource` | 来源门店确认验收 |
| `viewVerification` | 查看履约核验单及责任模块入口 |
| `resolveVerification` | 关闭履约核验单 |

`blockingReasons` 的每项至少包含 `code`、可展示参数 `params` 和可选的 `actionTarget`。调用端通过 `code` 映射本地文案；`actionTarget` 只允许服务端定义的站内业务入口标识，不返回任意 URL。页面只展示当前动作 `blockingReasonCodes` 引用且用户有权看到的原因，不能把订单全部阻塞原因无差别显示在每个按钮旁。

### 11.2 页面与交互规范

### UI-01 稳定命令 ID 生命周期

1. 页面不展示命令 ID 输入框。
2. 普通下单与报价转单：创建草稿实例时即生成并持久化 `{ draftOrQuoteId, draftRevision, commandId, requestFingerprint, submissionState }`。第一次实际发送前，用户编辑只更新同一草稿意图的 revision 与 fingerprint，不必反复生成 ID；第一次发送时原子锁定本次 revision、ID 和 fingerprint。按钮重复点击、网络超时、401 刷新 token 后重试和页面刷新恢复相同已锁定草稿时复用同一 ID。各自新建、尚未共享草稿 ID 的页面视为不同业务意图。
3. 非创建履约命令：用户打开操作确认框或第一次点击无表单操作时生成 ID，并保存对应请求指纹；请求失败且用户未修改输入时重试复用。用户修改原因、人员、时间、质检结果等业务输入后，旧 ID 失效并生成新 ID。页面不得在请求 pending 期间允许修改本次命令业务输入。
4. 请求成功、`REPLAYED` 或 `ALREADY_SATISFIED` 后清除本地待提交 ID。稳定 `REJECTED` 后保留该 ID、指纹和拒绝结果，避免单纯重复点击产生新意图；只有用户修改业务输入，或刷新到新权威版本并明确再次确认后，才清除旧 ID并生成新 ID。
5. 已明确事务回滚的 `INTERNAL_FAILURE` 保留 ID并允许原输入重试；网络失败或提交结果未知时进入“结果待确认”，创建/转单表单转为只读，只允许用原 ID重试确认结果。原结果确认成功、稳定拒绝或明确回滚前，不得通过修改输入自动生成新 ID；用户选择放弃未知请求时，页面必须先以原 ID查询/重放确认，不能仅清除本地记录后直接新建。
6. Web 使用 `Idempotency-Key` header，履约版本按 API contract 放入 command context；小程序继续以 `clientOperationId` 作为命令 ID。`X-Request-Id` 只用于链路追踪，不得替代命令 ID。
7. 本地命令状态必须按 `actorId + storeId + businessObjectOrDraftId + commandType` 隔离；登出、切换账号或切换门店后不得复用前一身份的命令 ID。用户回到原账号/门店时，相同草稿可继续恢复未确认提交。
8. 已收到稳定 `REJECTED` 的同一业务输入再次提交时，不复用已完成的拒绝记录；页面只有在用户根据阻塞原因改变业务输入或权威版本后才允许创建新业务意图。单纯重复点击仍展示原拒绝结果。
9. 同一草稿多标签页必须使用共享修订记录和原子 submission lease。某标签页锁定提交后，其他标签页立即标记为“草稿已在其他页面提交/已变化”，禁止用旧 revision 提交或自动生成新 ID；用户须先确认原提交结果，再选择载入最新版或显式另存为新草稿。lease 只能在明确未发送或事务明确回滚后释放，不能因页面关闭或超时自行释放。

### UI-02 权威数据刷新与提交保护

1. 页面加载时以同一响应中的权威结果渲染阶段、进度、按钮和阻塞原因。
2. 履约命令提交期间禁用同一命令按钮，防止本页面重复触发；其他会改变同一订单履约事实的按钮同时禁用。
3. `APPLIED`、`REPLAYED`、`ALREADY_SATISFIED` 后先用返回的权威结果更新当前页面，再失效相关订单、施工、跨店和列表查询；不得等查询刷新后才向用户确认结果。
4. 收款、库存、质保等事实操作成功后失效对应订单的权威结果查询，使按钮和进度及时更新。
5. 页面处于编辑/确认状态时收到新版本，不静默覆盖用户尚未提交的表单；提示数据已更新，保留草稿，并要求用户查看差异后确认是否按最新版本重新提交。

### UI-03 统一命令结果反馈

| 结果/错误 | 页面处理 | 用户反馈 |
|---|---|---|
| `APPLIED` | 关闭确认框，更新权威结果 | 使用具体动作成功文案，例如“订单已取消” |
| `REPLAYED` | 不重复触发跳转/动画，更新为原结果 | “已确认上次操作成功” |
| `ALREADY_SATISFIED` | 关闭确认框并刷新 | “当前已完成，无需重复操作” |
| `LIFECYCLE_VERSION_CONFLICT` | 不自动重试；保留表单草稿；展示最新阶段、版本变化和“查看最新状态” | “订单已被其他人更新，请确认最新状态” |
| `COMMAND_PRECONDITION_FAILED` | 保留表单；展示稳定阻塞原因和允许的处理入口 | 使用阻塞码对应文案，不只显示“操作失败” |
| `HISTORICAL_VERIFICATION_REQUIRED` | 关闭普通命令入口，显示整页/卡片级警示 | “历史履约事实待核验”，有权限者可进入核验页 |
| `COMMAND_ID_CONFLICT` | 保留输入，不自动生成新 ID重试 | “本次操作内容已变化，请确认后重新提交” |
| `FORBIDDEN` | 不刷新或显示受保护的最新结果 | “无此操作权限” |
| `INTERNAL_FAILURE` / 网络失败 | 保留命令 ID和表单，提供重试 | “提交结果尚未确认，可安全重试”并展示 request ID（若有） |

### UI-04 创建订单与报价转单

1. 创建订单表单字段、草稿恢复和成功后跳转订单详情保持现状；不增加技术字段。
2. 正式下单返回 `QUOTE_APPROVAL_REQUIRED` 时，沿用当前自动分流：页面提示“当前成交价需要审批，正在创建报价单”，随后将当前表单适配为报价提交；不得解析中文 message，也不额外增加一次确认点击。
3. 自动转报价前保留当前草稿；报价创建成功后再清除或标记草稿已转报价。报价创建失败时用户可回到原输入继续处理。
4. 报价详情点击“转正式订单”时按钮进入 loading；`APPLIED`、`REPLAYED` 或 `ALREADY_SATISFIED` 均跳转关联订单。网络失败时保留同一 ID并显示“重试转单”。
5. 报价创建（包括创建页自动分流）也必须使用稳定 `Idempotency-Key`。SalesQuote 增加调用者命令标识/幂等字段并以 `storeId + actorId + idempotencyKey` 唯一；同 ID同指纹返回原报价，同 ID不同指纹冲突，系统失败可同 ID重试。报价 ID生成后，本地草稿绑定该 quoteId，不再重复调用创建报价。

### UI-05 订单列表与详情

1. 订单列表的履约标签、进度和可操作快捷入口使用批量权威结果；原始 `OrderStatus` 只可作为非履约业务字段展示，不得决定履约进度。
2. 派生阶段至少提供中文标签：待库存确认、待出库、待派工、待领料、可开工、施工中、待质检、返工中、待尾款、待最终交付、已完成、已取消、历史待核验；历史兼容记录只显示“待最终交付（历史质保待核对）”，不提供独立质保生成入口。
3. 订单详情操作区按能力展示“最终交付”“取消订单”“回退待派单”；原因类操作使用确认框且原因必填。最终交付确认框展示质检、余额、质保和核验状态摘要。
4. `visible=true, enabled=false` 时按钮采用 disabled 状态并在相邻位置展示该动作的阻塞原因；桌面端可用 tooltip 辅助，但移动端和键盘操作不能依赖 hover 才能获知原因。`visible=false` 时隐藏按钮。调用端不得自行猜测是权限不足还是业务条件未满足。
5. 合法取消成功后明确说明已同步释放的预留/容量和已关闭的任务/待办；取消被不可逆事实阻断时，页面展示对应退货、退款或异常流程入口，不自动代用户发起其他流程。
6. 回退成功后提示人员分配与占用已撤销；若与开工并发冲突，保留原因草稿并展示最新施工状态。
7. 历史待核验订单在标题区显示持续警示，普通履约按钮全部隐藏/禁用；核验入口按 `viewVerification` 展示，关闭按钮按 `resolveVerification` 展示。核验页展示问题码、相关事实引用、责任模块和处理状态，不提供直接改写事实的万能编辑框。
8. 订单详情沿用现有 `/orders/:id/cancel`、`/orders/:id/return-to-pending`、`/orders/:id/final-delivery` transport 路径，由 adapter 增加 command context；页面返回后仍停留订单详情并刷新，不新增独立成功页。
9. 最终交付确认框必须明确“提交后订单进入终态并形成/激活质保”；取消确认框必须展示将释放/关闭的预览摘要；回退确认框必须展示将撤销的人员和占用摘要。摘要来自当前 `AuthoritativeLifecycleResult.actionImpactSummaries`，不新增独立 prepare 写入 seam，也不由页面猜测。若提交前版本变化，确认框失效并要求重新打开，不得沿用旧摘要。

### UI-06 派工与施工任务

1. 派工台按 `dispatch.visible/enabled` 渲染提交派工；人员、核对项和备注草稿按订单保存。
2. 派工版本冲突时保留已选人员与草稿，刷新最新阶段；如果订单仍可派工，用户人工确认后以新 ID和新版本提交；如果已被派工/取消，则关闭提交入口。
3. “验车/上传施工前照片”是施工证据操作，不改变订单或施工状态；派工后允许已分配施工人员执行，不要求先领料。
4. 页面将现有“开始验车”按钮拆分或改名：验车入口只引导拍摄 BEFORE 证据；正式履约命令按钮命名为“开始施工”。不得用“开始验车”调用 `START_CONSTRUCTION`。
5. 有锁定物料时，全部领取后 `startConstruction.enabled=true`；无锁定物料时可直接开始施工。按钮不可用时显示尚待领取的批次数量。
6. 提交完工按钮由 `completeConstruction` 控制，同时展示缺少的 BEFORE/AFTER 证据、未领取物料等阻塞原因。不得仅由页面本地计数决定可用性；本地信息只用于更即时的辅助提示。
7. 完工返回成功后立即显示“已完工/待质检”；提成快照和成本初始化失败时命令整体失败，页面保留同一 ID并允许安全重试，不显示已完工。
8. 开工前只允许上传 `BEFORE` 证据；`DURING` 和 `AFTER` 证据入口在正式开工后开放。证据 `takenAt` 可早于同步时间但必须由证据规则校验；页面不能通过修改 stage 绕过阶段限制，证据 API 也必须按服务端权威阶段执行同一校验。

### UI-07 质检与复检

1. `qualityCheck.visible=true` 时展示质检入口，只有 `enabled=true` 时可提交；不通过必须填写返工原因和责任类型。
2. 提交期间禁用质检按钮；相同 ID重放只展示原结果，不新增一条“本次质检成功”时间线动画。
3. 上次不通过后，在返工重新完工前不展示复检提交按钮；展示“等待返工重新完工”。重新完工后，用户打开复检表单时生成新命令 ID。
4. 质检通过后，页面按返回权威结果进入待尾款或待最终交付，不根据余额自行跳转。
5. 质检继续使用 `/construction/orders/:orderId` 现有页面。选择“需要返工”时动态显示且必填：返工原因（`note`，最多 500 字）和责任类型（`responsibilityType`，最多 50 字）。责任类型选项复用已发布的 `AFTER_SALE_RESPONSIBILITY` 字典，页面不硬编码另一套枚举；选择“通过”时责任类型不展示、不提交。
6. 页面工作区由 `qualityCheck` 和权威阶段决定；不得只根据 `record.status === COMPLETED` 打开质检。加载权威结果期间不显示可提交表单；记录不存在显示“施工记录待生成”；查询失败显示重试；无权限显示 403 空状态，不回退为只读敏感详情。

### UI-08 跨店协作

1. 跨店页的来源/执行门店 tab 可以保留，但每一行操作按钮以返回 capabilities 为准，不再仅以 tab 和 task.status 判断。
2. 接受、来源验收等无输入操作也必须 loading 并防重复点击；拒绝、取消、提交验收保留原因/说明表单。
3. 版本冲突时关闭成功提示，保留未提交的原因/说明，刷新该任务并显示“对方门店已更新任务”。
4. 无来源管理权限的执行门店用户不展示取消协作、来源验收或核验关闭入口。

### UI-09 小程序与 Web 离线队列

1. 每个队列项展示：业务类型、订单/工单、创建时间、当前结果、尝试次数和最后错误；不得仅以“同步失败”概括稳定业务错误。
2. 结果状态至少区分 `PENDING`、`SYNCING`、`APPLIED`、`REPLAYED`、`CONFLICT`、`REJECTED`、`RETRYABLE_FAILURE`。
3. `APPLIED`/`REPLAYED` 从待处理队列移除并进入本次同步结果摘要；`CONFLICT`/`REJECTED` 保留，等待用户查看详情、放弃或基于最新任务创建新意图；`RETRYABLE_FAILURE` 可用同 ID重试。“放弃”只删除本地待处理记录，必须二次确认并明确不会撤销服务端事实。
4. “全部同步”逐项处理，单项失败不阻断其他项；结果摘要分别显示成功、已重放、需处理和可重试数量。
5. 冲突项提供“查看最新任务”；只有用户查看最新版本并再次确认相同业务动作后，才创建新 ID。页面不得自动替换 expectedVersion 后重试。
6. 清理缓存前展示待处理项数量并二次确认；清理只删除本地队列，不撤销已在服务端成功的事实。
7. 本次同步结果摘要至少保留到用户关闭页面或主动确认清除；成功/重放项虽从待处理队列移除，仍能在摘要查看类型、订单/工单和结果。服务端命令/证据记录承担长期追溯，本地不永久保存敏感详情。

### UI-10 页面入口与通用状态

| 页面 | 现有/新增入口 | 主要角色 | 需覆盖的状态 |
|---|---|---|---|
| 订单创建 `/orders/create` | 现有 | 销售、客服、店长 | 草稿恢复、提交中、需报价审批、网络未知、成功跳转 |
| 报价详情 `/orders/quotes/:id` | 现有 | 销售、店长 | 已批准可转、转单中、重放/已转、冲突/失效 |
| 订单列表 `/orders` | 现有 | 订单查看角色 | 权威阶段加载、部分批量结果失败、历史核验标签 |
| 订单详情 `/orders/:id` | 现有 | 订单查看/操作角色 | loading、404、403、普通、操作冲突、历史待核验、终态 |
| 派工台 `/construction/assignments` | 现有 | 排班员、店长 | 可派工、业务阻塞、草稿、版本冲突、已被处理 |
| 施工任务 `/construction/tasks/:orderId` | 现有 | 已分配施工人员 | 验车证据、待领料、可开工、施工中、完工失败、待质检 |
| 施工质检 `/construction/orders/:orderId` | 现有 | 排班员、店长等有权角色 | 照片期、待质检、返工等待、可复检、已通过、无权/缺记录 |

| 离线队列 | Web 与小程序现有 | 施工人员 | 空、同步中、成功摘要、重放、冲突、拒绝、可重试、清理确认 |

通用规则：

1. 页面首次加载期间以 skeleton/loading 占位，不能短暂显示基于旧原始状态推断的按钮。
2. 订单列表批量权威结果部分失败时，失败行显示“履约状态加载失败”和单行重试，不以 `OrderStatus` 回退生成进度；其他成功行正常展示。
3. 404 显示对象不存在/已失效并提供返回列表；403 显示无权访问，不展示先前缓存的订单敏感信息。
4. 权威结果响应与当前路由对象不一致时丢弃响应并重新查询，防止快速切换订单时串行显示。
5. 浏览器返回、页面刷新和 query cache 恢复时，所有写按钮仍以最新权威版本重新校验；本地草稿可以恢复，但不能让缓存能力直接发起命令。

### 11.3 用户页面操作影响总览

| 页面/场景 | 正常路径变化 | 新增用户操作 | 异常/并发时变化 | 已填写内容处理 |
|---|---|---:|---|---|
| 创建订单 | 字段、提交入口和成功跳转不变；需审批时仍自动创建报价 | 0 | 网络结果未知时进入只读确认，不允许直接再建一单 | 草稿与原命令 ID 保留 |
| 报价详情转单 | “转正式订单”入口不变，增加 loading 与安全重试 | 0 | 已转单/重放直接进入关联订单；冲突时先看最新状态 | 报价输入不丢失 |
| 订单列表 | 状态标签与进度改为权威履约阶段 | 0 | 单行加载失败可单独重试，不拖垮整页 | 不涉及表单 |

| 派工台 | 人员选择和提交方式不变 | 0 | 他人先处理时不自动覆盖，需查看最新状态后人工确认 | 人员、核对项、备注保留 |
| 施工任务 | 验车证据与“开始施工”分开；未领完物料不能正式开工 | 正式开工仍为 1 次明确点击 | 完工失败可用原命令安全重试 | 照片/本地队列与命令 ID 保留 |
| 施工质检 | 通过流程不增加字段；选择返工时新增责任类型必填 | 仅返工场景增加 1 个字段 | 返工未重新完工前不允许复检 | 原因与责任类型在冲突时保留 |

| 离线队列 | “全部同步”入口不变，结果拆分为成功、重放、冲突、拒绝、可重试 | 正常同步 0；清理/放弃增加 1 次确认 | 冲突不自动覆盖版本；可重试项复用原 ID | 失败项保留，成功项进入本次摘要 |

总体影响：日常成功路径不要求用户理解或填写技术字段；新增操作主要集中在高风险确认、并发冲突和历史异常处置。页面不会因本需求新增一次普通下单确认，也不会要求施工人员在正常同步中逐项确认。

## 12. 稳定错误与反馈

| 错误码 | HTTP 映射 | 触发条件 | 必返内容 | 调用端处理 |
|---|---:|---|---|---|
| `FORBIDDEN` | 403 | 无操作权限或无数据范围 | 错误码与既有中文文案 | 不展示最新权威结果 |
| `ORDER_NOT_FOUND` | 404 | 有权范围内订单不存在 | 错误码 | 展示不存在/已失效 |
| `COMMAND_ID_CONFLICT` | 409 | 命令标识绑定的操作者、类型或对象不一致 | 错误码 | 生成新业务命令前要求人工确认，不自动重试 |
| `COMMAND_ID_REQUIRED` | 400 | 普通下单或报价转单未提供稳定命令标识 | 错误码与弃用/升级说明 | 升级调用端；不得自动重试创建 |
| `QUOTE_APPROVAL_REQUIRED` | 409 | 普通下单输入经权威定价决策判定必须先走报价审批 | 定价计算 ID、稳定原因码、可转报价的输入引用/摘要 | Web 按既有自动流程提示后提交报价；不得解析 message |
| `LIFECYCLE_VERSION_CONFLICT` | 409 | `expectedVersion` 已过期或来源状态变化 | 最新版本、最新权威履约结果 | 刷新页面/离线队列后由用户确认是否重试 |
| `HISTORICAL_VERIFICATION_REQUIRED` | 409 | 历史事实矛盾或缺失 | 阻塞原因、历史核验入口信息 | 进入历史核验流程 |
| `COMMAND_PRECONDITION_FAILED` | 400 | 前置事实不满足 | 稳定阻塞原因 | 展示业务原因，不自动改走其他流程 |
| `INTERNAL_FAILURE` | 500 | 未分类系统错误且事务已回滚 | 请求追踪标识 | 可使用同一命令标识安全重试 |

Web 与小程序不得通过 `message.includes(...)` 或其他中文文案解析选择业务流程。

### 12.1 页面阻塞码与站内处理入口

下列高频阻塞必须提供稳定 `blockingReasons.code` 与允许的 `actionTarget`；具体文案可本地化，但语义不得只存在于中文 message：

| 阻塞码 | 含义 | 允许的站内处理入口 |
|---|---|---|
| `INVENTORY_NOT_READY` | 库存尚未匹配或出库 | `INVENTORY_MATCHING` / `INVENTORY_OUTBOUND` |
| `MATERIAL_PICKUP_REQUIRED` | 存在未领取锁定物料 | `CONSTRUCTION_MATERIALS` |
| `BEFORE_EVIDENCE_REQUIRED` / `AFTER_EVIDENCE_REQUIRED` | 缺少施工前/后证据 | `CONSTRUCTION_EVIDENCE` |
| `EVIDENCE_STAGE_NOT_ALLOWED` | 当前履约阶段不允许该类施工证据；开工前仅允许 `BEFORE` | `CONSTRUCTION_TASK` |
| `QUALITY_NOT_PASSED` | 尚未质检通过 | `QUALITY_CHECK`（仅有权限且满足阶段时） |
| `BALANCE_UNPAID` | 尾款未结清 | `ORDER_PAYMENT`（仅有收款入口权限时） |
| `WARRANTY_NOT_READY` | 质保事实尚不允许最终交付 | `WARRANTY` |
| `IRREVERSIBLE_CASH_FACT` | 已有不可逆现金事实，不能直接取消/回退 | `REFUND_OR_EXCEPTION` |
| `INVENTORY_ALREADY_OUTBOUND` | 已出库，不能直接取消/回退 | `SALES_RETURN` |
| `CONSTRUCTION_ALREADY_STARTED` | 已开工，不能直接取消/回退 | `AFTER_SALES_OR_EXCEPTION` |
| `HISTORICAL_FACTS_INCONSISTENT` | 历史事实矛盾 | `LIFECYCLE_VERIFICATION` |

transport adapter 负责将 `actionTarget` 映射到当前 Web/小程序实际路由；服务端不接收由页面传回的任意跳转地址。

## 13. 消息、待办、审计和进程日志

| 类型 | 是否核心事实 | 提交位置 | 幂等/失败规则 |
|---|---:|---|---|
| 履约待办 | 是 | 与命令同事务 | 使用业务去重键；失败回滚命令 |
| 数据库审计事实 | 是 | 与命令同事务 | 同命令只写一次；失败回滚命令 |
| 通知投递意图 | 是 | 与命令同事务 | 使用去重键；提交后派发 |
| 站内通知/外部通知投递 | 否 | 事务提交后 | 失败重试，不回滚核心事实，不重复有效送达 |
| 进程日志 | 否 | 事务提交后 best-effort | 失败不回滚；不得在提交前记录“已成功” |

通知接收人、文案和跳转沿用现有业务规则。本需求只改变事务与去重语义，不新增通知渠道或频率。

## 14. 历史数据与发布迁移

### 14.1 历史数据迁移

1. 所有已有订单初始化 `lifecycleVersion = 1`。
2. 不伪造历史命令记录；命令历史从新版本启用后开始。
3. 迁移前扫描以下矛盾：
   - 已完成/已质保订单缺少通过的质检事实；
   - 订单状态与施工记录状态矛盾；
   - 已最终交付但质保未激活；
   - 订单收款明细与现金事实/金额摘要不一致；
   - 已施工完工但施工成本结算或提成快照缺失；
   - 报价已转换但未关联订单，或存在疑似孤儿订单。
4. 矛盾订单进入历史核验清单；迁移脚本不得猜测覆盖原事实。
5. 历史初始定金缺少现金事实不在迁移中自动补造；进入财务数据核验，确认后以明确修复记录处理。
6. 对每个矛盾订单创建一个 `OPEN` 履约核验单并保存稳定问题码；无核验单的迁移异常不得只输出临时日志后放行。
7. 恢复写入门禁：所有非终态矛盾订单必须已有核验单、明确责任角色和处理入口；所有无核验单异常必须为 0。终态历史订单可带 `OPEN` 核验单上线，但不得执行普通履约命令。

### 14.2 发布方式

- 使用短维护窗口一次切换，维护期间停止订单履约写入。
- 顺序：数据库备份与预检 → 部署 schema/迁移 → 部署唯一 seam 应用 → 部署 Web/小程序适配 → 运行 smoke/并发门禁 → 恢复写入。
- 不允许旧应用节点在迁移后继续写入。
- 新数据库字段与命令记录不回滚删除；应用失败采用停止写入并向前修复。
- 兼容 adapter 仅存在一个发布版本：旧的非创建订单命令缺少命令标识/版本时，adapter 在收到请求后读取当前版本并生成请求级命令标识，同时返回弃用响应头；核心 implementation 从第一天起不接受缺失值。该兼容只能防止并发状态覆盖，不能把跨请求重试识别为同一业务意图。
- `CREATE_ORDER` 与 `CONVERT_QUOTE_TO_ORDER` 不适用自动生成命令标识的兼容，因为网络重试会造成重复订单。所有已知 Web、报价服务及集成调用方必须在维护窗口恢复写入前发送稳定 `Idempotency-Key`；缺失时返回 `COMMAND_ID_REQUIRED`，不得下沉到核心 implementation。
- 下一个发布版本移除兼容 adapter 并强制调用端提交真实值。

### 14.3 实施顺序

1. 新增履约版本、命令记录、事实来源与唯一约束。
2. 发布 `orders.lifecycle` 细粒度权限 actions、默认角色绑定和缓存失效；权限 contract 通过后方可接入命令。
3. 建立 transaction-scoped 内部 implementation。
4. 迁移普通下单、首次定金和报价转单。
5. 迁移施工与跨店命令，收口完工同步义务。
6. 接入库存、现金、质保和履约待办的版本失效。
7. 迁移 Web、施工 Web、小程序和离线队列。
8. 删除 optional、fallback、运行期注册和内部 implementation 导出。
9. 删除调用端状态/能力推断与被替代的浅层测试。

## 15. 异常与边界

| 场景 | 系统处理 | 事实结果 | 用户反馈 |
|---|---|---|---|
| 同命令标识网络重试 | 返回原结果 | 不重复写入 | 显示原成功/拒绝结果 |
| 命令标识被其他用户使用 | 拒绝 | 无变化 | `COMMAND_ID_CONFLICT` |
| 两个不同命令竞争同一版本 | 仅一个条件更新成功 | 失败方无写入 | 返回最新权威结果 |
| 取消与最终交付竞争 | 按版本和来源状态只允许一个成功 | 不产生取消且已交付等矛盾 | 失败方刷新确认 |
| 回退与开工竞争 | 仅一个成功 | 不覆盖已开工事实 | 失败方刷新确认 |
| 完工时成本初始化失败 | 整体回滚 | 仍为施工中，可同 ID 重试 | 系统失败且可安全重试 |
| 通知派发失败 | 记录失败并重试 | 核心事实保持成功 | 不提示业务失败 |
| 报价创建订单后关联步骤故障 | 同事务回滚 | 无孤儿订单 | 可同 ID 重试 |
| 质检同 ID 重试 | 返回原结果 | 不重复历史/返工次数 | 显示原结果 |
| 新 ID 复检但未重新完工 | 拒绝 | 无变化 | 前置条件失败 |
| 历史事实矛盾 | 阻断普通命令 | 无自动修复 | 引导历史核验 |
| 旧的非创建命令缺少版本/命令 ID | 一版本内兼容 adapter 补齐 | 仍走核心唯一 seam | 返回弃用提示 |
| 下单/报价转单缺少命令 ID | 拒绝，不自动生成 | 无变化 | `COMMAND_ID_REQUIRED` |
| 事务提交后进程日志失败 | 记录可观测异常 | 业务成功 | 不向用户报告业务失败 |
| 进程在命令事务中崩溃 | 数据库回滚事务和命令占位；同 ID 重试重新执行 | 不遗留半成品命令状态或业务事实 | 返回连接失败；重试安全 |

### 16.2 结构化事件

每个命令至少记录：命令类型、调用端、是否重放、前后版本、结果码、耗时、是否跨店、事务是否回滚、通知意图数量；页面另记录“结果待确认、原 ID 重试恢复、查看最新版本、人工创建新意图”的匿名操作事件。不得记录敏感客户联系方式、表单原文或照片内容。

Web 页面事件通过受登录保护的 `POST /orders/lifecycle/client-events` 上报，服务端只接受白名单 `event`、`surface`、`commandType` 和固定 `source=WEB`，写入指标与结构化日志，不写业务审计表；事件上报失败不得阻塞原业务命令。当前页面映射为：创建订单页记录 `RESULT_UNKNOWN` 与成功的 `ORIGINAL_COMMAND_RETRY_RECOVERED`，订单列表记录 `CREATE_NEW_INTENT`，离线同步页记录 `VIEW_LATEST_VERSION`。小程序不接入本轮契约。

运行期 `OrderLifecycleReconciliationService` 每 5 分钟只读扫描历史履约一致性检查；发现终态质检/质保缺失、历史矛盾无核验单或版本账本缺口时，在事务内按订单获取 PostgreSQL advisory lock，幂等创建或合并一个 `OPEN` 核验单，并递增固定 invariant 标签指标。对账失败只记录结构化错误与失败计数，不阻断 API 启动；核验单仍必须通过正常责任模块纠正和版本化关闭，不直接改写业务事实。

## 17. 验收标准

### AC-01 普通下单幂等与首次现金事实

Given：销售有本人订单写权限，订单输入有效并包含定金，使用命令标识 A。  
When：相同请求并发或顺序提交两次。  
Then：仅创建一个订单、一组明细、一笔初始订单收款和一笔对应现金事实；两次返回相同订单与版本 1。

Given：同一命令标识 A 被并发提交，但其中一次修改了会影响业务结果的订单输入。  
When：系统比较请求指纹。  
Then：仅首个有效输入可以执行，另一次返回 `COMMAND_ID_CONFLICT`；不得把首个结果冒充为修改后输入的成功结果。

### AC-02 报价转单强原子

Given：报价有效、已批准且未关联订单。  
When：在报价认领、订单创建、报价关联或审计任一点注入失败。  
Then：事务整体回滚，不存在孤儿订单，报价仍可使用同一命令标识重试；成功后报价只能关联一个订单。

### AC-03 命令重放

Given：开工命令 A 已成功。  
When：同一操作者对同一订单再次提交 A。  
Then：返回第一次权威履约结果，不改变开始时间、不新增审计、不递增版本。

Given：订单已经由命令 A 完成最终交付。  
When：同一操作者用新命令标识 B 再次发起最终交付。  
Then：返回 `ALREADY_SATISFIED` 和当前权威履约结果；命令 B 形成可重放结果，但不新增质保、业务审计、通知意图或版本。

### AC-04 命令标识冲突

Given：命令标识 A 已被用户甲用于订单甲的开工。  
When：用户乙或订单乙使用 A。  
Then：返回 `COMMAND_ID_CONFLICT`，不泄露订单甲的结果且不写任何事实。

### AC-05 不同命令竞争

Given：取消和最终交付基于同一履约版本并发提交。  
When：数据库执行两个条件更新。  
Then：仅一个命令成功；另一命令返回 `LIFECYCLE_VERSION_CONFLICT`，订单不出现已取消且质保激活等矛盾事实。

### AC-06 施工完工原子性

Given：施工中订单已满足照片与领料条件。  
When：提交完工且在提成快照或成本结算初始化处失败。  
Then：施工记录、跨店任务、提成快照、成本结算、命令记录、版本和审计全部回滚；同命令标识可安全重试。

### AC-07 质检重试与复检

Given：一次质检不通过已成功。  
When：同命令标识重试。  
Then：不新增质检历史、不重复递增返工次数。  
Given：返工重新完工。  
When：用新命令标识复检。  
Then：追加一条新质检事实并返回新权威结果。

### AC-08 取消的不可逆事实门禁

Given：订单已经出库、开工、形成现金事实或最终交付。  
When：提交取消。  
Then：返回稳定阻塞原因，不释放或覆盖既有事实，并指向退货、退款或异常处理流程。

### AC-09 合法取消的同步收口

Given：订单未出库、未开工且没有现金事实。  
When：店长提交合法取消。  
Then：订单取消，未出库预留和容量预留释放，未开始施工/跨店任务取消，履约待办关闭，审计和版本同步完成。

### AC-10 回退门禁

Given：订单已派工但未开工、未出库且没有不可逆事实。  
When：有权限角色回退。  
Then：撤销施工分配并回到待派单；若并发开工先成功，回退必须冲突而不能覆盖。

### AC-11 事实变化使版本失效

Given：调用端持有版本 N 的权威履约结果。  
When：库存出库或现金事实使履约阶段/能力变化。  
Then：订单版本变为 N+1；基于 N 的后续命令返回版本冲突和最新权威结果。

Given：同一库存或现金事实事务同时改变多个参与履约解释的字段。  
When：该事务提交。  
Then：订单版本只从 N 变为 N+1，并形成唯一版本变更记录；事实写入、版本与记录任一失败都整体回滚。再次使用相同来源键不得重复递增。

### AC-12 权威读取一致性

Given：订单事实正在由并发事务改变。  
When：查询权威履约结果。  
Then：返回来自同一数据库快照的事实组合和对应版本，不混合事务前后状态。

Given：权威结果需要多条 SQL 才能读取完整事实。  
When：第一条与最后一条查询之间有并发事实事务提交。  
Then：本次结果仍全部来自同一 `REPEATABLE READ` 快照，`lifecycleVersion` 与所有事实一致；下一次查询才看见新版本。

### AC-13 历史矛盾阻断

Given：历史订单标记为已完成但缺少通过质检或有效质保。  
When：发起普通履约命令。  
Then：返回 `HISTORICAL_VERIFICATION_REQUIRED`，不自动补造或覆盖事实。

Given：迁移预检识别到历史矛盾。  
When：系统准备恢复履约写入。  
Then：每个矛盾订单都存在一个含稳定问题码的 `OPEN` 核验单，非终态订单已有责任角色和处理入口，未建单异常为 0；否则阻断恢复写入。

### AC-14 Web 与小程序调用端

本轮验收范围为 Web 与施工 Web；小程序调用端按第 4.3 节延期。  
Given：新版本 Web、施工 Web。  
When：提交履约命令。  
Then：发送真实命令标识和期望版本；遇到冲突按错误码刷新；不解析中文错误，不自行推断阶段或能力。小程序适配器后续重新纳入时复用同一契约并单独验收。

### AC-15 权限矩阵

Given：店长、销售、客服、排班员、施工人员、学徒、财务、采购和总部管理员。  
When：逐一执行每类命令。  
Then：结果与第 5 节及已发布权限数据一致；最终交付只允许归属门店授权角色，施工人员只操作本人任务。

Given：执行门店拥有施工写权限、但不拥有归属门店管理权限的跨店角色。  
When：其尝试最终交付或来源门店验收。  
Then：返回 `FORBIDDEN`，且不返回订单最新权威结果；执行门店权限不能提升为归属门店权限。

### AC-16 通知与进程日志失败

Given：核心事务已经成功提交。  
When：外部通知或进程日志失败。  
Then：命令仍返回成功，投递意图可重试且不会重复有效送达；业务事实不回滚。

### AC-17 删除测试

Given：所有调用端完成迁移。  
When：扫描生产代码与 Nest module export。  
Then：不存在 optional `OrderLifecycle`、生产 fallback、`registerConstructionHandler`、`CreateOrderUseCase` 外部导出、施工状态写入导出或调用端状态/能力回退推断；删除 `OrderLifecycle` 会使复杂度重新散回多个真实调用者。

Then：系统重新执行全部一致性校验；仍有问题时保留 OPEN 并列出剩余问题，全部通过时要求/记录纠正事实或审计引用并关闭核验单、刷新订单权威结果。

### AC-30 质检表单字段与权威入口

Given：施工记录状态为已完工，但权威结果的 `qualityCheck.visible=false`。  
When：用户打开施工质检页。  
Then：页面不因本地 record 状态展示可提交质检表单；按无权或动作不适用状态处理。

Given：有权用户选择“需要返工”。  
When：提交质检。  
Then：返工原因和来自 `AFTER_SALE_RESPONSIBILITY` 已发布字典的责任类型均为必填；缺失时前端不提交，服务端仍执行相同校验。选择“通过”时不提交责任类型。

### AC-31 页面加载、无权与批量部分失败

Given：订单详情或施工页正在加载权威结果。  
When：页面首次渲染。  
Then：只显示 loading/skeleton，不短暂显示基于原始状态推断的写按钮；403 时清除敏感缓存并显示无权状态，404 时提供返回列表。

Given：订单列表批量权威结果只有部分订单失败。  
When：列表渲染。  
Then：成功行正常展示权威阶段；失败行显示“履约状态加载失败”和单行重试，不以原始 `OrderStatus` 回退生成进度。

### AC-32 多标签页、账号和门店隔离

Given：同一账号在两个标签页打开同一订单草稿。  
When：两个标签页输入一致并重试同一未确认创建意图。  
Then：共享同一草稿修订与命令 ID；首次发送原子取得 submission lease，另一个标签页不能再次形成新创建意图。

Given：两个标签页对同一草稿形成不同输入。  
When：其中一个标签页先锁定并发送某一 revision。  
Then：另一标签页标记过期并禁止提交，不自动生成新 ID；用户先确认原提交结果，再显式载入最新版或另存为新草稿。

Given：用户登出后换账号或切换门店。  
When：新身份打开相同本地草稿标识。  
Then：不得复用前一 actor/store 的命令 ID或展示其命令结果；本地命令状态按 actor、store、对象和命令类型隔离。

### AC-33 提交结果未知时禁止生成重复意图

Given：创建订单或报价转单请求已发出，但客户端在提交窗口收到网络中断，无法判断服务端是否提交。  
When：页面进入“结果待确认”。  
Then：原表单只读，保留原命令 ID，只提供“确认上次结果/安全重试”；不得允许用户修改输入后直接生成新 ID。原 ID 返回成功、稳定拒绝或明确回滚后，页面才恢复对应后续操作。

### AC-34 高风险操作确认摘要

Given：用户有最终交付、取消或回退待派单权限。  
When：打开对应确认框。  
Then：分别展示终态与质保影响、将释放/关闭的事实摘要、或将撤销的人员/占用摘要；摘要来自当前权威结果。确认期间履约版本变化时，旧确认框失效，必须刷新摘要并重新确认。

### AC-35 证据阶段服务端校验与离线留痕

Given：订单已派工但尚未正式开工。  
When：页面或离线同步上传施工证据。  
Then：仅 `BEFORE` 证据可成功；`DURING`/`AFTER` 即使绕过页面也被服务端以 `EVIDENCE_STAGE_NOT_ALLOWED` 稳定拒绝。正式开工后按证据规则开放后续阶段。

Given：离线批次中的成功/重放项已从待处理队列移除。  
When：用户尚未关闭页面或确认清除摘要。  
Then：仍可在本次同步摘要查看业务类型、订单/工单和结果；放弃冲突/拒绝项时明确只删除本地记录、不撤销服务端事实。

## 18. 测试替换策略

1. 新建只穿过正式 interface 的 contract tests，断言可观察结果，不断言内部调用顺序。
2. 使用真实 transaction 或能验证回滚的数据库测试，不再以 `fn(tx)` 假事务证明原子性。
3. 建立 opt-in PostgreSQL 并发 stage gate，沿用 `MALLBAY_RUN_REAL_DB_TESTS=1`。
4. 保留 transport adapter、页面渲染和施工证据 implementation 的专属测试。
5. 新 interface 覆盖等价行为后，删除：
   - 只验证 `OrderLifecycle` 委托 handler 的测试；
   - 只验证 fallback 存在的测试；
   - `ConstructionFulfillment` 大面积 pass-through contract tests；
   - 只验证旧内部方法调用顺序的测试；
   - 被权威结果替代的页面状态推断测试。

## 19. 风险与依赖

| 风险/依赖 | 影响 | 应对 |
|---|---|---|
| Orders 与 Construction 现有依赖方向 | 简单互相注入会形成循环 | 独立应用级履约 module；内部写入 implementation 不导出整个 ConstructionModule |
| 事务范围扩大 | 锁等待与命令耗时上升 | 条件更新、固定锁顺序、真实并发压测、监控 P95/P99 |
| 历史事实质量 | 普通命令被阻断 | 发布前生成历史核验清单，不静默修复 |
| 小程序离线版本过期 | 同步冲突增加 | 每项返回最新结果，由用户确认新业务意图；同 ID 重放安全 |
| 兼容 adapter 被长期保留 | interface 再次变浅 | 限定一个发布版本并设删除门禁 |
| 现金/库存 module 接入版本失效 | 跨 module 改动范围大 | 按第 14.3 节分阶段迁移，但切换前必须全部接入 |
| 发布不可回滚旧应用 | 维护窗口失败影响写入 | 备份、预演、停止写入、向前修复，不让旧节点重新写 |
