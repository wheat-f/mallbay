# PermissionGovernance 深化 PRD

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 需求名称 | PermissionGovernance 权限治理 seam 深化 |
| 文档版本 | v1.0 |

| 关联模块 | `apps/api/src/permissions`、`AccessContext` |
| 关联 ADR | ADR-0013、ADR-0012 |

## 2. 背景与目标

当前 `PermissionsService` 同时承载运行时访问解析、范围判断、权限策略版本治理、角色治理和角色绑定治理。`AccessContext` 已经是运行时访问 seam，但权限管理 controller 仍直接依赖包含全部能力的实现，导致规则、缓存、审计和测试 surface 分散。

本期目标：

- 建立深的 `PermissionGovernance` interface，集中权限策略、角色和绑定治理。
- 让 `AccessContext` 只负责运行时访问能力与访问范围判断。
- 集中并保持策略发布/回滚、总部管理员保护、审计和缓存失效规则。
- 不改变已有权限数据结构、路由语义和权限业务结果。

## 3. 范围与非目标

### 本期范围

- 权限策略：当前版本、草稿、校验、影响分析、发布、回滚。
- 角色：查询、创建、停用及权限项校验。
- 角色绑定：查询、绑定、即时停用、范围校验。
- 权限目录查询。
- controller/module 依赖迁移到治理 seam。
- seam contract tests 和现有权限回归测试。

### 非目标

- 不开放通过页面新增总部成员。
- 不改变 ADR-0013 的唯一总部管理员规则。
- 不新增权限数据库表或迁移。
- 不引入只有一个实现的泛化 `PermissionAdapter`。
- 不重做 `AccessContext` 的运行时判断算法。

## 4. 角色与权限

| 角色 | 可查看 | 可操作 | 数据范围 |
|---|---|---|---|
| 总部管理员 | 权限目录、角色、绑定、策略版本及影响 | 创建/停用角色、绑定/停用绑定、草稿、校验、发布、回滚 | 总部治理范围 |
| 普通访问主体 | 自身运行时权限结果 | 由业务模块按访问能力执行操作 | 总部、门店或本人责任范围 |

治理操作本身必须通过已发布策略判断操作者是否具备总部全局权限；旧的 `isAuditor` 或岗位字段不得成为授权依据。

## 5. 核心对象与状态

| 对象 | 定义 | 状态 |
|---|---|---|
| 权限策略版本 | 一组角色、访问能力、动作和范围的版本化配置 | DRAFT、VALIDATED、VALIDATION_FAILED、PUBLISHED、ROLLED_BACK |
| 角色 | 一组访问能力授权的可复用身份定义 | ACTIVE、DISABLED |
| 角色绑定 | 用户与角色及总部/门店组织范围的有效关系 | ACTIVE、DISABLED |
| 权限影响快照 | 某策略版本相对当前版本影响的角色、用户、组织和能力集合 | 查询结果，不单独改变状态 |

## 6. 核心流程与规则

### 6.1 策略发布流程

1. 总部管理员创建或更新草稿，并可携带 `expectedVersion`。
2. 系统校验权限定义、角色、动作、范围和重复授权项。
3. 系统生成影响结果，包含受影响角色、用户、组织和被授予/撤销能力。
4. 发布前再次检查版本未变化、策略仍为已校验、保留 `HQ_ADMIN` 全局设置能力、至少存在一个总部管理员绑定，且当前操作者发布后仍有发布能力。
5. 在同一事务中将旧发布版本置为回滚、发布新版本、应用角色授权并写审计记录。
6. 成功后统一失效运行时权限缓存。

### 6.2 角色与绑定规则

- 角色编码和名称不能为空；授权项必须存在于有效权限目录，动作和范围必须受定义支持，且不可重复。
- 门店范围绑定必须有 `storeId`；总部范围绑定不得有 `storeId`。
- 停用最后一个总部管理员绑定必须拒绝。
- 当前阶段总部成员绑定仍按 ADR-0013 限制，不开放页面新增其他总部成员。
- 绑定变化成功后只失效受影响用户的运行时缓存。
- 角色创建、角色停用、绑定创建和绑定停用的业务状态写入与治理审计必须在同一事务中完成；事务失败时权限状态不改变。
- 缓存失效只能发生在事务提交后；提交前或事务失败不得提前清除缓存。

### 6.3 并发与重复

- 带 `expectedVersion` 的草稿保存或发布发现版本变化时拒绝，不覆盖其他管理员结果。
- 已停用角色/绑定再次停用返回当前结果或明确幂等成功，不重复写入业务状态。
- 审计记录失败不得把运行时拒绝变成 500；治理写入则必须保证业务状态与审计事务的一致性。

## 7. Seam 与实现约束

- `PermissionGovernance` 是管理 controller 的唯一外部治理 seam；策略版本、角色/绑定规则和 Prisma 访问属于 implementation 内部。
- `AccessContext` 是运行时访问 seam，只读取治理产生的已发布结果/快照，不执行治理写入。
- 先通过 token/interface 接入现有实现，再物理拆分实现；旧实现仅作为过渡 adapter，不保留运行时 fallback，不做双写。
- “one adapter = hypothetical seam, two = real”：本期不为不存在第二实现的存储、审计或缓存制造抽象。

## 8. 验收标准

- Given 两个管理员基于同一已发布版本编辑策略，When 后提交者发布，Then 因版本冲突拒绝且先提交结果不被覆盖。
- Given 新策略会移除最后一个总部管理员，When 发布，Then 拒绝且当前发布版本不变。
- Given 角色授权项引用不存在的权限、未支持动作/范围或重复项，When 校验，Then 状态为 `VALIDATION_FAILED` 并产生失败审计。
- Given 有效门店绑定，When 停用，Then 绑定变为 `DISABLED`、目标用户缓存失效且产生审计。
- Given `AccessContext` 执行运行时判定，When 权限策略发布后再次查询，Then 使用新版本结果且治理 controller 不参与判定。
- Given 角色或绑定治理写入的审计失败，When 事务提交失败，Then 权限状态保持原值且缓存不被提前失效。
- Given 现有权限路由和数据库，When 迁移完成，Then 路由、数据结构和权限结果保持兼容。
- API typecheck、Nest build、权限模块 contract tests 和全量 API tests 通过。

## 9. 指标与待确认

- 技术指标：权限治理规则可通过 seam contract tests 验证；不新增双写路径。
- 业务指标：权限误配率、权限拒绝申诉量暂无基线，标记为上线后补充。
- 待确认：治理页面是否需要展示影响快照的分页/导出；不阻塞本期 seam 落地。
