# 权限模型改造 PRD

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 需求名称 | 角色权限矩阵与后端鉴权联动改造 |
| 文档版本 | v1.1 |
| 当前状态 | 第二轮评审通过，可进入研发 |
| 创建日期 | 2026-07-31 |
| 关联问题 | 角色权限矩阵与后端真实权限未联动 |

## 2. 需求背景

当前前端“角色与权限”页面保存 settings.permissions 配置矩阵，但后端仍根据 isAuditor、StoreMember.position 和能力域硬编码判断权限，造成页面勾选结果与接口真实权限不一致。

本期将权限矩阵升级为后端真实鉴权来源，支持一用户多角色、总部/门店组织范围、能力/动作/数据范围控制，并保证权限变更可追踪、可回滚。

## 3. 产品目标

- 发布后的权限矩阵真实控制后端接口权限。
- 前端菜单、页面、按钮与后端使用同一套权限目录和有效权限结果。
- 支持一个用户绑定多个角色，最终权限取允许权限并集。
- 角色权限按总部/门店范围生效，不能突破组织安全边界。
- 现有岗位用户平滑迁移，不因模型切换丢失权限。
- 权限发布、角色绑定和回滚均可审计。

## 4. 范围

### 4.1 本期包含

- 后端权限目录。
- 系统角色和自定义角色。
- 用户多角色绑定及组织范围。
- 能力、操作、数据范围三级权限模型。
- 后端统一鉴权服务。
- 前端菜单、工作台、按钮权限接入。
- 现有 StoreMember.position 到角色绑定的迁移。
- 权限矩阵草稿、校验、发布、影响分析和回滚。
- 权限缓存及变更失效机制。
- 权限审计和异常待处理清单。

### 4.2 非目标

- 首期不启用 ORG 数据范围。
- 首期不强制双人复核发布。
- 首期不删除 StoreMember.position 字段。
- 首期不支持复杂的显式拒绝权限。
- 首期不改变业务岗位字段含义。

## 5. 已确认规则

### 5.1 权限生效

- 权限矩阵发布后作为后端真实生效来源。
- 未配置权限默认拒绝。
- 一个用户的多个角色允许权限取并集。
- 系统安全边界优先于角色权限配置。
- 权限矩阵发布生效；角色绑定保存成功后即时生效并审计。

### 5.2 角色

- 角色定义全局统一，绑定按总部或门店范围生效。
- 一个用户允许绑定多个角色。
- 系统角色不可删除。
- 总部管理员可创建和停用自定义角色。
- 已被绑定的自定义角色不能物理删除，只能停用。

### 5.3 数据范围

首期支持：

- OWN：本人数据。
- STORE：角色绑定门店内数据。
- GLOBAL：总部全量数据。

ORG 仅预留，不在本期开放。角色绑定范围不能超过角色所属组织范围；店长默认最多只能获得 STORE。

### 5.4 发布安全

- 不允许移除最后一个具备角色管理和权限发布能力的总部管理员。
- 不允许发布导致当前操作者失去必要权限的配置。
- 发布前展示受影响用户、角色、菜单和接口数量。
- 保留历史版本并支持回滚。
- 发布、回滚、角色变更全部记录审计。
- 采用单人发布，暂不强制双人复核。

## 6. 核心对象

| 对象 | 定义 | 关键字段 |
|---|---|---|
| PermissionDefinition | 后端统一维护的权限目录项 | code、resource、action、supportedScopes、status |
| Role | 全局角色定义 | code、name、type、status、scopeType |
| RolePermission | 角色对权限目录项的授权 | roleId、permissionCode、scope |
| UserRoleBinding | 用户在组织范围内的角色绑定 | userId、roleId、scopeType、scopeId、status、effectiveAt、expiredAt |
| PermissionPolicyVersion | 权限矩阵草稿或发布版本 | version、status、payload、publishedAt |
| PermissionAuditEvent | 权限变更审计事件 | actorId、target、before、after、reason、createdAt |

## 7. 权限编码

权限目录由后端维护，权限编码上线后不可修改，只能停用。前端动态读取权限目录，未登记的权限默认拒绝。

权限编码建议使用：

    资源.动作.范围

示例：

    dictionaries.view.store
    dictionaries.create.store
    dictionaries.edit.store
    finance.approve.global
    orders.view.own

## 8. 业务流程

### 8.1 权限矩阵发布

1. 总部管理员加载后端权限目录和当前已发布版本。
2. 按角色配置能力、动作和数据范围。
3. 系统保存草稿并校验权限编码、范围和安全边界。
4. 系统展示受影响角色、用户、菜单和接口。
5. 管理员确认发布。
6. 系统事务性发布新版本，生成审计记录。
7. 系统清理相关权限缓存。
8. 后续请求按新版本重新计算权限。

### 8.2 角色绑定

1. 管理员在人员详情页查看用户有效角色。
2. 新增、移除或停用角色绑定。
3. 系统校验操作者范围、目标用户归属和重复绑定。
4. 保存成功后立即生效。
5. 系统清理目标用户权限缓存并记录变更前后内容。

### 8.3 后端鉴权

1. JWT 仅提供用户身份，不保存完整权限。
2. 鉴权服务读取用户状态、角色绑定和已发布权限矩阵。
3. 根据能力、动作、角色范围和请求对象范围计算有效权限。
4. 多角色允许权限取并集。
5. 系统安全边界再次校验。
6. 满足权限则进入业务处理，否则返回统一 403。

## 9. 权限矩阵页面

### 9.1 页面结构

- 左侧：权限资源目录树。
- 右侧：当前资源的动作和数据范围配置。
- 顶部：当前版本、草稿状态、影响分析和发布状态。
- 底部：保存草稿、校验、发布、回滚。

### 9.2 交互规则

- 权限目录由服务端接口提供，前端不维护权限清单。
- 未支持的动作或范围不可选择。
- 已停用权限只展示历史配置，不允许新增配置。
- 发布前必须完成服务端校验。
- 发布失败保留草稿，不改变当前生效版本。
- 回滚前展示目标版本和影响范围。

### 9.3 版本状态

| 状态 | 第一轮评审修订中 |
|---|---|---|
| DRAFT | 未发布草稿 | 编辑、校验、删除草稿 |
| VALIDATED | 校验通过待发布 | 发布、继续编辑 |
| PUBLISHED | 当前生效版本 | 查看、创建新草稿、回滚 |
| ROLLED_BACK | 已被后续版本替代 | 查看、审计 |
| VALIDATION_FAILED | 校验失败 | 查看错误、修改、重新校验 |

## 10. 角色绑定页面

人员详情页维护用户、角色、总部/门店范围、生效状态、生效时间、失效时间和变更历史。

规则：

- 一个用户可同时拥有多个有效角色。
- 同一用户、同一角色、同一组织范围不得重复绑定。
- 移除角色绑定即时生效。
- 已过期绑定不参与权限计算。
- 角色停用后，所有关联绑定不再产生有效权限。
- 操作者不能把绑定范围扩大到自身已有范围之外。

## 11. 存量迁移

| 现有岗位 | 初始角色 |
|---|---|
| MANAGER | 店长 |
| SALES | 销售 |
| CUSTOMER_SERVICE | 客服 |
| FINANCE | 财务 |
| PURCHASING | 采购 |
| SCHEDULER | 排班员 |
| CONSTRUCTION | 施工员 |
| APPRENTICE | 学徒 |

迁移规则：

- 保留 StoreMember.position 作为业务岗位字段。
- 依据现有岗位和门店关系生成角色绑定。
- 总部审计员按现有 isAuditor 生成总部角色绑定。
- 迁移脚本必须幂等，重复执行不产生重复绑定。
- 迁移异常记录明细并进入待处理列表。
- 切换完成后，权限以角色绑定为准。

## 12. 缓存与一致性

- 普通权限结果允许短时缓存，建议技术评估 30～60 秒 TTL。
- 权限矩阵发布时，清理受影响角色和组织范围缓存。
- 角色绑定变更时，清理目标用户缓存。
- 用户停用或门店关系失效时，立即清理用户缓存。
- 审批、删除、发布、付款等高风险操作强制实时校验。
- 缓存不可作为权限唯一来源；高风险场景缓存读取失败时默认拒绝。

## 13. 接口需求

- GET /permissions/catalog：读取权限目录。
- GET /auth/me/permissions：返回当前用户有效角色、组织范围、权限项和权限版本。
- GET/POST/PATCH /roles：角色查询、新增和编辑。
- GET/POST/PATCH /users/:id/role-bindings：角色绑定查询和变更。
- GET/POST/PATCH /permission-policy-versions：权限矩阵版本管理。
- POST /permission-policy-versions/:id/validate：校验草稿。
- GET /permission-policy-versions/:id/impact：影响分析。
- POST /permission-policy-versions/:id/publish：发布。
- POST /permission-policy-versions/:id/rollback：回滚。

接口必须返回统一错误码、requestId 和权限版本信息。

## 14. 异常与边界

| 场景 | 系统处理 | 用户反馈 |
|---|---|---|
| 未配置权限 | 拒绝访问 | 403，无权限提示 |
| 角色已停用 | 不参与计算 | 页面不可选，历史可查看 |
| 绑定范围越权 | 拒绝保存 | 提示无权绑定该范围 |
| 重复角色绑定 | 拒绝保存 | 提示已存在绑定 |
| 权限矩阵校验失败 | 不允许发布 | 展示具体错误 |
| 发布并发冲突 | 拒绝覆盖 | 提示刷新后重试 |
| 最后管理员被移除 | 拒绝操作 | 提示必须保留管理员 |
| 发布后操作者失权 | 拒绝发布 | 展示影响原因 |
| 迁移异常 | 保留异常明细 | 进入待处理列表 |
| 权限缓存不可用 | 高风险操作拒绝 | 提示稍后重试 |

## 15. 审计要求

必须记录：

- 权限目录新增、停用。
- 角色新增、编辑、停用。
- 角色权限变更。
- 用户角色绑定新增、移除、停用。
- 权限矩阵草稿保存、校验、发布、回滚。
- 存量迁移成功、跳过、失败。

审计至少包含操作者、目标对象、组织范围、变更前、变更后、版本、原因、requestId 和时间。

## 16. 验收标准

### 16.1 后端真实联动

- Given：角色矩阵未配置订单编辑权限。
- When：该角色用户调用订单编辑接口。
- Then：接口返回 403，并记录权限拒绝日志。

- Given：角色矩阵发布 dictionaries.edit.store。
- When：用户绑定该角色并访问本门店字典编辑接口。
- Then：请求成功；访问其他门店返回 403。

### 16.2 多角色合并

- Given：角色 A 拥有订单查看本人权限，角色 B 拥有订单查看本门店权限。
- When：用户查看订单列表。
- Then：有效范围为本门店，权限结果不重复。

### 16.3 即时生效

- Given：用户已登录，管理员移除其角色绑定。
- When：用户再次调用受保护接口。
- Then：无需重新登录即可按新权限返回 403。

### 16.4 前后端一致

- Given：用户没有某能力的 view 权限。
- When：加载工作台和菜单。
- Then：前端不展示对应入口；直接访问 URL 或接口仍由后端拒绝。

### 16.5 发布安全

- Given：发布会导致最后一个总部管理员失去权限。
- When：管理员提交发布。
- Then：发布失败，当前生效版本不变，并提示影响原因。

- Given：当前已发布版本 V2，存在历史版本 V1。
- When：管理员执行回滚 V1。
- Then：V1 成为生效版本，相关缓存失效，并产生回滚审计记录。

### 16.6 存量迁移

- Given：现有门店成员岗位为 MANAGER。
- When：执行迁移脚本。
- Then：生成该用户所属门店的店长角色绑定，重复执行不产生重复绑定。

## 21. 研发落地补充（第一轮评审修订）

> 本章为正式规则；与前文冲突时以本章为准。

### 21.1 三层范围和判定算法

- 授权范围：角色权限项上的 OWN、STORE、GLOBAL。
- 绑定范围：用户绑定角色时的 HQ 或 STORE(storeId)，同一用户可有多条门店绑定。
- 对象范围：资源解析器从请求对象计算出的 storeId、ownerUserId 等。

请求只有在用户可用、角色和绑定可用、绑定范围覆盖请求门店、且授权范围覆盖对象范围时才允许。多角色只取允许结果并集，不支持显式拒绝；系统安全边界优先。GLOBAL 覆盖任意组织，STORE 仅覆盖绑定门店，OWN 仅覆盖本人且对象属于绑定门店。对象无法解析归属时默认拒绝，不能回退 GLOBAL。

每类资源必须登记范围解析器和列表过滤器：订单/施工/售后/库存/采购按 object.storeId；客户按 customer.storeId 和 ownerUserId；费用/报销/发票按 record.storeId 和申请人/销售负责人；无门店总部配置只允许 GLOBAL。列表、统计、导出使用同一过滤器，详情/修改读取对象后再次校验，创建校验门店上下文。

### 21.2 统一后端鉴权和安全边界

所有受保护接口必须经过统一 AuthorizationService，业务服务不得新增基于岗位或 isAuditor 的独立放行逻辑。服务至少提供 authorize(userId, permissionCode, action, context) 和 buildScopeFilter(userId, permissionCode, action, context)。未完成映射的接口默认拒绝，不能通过旧岗位判断绕过。

安全边界顺序为：用户状态 → 门店/组织关系 → 角色和绑定状态 → 权限矩阵 → 对象范围。请求门店必须在用户有效绑定范围内；总部范围仅总部绑定可用；停用最后一个可发布总部管理员，或发布后导致发布者失去发布能力，必须拒绝。

### 21.3 版本、并发、影响分析和回滚

同一权限域只允许一个 PUBLISHED 和一个可编辑 DRAFT。状态为 DRAFT → VALIDATED → PUBLISHED；校验/发布失败保留草稿，已发布版本不可编辑。保存、校验、发布、回滚均提交 expectedVersion，版本冲突拒绝并保留现状。发布事务同时写生效版本、审计和失效标记，幂等键防止重复发布。

回滚通过复制目标已发布版本生成新版本，不修改历史；不兼容当前权限目录则禁止。影响分析绑定 policyVersion 快照，必须返回受影响角色、用户、组织、菜单、接口和由允许变拒绝的权限项；发布提交快照确认标记，快照过期必须重算。

### 21.4 存量迁移和切换

迁移分准备期、兼容期、切换期：准备期创建角色/绑定并按岗位生成初始绑定；兼容期新建和变更人员同时写绑定并做新旧差异校验；切换期完成接口映射、差异处理和异常清零或豁免后开启统一鉴权开关。切换失败可关闭开关回退旧逻辑，绑定与审计不删除。

首期 isAuditor=true 映射为总部管理员，保持现有全局权限；审计只读角色拆分为后续治理，不改变本期账号权限。迁移后 isAuditor 和 StoreMember.position 仅用于展示、岗位业务语义、回退和差异核对，不再作为新权限放行依据。脚本幂等，输出成功/跳过/失败/差异/无法映射接口明细；失败不回滚基础数据，由总部管理员重试。

### 21.5 即时生效和统一响应

权限结果必须带 policyVersion、bindingVersion。发布或绑定提交成功后写版本/失效标记并清理相关缓存；TTL 不是生效保证，失效无法确认或缓存不可用时高风险操作默认拒绝。绑定、停用、门店关系变化后下一次请求无需重新登录即使用新结果。 角色绑定不支持未来定时生效；提交成功即 effectiveAt=当前时间，expiredAt 仅用于可选的失效时间。

GET /auth/me/permissions 返回 userId、policyVersion、bindingVersion、roles（roleCode/scopeType/scopeIds）、permissions（code/actions/scopes）、generatedAt。前端菜单、页面和按钮只消费该结果。兼容期保留 /settings/capabilities，但必须由同一 AuthorizationService 计算并标记迁移说明；新页面只使用新接口。

### 21.6 研发交付物、审计和验收补充

研发必须维护“权限编码—Controller/Service 方法—范围解析器—列表过滤方式”全量清单，未完成映射不得开启统一鉴权。审计复用现有事件模型，支持按时间、操作者、目标、权限版本分页筛选，before/after 脱敏并受审计权限保护。

必须新增验收：仅绑定门店 A 的用户访问 B，列表不返回、详情/修改 403；旧影响快照遇新版本发布返回版本冲突；绑定变更后不重新登录立即按新结果；无法解析资源范围默认拒绝；迁移重复执行保持幂等。指标上线前补充基线和目标阈值，不阻塞研发。

### 21.7 评审状态

第一轮 S0/S1 问题已补齐，进入第二轮评审。实现阶段如发现资源不满足范围解析契约，必须先补权限目录和验收用例，不得临时沿用岗位判断。
