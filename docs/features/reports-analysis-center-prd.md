## 2. 需求背景

### 2.1 业务背景

当前报表分析页面已经具备日期、人员、施工类型、产品分类和订单状态筛选，也按照销售、施工、财务、项目和售后维度展示明细数据。

### 2.2 当前问题

当前页面主要由四张统计卡、多个 Tab 和明细表组成，用户能够看到统计结果，但不能快速判断：

- 本期经营结果相较上一周期是变好还是变差。
- 订单金额、实际收款、待收金额和毛利之间的差异来自哪里。
- 哪些销售人员、施工人员、项目类型或售后责任类型需要关注。
- 数据是否完整，毛利为 0 是真实结果还是成本尚未补齐。
- 查看报表后应该采取什么业务动作。

现有 `OperationalReport` 主要返回人员、订单和分类聚合数据，没有统一的趋势、周期对比、数据完整度和可解释结论结构。因此，仅调整前端视觉或增加装饰性图表不能解决核心问题。

### 2.3 需求依据

- 截图反馈：页面“只有一些统计信息，但是没有分析”。
- 当前页面实现：`apps/web/app/reports/page.tsx` 仅展示统计卡、Tab 和表格。
- 当前 API 类型：`packages/shared/src/index.ts` 的 `OperationalReport` 未包含趋势、对比和分析结论字段。

## 3. 产品目标

### 3.1 业务目标

- 将报表从“结果展示”升级为“结果解释和行动入口”。
- 帮助店长在进入页面后快速识别经营变化、收款风险、利润风险和售后异常。
- 保持所有金额、成本、提成和售后数据来源真实可追溯。

### 3.2 用户目标

- 10 秒内知道本期经营结果和最需要关注的问题。
- 30 秒内定位问题涉及的人员、项目、订单或售后责任类型。
- 1 分钟内从分析结论进入可执行的明细页面或订单列表。

### 3.3 设计原则

- MUST：每个分析结论必须有数据证据。
- MUST NOT：将成本缺失、未确认或未结算数据显示成真实的 0。
- MUST：保留当前深蓝品牌色和紧凑、可靠的后台工作台视觉方向。
- RECOMMENDED：使用现有 React + CSS/SVG 实现图表，不为单页引入大型图表依赖。

## 4. 非目标

本期不包含：

- 不新增预算、销售目标、人员目标或绩效考核规则。
- 不新增订单、收款、成本结算或售后状态。
- 不替代财务总账、发票、收款和成本结算页面。
- 不基于缺少事实依据的数据生成“经营健康”“表现优秀”等主观结论。
- 不实现跨门店集团级经营分析，除非权限和数据范围另行确认。
- 不在本期建设复杂的自定义报表设计器。

## 5. 用户角色与权限

| 角色 | 使用场景 | 可查看内容 | 可执行操作 | 数据范围 |
|---|---|---|---|---|
| 店长 | 查看门店经营结果并安排后续动作 | 全部报表视图、趋势、结论、明细 | 筛选、钻取、导出 | 当前门店 |
| 财务人员 | 核对收款、待收、成本和利润 | 财务订单利润、收款和成本完整度 | 筛选、钻取、导出 | 当前门店 |
| 销售人员 | 查看个人销售业绩 | 个人销售视图及允许查看的明细 | 筛选个人可用条件、导出个人视图 | 仅本人相关数据 |
| 审计人员 | 复核门店经营数据 | 授权范围内的全部报表 | 筛选、钻取、导出 | 按审计权限确定 |

权限规则沿用现有 `/reports/operational` 权限校验，不新增权限模型。销售角色继续由后端限制为本人数据，前端不得通过隐藏筛选项绕过权限。

导出范围必须与当前用户可查看的数据范围一致。店长查看当前门店全部视图；财务重点查看财务、收款和成本数据；销售仅查看并导出本人销售数据；审计人员沿用现有授权门店和视图范围。

## 6. 核心业务场景

### 场景 1：店长查看本期经营结果

- 使用角色：店长。
- 触发时机：进入 `/reports` 或调整日期筛选后。
- 当前问题：只能看到订单金额、收款、毛利和售后单数，缺少环比、风险和行动提示。
- 目标结果：看到核心指标、与上一周期对比、数据完整度和最多 3 条带证据的经营结论。

### 场景 2：店长定位收款风险

- 使用角色：店长、财务人员。
- 触发时机：实际收款明显低于订单金额或存在较高待收金额。
- 目标结果：结论展示订单金额、实际收款和待收证据，并可进入待收订单明细。

### 场景 3：财务核对利润可信度

- 使用角色：财务人员。
- 触发时机：查看财务订单利润视图。
- 目标结果：区分实际成本、标准成本和待补齐成本；毛利缺失时显示“待补齐”，并可定位相关订单。

### 场景 4：店长定位人员或项目差异

- 使用角色：店长。
- 触发时机：查看销售、施工或项目分析。
- 目标结果：通过贡献结构和风险结构定位人员、施工类型、产品分类或售后责任类型。

## 7. 核心业务对象

| 对象 | 定义 | 关键字段 | 状态/口径 | 数据来源 |
|---|---|---|---|---|
| 报表查询 | 当前用户在指定门店和筛选条件下的一次数据查询 | 门店、日期范围、日期口径、人员、施工类型、产品分类、订单状态 | 不持久化 | 查询参数 |
| 报表汇总 | 当前查询范围的金额、数量和完整度聚合 | 订单数、订单金额、实际收款、待收、毛利、成本完整度 | 实时计算 | 订单、收款、成本 |
| 报表趋势 | 按日、周或月聚合的时间序列 | 周期、订单数、订单金额、收款、待收、毛利 | 由日期范围决定粒度 | 订单、收款、成本 |
| 分析结论 | 由确定性规则生成的带证据和动作入口的提示 | 严重程度、标题、证据、动作、目标视图 | 只读，不改变业务状态 | 汇总、趋势、明细 |
| 报表明细 | 可追溯到人员、项目或订单的原始聚合行 | 现有各 Tab 行字段 | 沿用现有业务状态 | 订单及关联记录 |

## 8. 产品信息架构

页面顺序 MUST 为：

1. 页面标题、当前数据口径和更新时间。
2. 全局筛选。
3. 核心经营汇总。
4. 本期经营结论。
5. 趋势分析。
6. 贡献结构与风险结构。
7. 现有分析 Tab 和明细表。

推荐首屏结构：

```text
页面标题 / 数据范围 / 更新时间 / 导出
全局筛选
订单金额  实际收款  毛利  待收金额
较上期变化 + 数据完整度
经营结论：最多 3 条
趋势图：金额 / 收款 / 毛利 / 待收
```

## 9. 功能需求

### 9.1 全局筛选与数据口径

#### 功能目标

让用户明确当前报表统计了哪些数据，以及数据按照什么日期计算。

#### 功能规则

1. 首次进入页面时，日期范围默认当前自然月。
2. 保留现有 `dateBasis` 筛选项，但它只用于订单创建日期/订单型明细的订单集合；实际收款、施工成本和售后费用始终按各自业务日期统计，不被 `dateBasis` 覆盖。
3. 筛选变化后，汇总、结论、趋势、结构和明细必须使用同一组筛选条件；各指标在同一查询中使用各自定义的业务日期。
4. 页面显示当前筛选摘要、日期口径和数据更新时间。
5. 点击“重置筛选”后恢复门店默认范围和默认日期口径。
6. 筛选项无可选数据时显示“暂无可选值”，不得展示虚构选项。
#### 指标日期口径

| 指标 | 统计日期 | 缺失日期处理 |
|---|---|---|
| 订单金额、订单数 | 订单创建日期 | 缺失时不纳入订单日期统计 |
| 实际收款 | 收款入账日期 | 缺失时不纳入收款日期统计 |
| 施工成本 | 成本确认或结算日期 | 缺失时标记数据不完整 |
| 售后费用 | 售后费用确认日期 | 缺失时标记数据不完整 |

页面必须显示当前指标日期口径。不同指标使用不同业务日期时，页面显示“按指标业务日期统计”；筛选摘要同时说明 `dateBasis` 仅作用于订单集合。

默认日期范围为当前自然月。当前月未结束时，对比上月同期天数。上一周期无数据时显示“暂无可比数据”，不显示异常百分比。

#### 周期对比规则

- 自定义日期范围：对比前一个等长周期。
- 自然月查询：对比上一个自然月。
- 当前月未结束：对比上月同期天数。
- 若筛选范围完整覆盖一个自然月，按自然月规则；否则按自定义范围规则。
- 上一周期无数据：显示“暂无可比数据”。
- 上期为 0、本期大于 0：显示“新增”。
- 当前值和对比值均为 0：显示“无变化”。

#### 验收标准

- Given：用户修改日期范围或人员筛选。
- When：接口返回成功。
- Then：页面所有模块同时更新，且当前筛选摘要与请求参数一致。

### 9.2 核心经营汇总

#### 展示指标

| 指标 | 口径 | 缺失处理 |
|---|---|---|
| 订单金额 | 当前查询范围内订单总金额 | 无数据显示 ¥0.00，并显示无订单状态 |
| 实际收款 | 当前查询范围内实际收款金额 | 无数据显示 ¥0.00 |
| 毛利 | 订单金额减可确认总成本 | 所有订单成本完整时展示；存在缺失时显示“待补齐” |
| 待收金额 | 命中订单创建日期的订单应收总额，减去截至查询结束时该订单集合累计入账金额 | 无待收显示 ¥0.00 |

每个指标应显示：当前值、上一周期变化值（如可计算）、数据完整度或缺失提示。
当存在成本待补齐订单时，同时显示成本完整度、已确认成本订单数和待补齐订单数；不允许将缺失成本按 0 参与毛利或毛利率计算。成本完整度分母为当前查询范围内财务订单利润视图返回的订单数；不在该视图中的草稿或无效对象不进入分母。

### 9.3 经营结论

#### 功能目标

将统计结果转成可解释、可追溯、可行动的提示。

#### 规则

1. 系统最多展示 3 条结论，固定按“收款落后、成本待补齐、人员贡献集中、售后比例偏高”的规则优先级排序；同类结论按证据数值从高到低排序。
2. 每条结论 MUST 包含标题、证据、影响对象和动作入口。
3. 当没有足够数据时，显示“数据不足，暂不生成结论”，不生成猜测性文案。
4. 结论只使用确定性规则生成，并使用本节已确认的默认阈值。
5. 结论和趋势本期优先在报表内部钻取：切换到固定 Tab，并自动带入日期、人员、施工类型、产品分类和订单状态筛选。外部订单级跳转后置。
6. `targetView` 仅允许 `sales`、`construction`、`finance`、`project`、`afterSalesWorker`、`afterSalesBreakdown`。

#### 钻取目标与筛选映射

| 目标视图 | 自动带入条件 | 页面反馈 |
|---|---|---|
| `sales` | 日期、销售人员、订单状态、产品分类 | 显示已应用条件，支持清除 |
| `construction` | 日期、施工人员、施工类型、订单状态 | 显示已应用条件，支持清除 |
| `finance` | 日期、订单状态、成本来源、待收状态 | 显示待收或待补齐条件 |
| `project` | 日期、施工类型、产品分类、订单状态 | 显示项目条件 |
| `afterSalesWorker` | 日期、施工人员、售后责任、售后状态 | 显示人员和责任条件 |
| `afterSalesBreakdown` | 日期、售后责任、售后状态 | 显示状态/责任条件 |

成本来源、待收状态、售后责任和售后状态为本期新增查询字段，后端必须执行权限过滤。
#### 已确认规则

| 结论 | 触发条件 | 证据 | 动作 |
|---|---|---|---|
| 收款落后于订单金额 | 收款率低于 80% 且待收金额大于 0 | 订单金额、实际收款、待收 | 查看财务订单利润视图 |
| 成本数据待补齐 | 存在成本来源为“待补齐”的订单 | 待补齐订单数、成本完整度 | 查看财务订单利润视图 |
| 人员贡献集中 | 单人员金额占团队金额至少 50%，且至少 3 笔订单 | 人员金额、团队占比 | 查看销售或施工分析 |
| 售后比例偏高 | 售后率至少 10%，且施工订单数不少于 10 笔 | 售后单数、施工订单数、售后率 | 查看售后人员分析 |

未达到最低样本量时不生成异常结论，只显示数据量不足。上述结论本期统一使用 `WARNING` 严重程度，避免在未建立目标体系前引入主观等级。

### 9.4 趋势分析

#### 功能目标

展示当前查询范围内经营指标随时间的变化，并支持定位到明细。

#### 功能规则

1. 趋势至少支持订单数、订单金额、实际收款、待收金额和毛利。
2. 查询范围不超过 7 天按日聚合，8–90 天按周聚合，超过 90 天按月聚合。
3. 周一为每周起始日，所有日期边界使用门店业务时区 `Asia/Shanghai`。
同步报表查询最多支持 366 天。超过范围时，在发起明细查询前直接阻止请求，提示“日期范围不能超过 366 天，请缩小范围”；不展示旧查询结果，不执行明细级全量查询，也不允许导出当前超限视图。
4. 毛利或成本数据不完整时，趋势点必须标记数据缺失，不按 0 绘制。
5. 点击趋势点后，当前报表明细使用对应时间范围刷新，并保留其他已选筛选条件。
6. 趋势无数据时显示空状态和调整筛选提示。

### 9.5 贡献结构与风险结构

#### 贡献结构

- 销售人员贡献。
- 施工类型贡献。
- 产品分类贡献。
- 毛利贡献（成本完整时）。

#### 风险结构

- 待收订单。
- 成本待补齐订单。
- 待确认工时。
- 售后高发状态或责任类型。
- 收款红冲、退款或补偿异常（数据可用时）。

结构项点击后必须进入对应视图或带条件的明细列表。

### 9.6 现有分析视图增强

| 视图 | 新增重点 |
|---|---|
| 销售业绩 | 收款率、毛利率、客单价、人员贡献占比、成本完整度 |
| 施工绩效 | 确认工时、施工金额分摊、待确认工时、提成状态 |
| 财务订单利润 | 待收、毛利率、成本来源、成本完整度、待补齐订单入口 |
| 项目经营分析 | 平均客单价、金额贡献占比、施工收费占比 |
| 售后人员分析 | 售后率、售后成本、退款/补偿、供应商追偿 |
| 售后结构分析 | 状态、责任、数量、占比、待处理入口；处理时长需后端补充 |

### 9.7 导出

1. 导出内容必须包含当前筛选条件、日期口径、实际查询时间和数据覆盖提示。
2. 当前视图导出保留现有能力。
3. 导出增加“分析摘要”工作表，包含核心指标、对比结果、数据完整度、各指标缺失数量和经营结论；成本或毛利为 `null` 时导出“待补齐”，不得导出为 0。
4. 导出失败时保留当前页面数据，并显示可重试错误反馈。

```ts
      ordersWithMissingBusinessDate: number;
      paymentsWithMissingEntryDate: number;
      costsWithMissingConfirmationDate: number;
      afterSalesWithMissingConfirmationDate: number;
    };
  };
  comparison: {
    amount: MetricComparison;
    received: MetricComparison;
    outstanding: MetricComparison;
    grossProfit: MetricComparison;
  };
  trendGranularity: "day" | "week" | "month";
  trend: Array<{
    period: string;
    orders: number;
    amountCents: number;
    receivedCents: number;
    outstandingCents: number;
    afterSalesCount: number;
    afterSalesExpenseCents: number;
    constructionOrderCount: number;
    grossProfitCents: number | null;
    costCompletenessBps: number;
    metricCompleteness: "complete" | "incomplete";
    knownCostOrderCount: number;
    pendingCostOrderCount: number;
    knownCostGrossProfitCents: number | null;
  }>;
  insights: Array<{
    severity: "WARNING";
    title: string;
    evidence: string;
    action: string;
    targetView?: ReportTargetView;
    filters?: ReportDrilldownFilters;
  }>;
};
```

以上字段为产品数据契约，实现必须遵守：各指标按业务日期统计；对比按已确认周期规则计算；成本不完整时毛利为 `null` 或明确“待补齐”；成本完整度分母按第 9.2 节执行；周期对比必须返回状态和可计算变化值；趋势返回粒度与完整度；权限过滤在后端执行。

### 10.2 模块加载与降级

本期保留 /reports/operational 作为兼容入口，但响应按模块返回状态：summary、trend、insights、details 各自包含 status: ready 或 error、可选 data 和可选 errorCode。summary 或 details 失败时按接口失败处理；trend 或 insights 失败时保留其他模块，并显示模块级重试入口。

超过 366 天的请求在服务端校验并返回 REPORT_DATE_RANGE_TOO_LARGE，不执行明细查询。

### 10.3 数据一致性要求

- 汇总、趋势、结论和明细必须使用同一组筛选条件，但各指标按各自业务日期形成对应数据集合。
- 待收金额按订单创建日期命中的订单集合计算累计应收余额；实际收款指标只统计查询范围内的收款入账金额。
- 实际收款按收款入账日期统计，施工成本按成本确认或结算日期统计，售后费用按费用确认日期统计。
- 上期为 0 且本期大于 0 时返回“新增”标识；两期均为 0 时返回“无变化”。
- 缺少成本、收款或业务日期的数据必须保留缺失标记，不得转换为 0。
- 金额统一使用分为后端单位、元为页面展示单位。
- 服务端返回 `null` 的成本或毛利不得被前端转换为 0。
- 所有结论必须能通过当前返回数据复算。
- 数据更新时间必须来自服务端响应时间或明确的查询完成时间。

## 11. 页面与交互

### 11.1 加载状态

- 首次加载显示筛选骨架、指标骨架、趋势骨架和表格骨架。
- 筛选刷新时保留旧结果并显示局部 loading，避免整页闪烁。

### 11.2 空状态

- 当前范围没有订单：显示“当前筛选范围暂无订单”，提供扩大日期范围或重置筛选操作。
- 当前范围有订单但无成本：显示“暂无可用成本数据”，提供进入成本补齐视图的入口。
- 当前范围无售后：显示“当前范围暂无售后记录”，不显示空白图表。

### 11.3 错误状态

- 接口失败时显示失败原因和“重试”按钮。
- 某个分析模块失败时不阻塞其他模块展示，并标明该模块数据不可用。

### 11.4 无权限状态

- 沿用现有后端权限返回。
- 无权限时不展示部分数据的残留缓存，并显示“暂无报表查看权限”。

### 11.5 响应式

- 1440px：完整展示筛选、四项指标、结论、趋势和结构分析。
- 1024px：筛选区分两行，指标保持两列，趋势和结构分析上下排列。
- 390px：筛选区改为纵向字段，指标两列，表格改为横向滚动或移动端摘要卡。
- 关键结论、待收和待补齐入口必须在窄屏可见，不得被折叠到不可发现区域。

| 场景 | 触发条件 | 系统处理 | 用户反馈 |
|---|---|---|---|

## 16. 验收标准汇总

### 16.1 正常流程

- Given：用户具有当前门店报表权限，且当前日期范围存在订单数据。
- When：用户进入报表页面并完成数据加载。
- Then：页面显示当前筛选范围、日期口径、更新时间、四项核心指标、经营结论、趋势和明细视图。

### 16.2 默认范围与日期口径

- Given：用户首次进入报表页面。
  When：页面完成初始化。
  Then：日期范围为当前自然月，日期口径显示为“按指标业务日期统计”，并说明 `dateBasis` 仅作用于订单集合。
- Given：订单创建日期、收款入账日期、成本确认日期和售后费用确认日期不同。
  When：用户查询同一范围。
  Then：各指标按对应业务日期计算，不能通过切换 `dateBasis` 改变收款、成本或售后指标口径。

### 16.3 数据可信度

- Given：查询范围内存在成本来源为“待补齐”的订单。
- When：用户查看毛利和财务分析。
- Then：系统显示待补齐状态和成本完整度，不把缺失成本当作 0 计算或展示。

### 16.4 分析结论

- Given：查询结果满足某条已确认的分析规则。
- When：页面完成计算。
- Then：显示包含标题、证据和动作入口的结论；点击动作后进入对应明细视图。

### 16.5 无数据

- Given：用户筛选后没有任何订单。
- When：接口返回空结果。
- Then：核心区域显示统一空状态，并提供重置筛选操作，不显示误导性的经营结论。

### 16.6 权限

- Given：当前用户为销售角色。
- When：用户进入报表并请求数据。
- Then：页面只显示本人允许查看的数据，任何前端参数修改都不能扩大后端返回范围。

### 16.7 关键规则验收

- Given：订单创建日期与收款入账日期不在同一天。
  When：查询范围只覆盖其中一个日期。
  Then：订单指标和收款指标分别按各自业务日期计算。
- Given：查询范围内存在待补齐成本订单。
  When：查看汇总、趋势和导出。
  Then：毛利显示“待补齐”，待补齐数量和完整度可见，所有缺失毛利均不转换为 0。
- Given：某条规则达到阈值但样本量不足。
  When：系统生成结论。
  Then：不生成异常结论，只显示数据不足。
- Given：用户点击结论动作。
  When：目标视图存在。
  Then：切换到固定视图并带入映射筛选，页面显示已应用条件。
- Given：查询范围超过 366 天。
  When：用户提交筛选。
  Then：请求被拒绝且不执行明细查询，导出按钮不可用。
- Given：趋势模块失败而汇总接口成功。
  When：页面完成加载。
  Then：汇总和明细仍展示，趋势显示错误和重试入口。

### 16.8 响应式

- Given：用户使用 1440px、1024px 或 390px 宽度访问页面。
- When：页面加载并进行筛选、切换 Tab、查看明细。
- Then：无不可接受的横向溢出、遮挡或无法点击的关键操作。

## 17. 已确认决策

以下事项已通过产品讨论确认，研发和测试应按此执行：

| 编号 | 决策 | 具体规则 |
|---|---|---|
| 1 | 指标日期口径 | 订单按创建日期，收款按入账日期，施工成本按确认/结算日期，售后费用按费用确认日期 |
| 2 | 对比周期 | 自定义范围对比前一等长周期；自然月对比上月；未结束月份对比上月同期 |
| 3 | 成本缺失 | 毛利显示“待补齐”，不按 0 计算；展示完整度和待补齐数量 |
| 4 | 趋势粒度 | 7 天以内按日，8–90 天按周，超过 90 天按月；周一为周起点 |
| 5 | 时区 | 使用门店业务时区，当前为 `Asia/Shanghai` |
| 6 | 分析阈值 | 收款率低于 80%；人员金额占比至少 50% 且至少 3 单；售后率至少 10% 且至少 10 单 |
| 7 | 钻取方式 | 本期优先报表内部钻取，自动带入筛选；外部订单级跳转后置 |
| 8 | 权限范围 | 沿用现有后端权限，导出不得超过查看范围 |
| 9 | 历史数据 | 不自动回填，缺失数据标记为“待补齐”或“数据不完整” |
| 10 | 性能边界 | 同步查询最多 366 天，趋势聚合、明细分页 |
| 11 | 目标体系 | 本期不引入预算、销售目标和绩效目标 |
| 12 | 图表技术 | 使用现有 React + CSS/SVG，不新增大型图表依赖 |

以下内容属于技术实现细节，不再阻塞产品评审，但必须在技术方案中明确：

- API 字段命名、接口拆分和数据库聚合方式。
- 趋势聚合查询的索引和响应时间验证。
- 结论严重程度统一使用 `WARNING` 的前端展示方式。
- 局部模块失败时的重试和降级实现。

## 18. 风险与回滚原则

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 新增趋势查询导致接口变慢 | 页面加载时间增加 | 限制默认日期范围、聚合查询、保留旧明细接口 |
| 毛利口径改变引发财务争议 | 指标不一致 | 按已确认的成本完整度和 null 规则上线，并保留旧字段兼容 |
| 自动结论误导用户 | 业务决策风险 | 先使用确定性规则，所有结论展示证据并允许关闭展示 |
| 新 API 与旧页面不兼容 | 发布风险 | 保留现有字段，新增字段可选，前端渐进启用 |

回滚原则：若新增趋势或结论接口异常，前端必须能够退回现有汇总和明细视图；不得阻塞现有报表查询和导出能力。
