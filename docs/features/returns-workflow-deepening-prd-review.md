## 2. v0.1 评审问题与修复

### S1-01：数据库枚举与实际状态流转未区分

- 位置：状态流转、验收标准。
- 问题：数据库存在 `APPROVED`、`CLOSED`，当前 implementation 没有推进；若 PRD 默认启用，会扩大本期状态机和迁移范围。
- 影响：研发和测试无法判断状态是否需要落库，可能产生无依据的 schema/数据迁移。
- 修改：v0.2 明确以当前实际状态为 canonical，本期不启用 `APPROVED` / `CLOSED`。
- 严重程度：S1，已解决。

### S1-02：审核后取消窗口缺少产品决策

- 位置：销售/采购取消流程。
- 问题：历史需求与当前代码的可取消状态不一致。
- 影响：可能改变库存/现金事实产生前后的撤销责任，不能由架构重构擅自决定。
- 修改：v0.2 采用当前行为，不新增审核后取消；未来另立需求。
- 严重程度：S1，已解决。

### S1-03：纯换货是否可零现金结算未定义

- 位置：采购结算规则。
- 问题：DTO 支持 `EXCHANGE`，当前执行仍要求退款+抵扣金额大于 0。
- 影响：会改变供应商结算完成条件和现金事实口径。
- 修改：v0.2 保持当前金额规则，纯换货另立需求。
- 严重程度：S1，已解决。

### S1-04：成本核验驳回 workflow 超出当前实现

- 位置：成本核验流程。
- 问题：当前有提交、确认、重提，没有独立驳回 action、附件归属和完整批次校验。
- 影响：若写入 PRD，会把架构深化扩大为新的财务业务流程。
- 修改：v0.2 只收拢现有动作，不新增驳回 workflow。
- 严重程度：S1，已解决。

### S1-05：现金事实 sourceId 变更风险未处理

- 位置：销售退款事实追溯。
- 问题：当前销售退款以 `ReturnAction.id` 作为 `sourceId`；改成退货单或调整记录会影响财务历史解释。
- 影响：可能破坏现金事实 provenance 和历史数据查询。
- 修改：v0.2 保持现有 `sourceId` 口径，只约束必须经过 `CashFactWriter`。
- 严重程度：S1，已解决。

### S2-01：退款成功审计缺口未写入验收

- 位置：退款 command 的一致性与审计。
- 问题：当前退款逻辑没有对应 `auditEvent`，与其它退货动作的可追溯要求不一致。
- 影响：退款事实发生后无法通过退货审计完整解释。
- 修改：v0.2 将退款成功审计纳入原子提交和验收标准。
- 严重程度：S2，已解决。

## 5. 进入研发前的实施约束

1. 不新增 `APPROVED` / `CLOSED` 状态迁移。
2. 不新增审核后取消和纯换货零现金结算。
3. 不把成本核验扩展为新的驳回 workflow。
4. 不改变销售退款 `sourceId` 口径。
5. 退款成功审计必须与退款业务状态和现金事实同事务提交。
6. controller command route 迁移完成后不得保留第二条可写实现。

## 6. 最终结论

**有条件通过，可进入研发。**

条件仅包括实现阶段遵守上述 6 条约束；指标目标值、运营补偿动作和并发压测阈值属于后续确认事项，不阻塞本期 command seam 实施。
