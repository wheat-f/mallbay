## 2. 背景与目标

当前门店模块将公开门店目录、工作台详情、送审/审核、冻结、店长变更、财务主体和跨店施工配置集中在 `StoresService`。部分生命周期规则已经由 use case 承担，但 controller 仍面对宽 interface，门店组织配置与读取场景的 locality 不足。

本期目标：

- 建立 `StoreGovernance` 管理 seam，集中门店组织生命周期和组织配置规则。
- 为公开目录、工作台详情、施工可执行门店列表提供稳定读取契约。
- 让门店配置成为跨店施工资格的唯一来源，避免施工模块复制组织规则。
- 保持现有路由、数据库结构和业务结果兼容。

## 3. 范围与非目标

### 本期范围

- 门店创建、送审、审核、发布、冻结/解冻、店长变更。
- 财务主体创建/查询与门店跨店施工配置。
- 管理员门店列表、待审核列表和管理员详情。
- 公开门店目录、工作台门店详情、施工可执行门店读取契约。
- controller/module 依赖迁移、契约测试和现有门店回归。

### 非目标

- 不重做已有四个 use case 的业务实现。
- 不让 `ConstructionFulfillment` 写入门店配置。
- 不新增门店状态或财务主体字段。
- 不改变照片上传的 OSS 行为。

## 4. 角色与数据范围

| 角色 | 可查看 | 可操作 | 数据范围 |
|---|---|---|---|
| 总部管理员 | 全部门店、提交、财务主体和组织配置 | 创建、审核、冻结/解冻、变更店长、配置跨店施工 | 总部 |
| 店长 | 所属门店工作台和门店提交信息 | 编辑并提交所属门店信息、上传照片 | 本门店 |
| 公开访问者 | 已发布门店目录和详情 | 无写操作 | 已发布门店 |
| 施工模块 | 施工执行所需的可执行门店列表 | 只读 | 与来源门店财务主体和配置匹配的已发布门店 |

## 5. 核心对象与状态

| 对象 | 定义 | 状态/约束 |
|---|---|---|
| 门店 | 承载经营、成员和财务主体关系的组织单元 | DRAFTED、PENDING_REVIEW、PUBLISHED、FROZEN 等现有枚举 |
| 门店提交 | 店长提交给总部审核的门店资料快照 | PENDING、APPROVED、REJECTED 等现有枚举 |
| 财务主体 | 门店结算及跨店施工组织关系使用的主体 | ACTIVE 或现有失效状态 |
| 店长关系 | 门店与唯一店长成员的组织关系 | 同一用户不得同时成为其他门店店长 |

## 6. 核心流程与规则

### 6.1 门店生命周期

1. 总部管理员创建门店并指派店长；门店进入草稿状态，并初始化门店默认字典。
2. 店长补充资料、照片并提交；系统形成待审核提交。
3. 总部管理员审核；批准后门店发布，拒绝后返回可重新提交状态并保留审核结果。
4. 总部管理员可冻结或解冻门店；冻结不删除门店、成员、财务主体或跨店配置。
5. 总部管理员可变更店长；新店长唯一性和权限范围必须在同一事务中校验。

### 6.2 财务主体与跨店施工

- 创建或更新门店跨店施工配置时，目标财务主体必须存在且为有效状态。
- 来源门店未开启跨店施工时，可执行门店列表为空。
- 目标门店必须与来源门店属于同一财务主体、已开启跨店施工、已发布，且不得为来源门店自身。
- `ConstructionFulfillment` 只能读取该资格结果，不反向修改门店组织配置。

### 6.3 状态冲突与重复

- 送审、审核、冻结/解冻、店长变更均基于当前状态执行；状态不满足前置条件时拒绝，不自动覆盖。
- 重复冻结/解冻返回当前状态或幂等成功；重复审核同一已处理提交不得再次改变门店结果。
- 门店不存在、财务主体失效或店长已属于其他门店时明确拒绝。
- 审核拒绝后，若门店存在历史批准提交，门店回到 `PUBLISHED`；否则回到 `DRAFTED`，均允许店长重新提交。
- 门店状态和审核结果是权威业务结果；通知发送失败不得回滚已成功状态，由现有通知 dispatcher 负责重试或记录可观测失败。
- 冻结只允许 `PUBLISHED → FROZEN`，解冻只允许 `FROZEN → PUBLISHED`。

## 7. Seam 与实现约束

- `StoreGovernance` 是管理命令与管理查询的外部 seam；公开目录、工作台详情、施工资格是读取契约，不混入治理命令 interface。
- 现有 `ReviewStoreSubmissionUseCase`、`SubmitStoreForReviewUseCase`、`ChangeStoreManagerUseCase`、`SetStoreFrozenUseCase` 继续作为内部 adapter，由治理实现统一编排。
- 先通过 token/interface 接入现有实现，再逐步抽出实现；不做双写，不改变路由和数据库。
- 不引入泛化 `StoreAdapter`；现有 use case 已是真实内部 seam，新增外部 seam 以复用规则和测试 surface 为目的。

## 8. 验收标准

- Given 店长属于门店 A，When 提交门店资料，Then 产生待审核提交且门店进入对应待审核状态。
- Given 总部管理员审核批准，When 提交状态为待审核，Then 门店发布；若提交已处理，Then 重复审核拒绝且不改变结果。
- Given 门店 A 未开启跨店施工，When 查询可执行门店，Then 返回空列表。
- Given 门店 A 与门店 B 财务主体不同或 B 未发布，When 查询可执行门店，Then B 不出现在结果中。
- Given 门店已冻结，When 查询/解冻，Then 不删除配置，解冻后原配置仍可用。
- Given 门店存在历史批准提交，When 最新提交被拒绝，Then 门店保持 `PUBLISHED`；Given 不存在历史批准提交，Then 门店回到 `DRAFTED`。
- Given 新店长已属于其他门店，When 变更店长，Then 操作拒绝且原店长关系保持不变。
- Given `ConstructionFulfillment` 查询施工资格，When 门店配置改变，Then下一次读取反映最新资格，施工模块不产生门店配置写入。
- API typecheck、Nest build、门店/施工相关测试和全量 API tests 通过。

## 9. 指标与待确认

- 技术指标：门店生命周期规则集中到一个治理 seam；不新增写入事实或迁移。
- 业务指标：审核处理时长、冻结误操作率暂无基线，标记为上线后补充。
- 待确认：门店审核拒绝原因是否需要标准化枚举；不阻塞本期 seam。
