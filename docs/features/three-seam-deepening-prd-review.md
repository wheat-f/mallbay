## 2. 结论摘要

三份 PRD 已按 grilling 结果统一修订，三个 seam 独立推进，不形成运营总 interface。核心事实 owner、状态模型、权限来源、幂等语义和删除阶段门已闭合。

| 等级 | 数量 | 说明 |
|---|---:|---|
| S0 阻塞 | 0 | 无方向性或流程闭环阻塞 |
| S1 高风险 | 0 | 已在非目标和阶段门中明确隔离 |
| S2 一般问题 | 0 | 当前行为均有回归覆盖方向 |
| S3 优化建议 | 3 | 可在实施中优化，不阻塞 |

## 3. 评审已解决的关键问题

### 3.1 订单运营不吞并履约和现金事实

- `OrderLifecycle` 仍是履约 command authority。
- `CashFactWriter` 仍是 `PaymentRecord` 唯一写入 seam。
- 订单运营只编排并返回稳定结果。

### 3.2 售后与退货边界明确

- `AfterSalesResolution` 只拥有售后状态、证据、成本和审计编排。
- `ReturnsWorkflow` 继续拥有销售/采购退货状态。
- 售后不直接写现金事实、库存流水或最终交付状态。

### 3.3 ConstructionFulfillment 不被重新扩大

- 施工管理只覆盖容量、人员、请假和排班。
- 履约、证据、材料和离线同步明确为非目标。
- 施工管理不改变订单履约或库存事实。

## 4. 流程与状态评审

| 模块 | 流程起点 | 流程终点 | 状态/结果闭环 |
|---|---|---|---|
| 订单运营 | 读取或提交订单运营动作 | 稳定投影或事务结果 | 通过；履约 delegated 给 `OrderLifecycle` |
| 售后处置 | 售后创建/派单 | 关闭或成本红冲完成 | 通过；`OPEN → ASSIGNED → RESOLVED → CLOSED` |
| 施工管理 | 管理者提交管理动作 | 管理记录结果 | 通过；沿用现有对象状态 |

## 5. 权限与数据范围评审

- 三个 seam 均明确使用 `AccessContext`。
- 销售本人、施工人员本人、门店管理者、财务等范围已分别列出。
- 不再使用 `PermissionPolicy`、`isAuditor` 或页面岗位字段作为授权来源。
- 售后施工人员范围同时依赖实体指派关系，避免只凭门店范围越权。

## 6. 异常与边界评审

已覆盖：对象不存在、越权、重复提交、幂等键冲突、状态被并发改变、证据前置缺失、OSS 回滚、成本重复红冲、现金事实失败回滚、跨门店管理和旧入口误调用。

## 7. 可验收性评审

三份 PRD 均提供 Given/When/Then，覆盖：

- 主流程和不触发条件；
- 状态变化与终态行为；
- 权限与门店/本人范围；
- 幂等重放与冲突；
- 事实 owner 不被绕过；
- module export 和生产引用删除测试。

## 8. S3 优化建议

1. 实施时统一三份 contract test 的结果错误码命名，但不得改变现有 HTTP 兼容文案。
2. 页面迁移完成后补充订单、售后、施工管理各一份代表页面浏览器验收记录。
3. 三个 seam 通过删除阶段门后，再决定是否记录总架构 ADR；本期不新增重复性 ADR。

## 9. 研发进入结论

**可以进入研发。**

进入实施前必须保留三项硬约束：

1. 每个 seam 独立 contract test 和 deletion test。
2. 不新增第二条履约、现金事实或库存事实写入路径。
3. 旧 service 只能作为内部 implementation，不能继续作为 public export。
