# 财务管理工作流重构设计

- 文档类型：正式设计规范
- 文档状态：已确认，待实施
- 日期：2026-07-13
- 适用范围：费用申请、报销与付款、收款账户、资金流水
- 业务定义：费用申请是事前审批；报销是实际费用发生后的事后付款申请

## 1. 背景与问题

当前 `/finance` 同时承载费用创建、报销创建、报销审批、账户维护和流水查询。虽然功能入口较多，但页面结构和后台能力没有形成一致的业务闭环：

- “费用申请”默认展示创建表单，提交后的记录藏在“财务流水”页，申请人无法自然找到。
- 采购等角色能够提交费用或报销，但列表接口只允许财务管理角色访问，申请人提交后无法查看自己的单据。
- 后端仅支持报销审批，不支持费用申请审批、撤回、重新提交或详情查询。
- 页面展示部门主管、财务、总经理多级审批，数据库实际只保存一个审批人和一次审批结果。
- 附件区域仅为视觉占位，没有上传、持久化和预览能力。
- 报销审核与付款复用同一接口，审批通过和实际付款的职责边界不清楚。
- 资金流水依赖金额正负判断收支方向，但报销付款当前写入正数，可能被错误归类为收入。
- 单个 `apps/web/app/finance/page.tsx` 同时承担多个工作区、表单和明细，维护和测试成本过高。

## 2. 设计目标

重构后的财务管理 MUST 满足：

1. 申请人提交费用或报销后，可以立即在“我的申请”中查看状态、详情、附件和审批记录。
2. 店长或管理员处理业务合理性审批；财务只处理财务审核、付款和资金流水。
3. 费用申请与报销申请具有清晰的前后关系，不在同一个页面同时铺开两个创建表单。
4. 审批通过不等于已付款；付款必须是独立、可审计且幂等的动作。
5. 只有实际收付款动作生成资金流水，流水具有明确的收入/支出方向。
6. 附件使用现有对象存储能力，申请、审批和付款凭证可以上传、预览和下载。
7. 页面以列表和待办为主，创建和处理操作使用抽屉或独立详情页，不让表单长期占据主工作区。
8. 所有状态变化刷新后仍由 API 恢复，重复操作不得产生重复审批或重复流水。

## 3. 非目标

本次不实现：

- 可视化流程设计器。
- 任意层级、任意条件的通用审批引擎。
- 银企直连和自动付款。
- 税控级发票能力。
- 多币种、会计凭证和总账核算。
- 预算中心、成本中心和跨门店分摊。

## 4. 核心业务定义

### 4.1 费用申请

费用申请用于支出发生前的业务授权，例如耗材采购、临时设备购买或门店运营支出。

- 申请人提交费用用途、预计金额和附件。
- 店长审核业务必要性。
- 管理员可以代替店长完成业务审批，但本期不增加金额阈值或多级终审配置。
- 费用申请审批通过后只表示“允许发生该费用”，不生成资金流水。
- 实际支出发生后，申请人基于已批准费用发起报销/付款申请。

### 4.2 报销与付款

报销用于费用实际发生后的票据审核和付款。

- 报销优先关联一张已批准费用申请。
- 无法事前申请的紧急费用允许创建“未关联费用”的报销，但必须填写例外原因。
- 财务审核票据、金额、收款人和付款账户。
- 审核通过后进入待付款；只有财务执行“确认付款”后状态才变为已付款。
- 确认付款时在同一数据库事务中生成一条支出流水。

### 4.3 收款账户与资金流水

- 收款账户继续复用 `PaymentAccount`，仅店长、财务和管理员维护。
- 资金流水是实际资金变动记录，不承担费用申请或报销申请列表职责。
- 流水必须记录方向、类型、金额、账户、来源单据、经办人和时间。

### 4.4 端到端流程

```mermaid
flowchart LR
  A["申请人提交费用申请"] --> B["店长或管理员业务审批"]
  B -->|驳回| C["申请人补充并重新提交"]
  C --> B
  B -->|批准| D["实际费用发生"]
  D --> E["申请人提交报销与附件"]
  E --> F["财务审核票据与收款信息"]
  F -->|驳回| G["申请人补充并重新提交"]
  G --> F
  F -->|批准| H["待付款"]
  H --> I["财务选择账户并确认付款"]
  I --> J["生成一条支出流水"]
  J --> K["报销归档为已付款"]
```

费用批准、报销批准和确认付款是三个独立业务事件；只有最后一步改变资金余额。

## 5. 状态机

### 5.1 费用申请状态

沿用 `FinanceApprovalStatus`，语义如下：

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| `PENDING` | 待业务审批 | 申请人撤回；店长批准或驳回 |
| `APPROVED` | 已批准，可发生费用 | 创建关联报销 |
| `REJECTED` | 已驳回 | 申请人修改后重新提交 |
| `CANCELLED` | 已撤回/取消 | 只读 |
| `PAID` | 不用于费用申请 | 服务端拒绝写入 |

费用申请只执行一次业务审批；管理员与店长使用同一审批节点，不增加静态但不可执行的多级流程。

### 5.2 报销状态

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| `PENDING` | 待财务审核 | 申请人撤回；财务批准或驳回 |
| `APPROVED` | 已审核，待付款 | 财务确认付款 |
| `REJECTED` | 已驳回 | 申请人补充材料后重新提交 |
| `PAID` | 已付款并生成流水 | 只读 |
| `CANCELLED` | 已撤回/取消 | 只读 |

### 5.3 状态约束

- 终态单据不能再次审批。
- 已付款报销不能再次付款。
- 撤回仅允许申请人在 `PENDING` 状态执行。
- 重新提交仅允许原申请人对 `REJECTED` 单据执行。
- 报销金额不得超过关联费用申请的批准金额减去已关联有效报销金额。
- 费用申请审批和报销付款必须使用数据库事务。

## 6. 角色与权限

| 能力 | 采购/可申请角色 | 店长 | 财务 | 管理员 |
| --- | --- | --- | --- | --- |
| 新建费用/报销 | 是 | 是 | 是 | 是 |
| 查看自己的申请 | 是 | 是 | 是 | 是 |
| 查看全店申请 | 否 | 是 | 是 | 是 |
| 费用业务审批 | 否 | 是 | 否 | 是 |
| 报销财务审核 | 否 | 否 | 是 | 是 |
| 确认付款 | 否 | 否 | 是 | 是 |
| 维护收款账户 | 否 | 是 | 是 | 是 |
| 查看全店资金流水 | 否 | 是 | 是 | 是 |

前端 MUST 根据角色和单据状态隐藏无权操作；服务端仍作为最终权限边界。

详情接口返回的 `allowedActions` 必须使用固定动作集合，前端不得自行根据状态猜测权限：

- `REVIEW_EXPENSE`
- `WITHDRAW`
- `RESUBMIT`
- `CREATE_REIMBURSEMENT`
- `REVIEW_REIMBURSEMENT`
- `PAY`
- `UPLOAD_ATTACHMENT`

## 7. 信息架构与页面设计

### 7.1 `/finance` 财务总览

首页只承载概览和待办，不直接展示创建表单。

第一行使用四个紧凑指标：

- 待我审批
- 待付款
- 本月收入
- 本月支出

主体采用两栏：

- 左侧：待办队列，按“费用审批、报销审核、待付款”切换。
- 右侧：最近资金动态和异常提醒。

顶部命令区仅保留：`新建申请`、`导出流水`。

### 7.2 `/finance/expenses` 费用申请

列表是第一屏主体，包含：

- 范围：我的申请 / 全部申请（按权限显示）。
- 筛选：状态、申请人、申请日期、金额范围、关键词。
- 列：申请单号、标题、申请人、预计金额、当前节点、状态、申请时间、操作。
- 操作：查看、撤回、重新提交、审批、创建报销。

“新建费用申请”使用右侧抽屉。抽屉关闭后列表仍保留筛选和分页。

### 7.3 `/finance/expenses/:id` 费用详情

详情页包含：

- 单据摘要和状态。
- 申请内容、预计金额和用途。
- 附件列表与预览。
- 审批时间线。
- 已关联报销及累计报销金额。
- 当前角色可执行动作。

### 7.4 `/finance/reimbursements` 报销与付款

同一列表通过状态标签分为：

- 我的报销
- 待审核
- 待付款
- 已完成

列表字段：报销单号、关联费用、申请人、收款信息、报销金额、当前状态、申请时间、操作。

创建报销使用右侧抽屉；审批和付款进入详情页处理，不在列表中放置完整表单。

### 7.5 `/finance/reimbursements/:id` 报销详情

详情页包含：

- 报销内容和关联费用额度。
- 发票、合同、付款截图等附件。
- 申请人及收款信息。
- 审批时间线。
- 财务审核区或待付款区，按状态互斥显示。
- 已付款后展示关联资金流水和付款凭证。

### 7.6 `/finance/accounts` 收款账户

保持账户列表与维护表单，但改为列表主视图：

- 新建/编辑使用抽屉。
- 单行展示账户名称、类型、开户行、掩码账号、默认状态和启用状态。
- 账户审计记录放在详情抽屉中，不与新增表单并排。

### 7.7 `/finance/ledger` 资金流水

- 筛选：收入/支出、类型、账户、日期、来源单据和经办人。
- 列：流水摘要、方向、金额、账户、来源单据、经办人、发生时间。
- 点击进入现有流水详情页。
- 费用和报销申请列表不得再放在本页面。

### 7.8 响应式规则

- 桌面端列表保持固定列宽和横向滚动，不压缩到不可读。
- 900px 以下切换为单据卡片。
- 创建、审批和付款抽屉在移动端使用全屏宽度。
- 不使用卡片套卡片；页面分区使用无边框布局，卡片仅用于指标、单据和详情块。

## 8. 数据模型设计

保留现有 `ExpenseApplication`、`ReimbursementApplication` 和 `PaymentRecord`，避免高风险数据迁移。

### 8.1 新增审批记录

新增 `FinanceApprovalRecord`：

- `id`
- `storeId`
- `applicationType`: `EXPENSE | REIMBURSEMENT`
- `applicationId`
- `node`: `MANAGER_REVIEW | FINANCE_REVIEW | PAYMENT`
- `action`: `SUBMITTED | APPROVED | REJECTED | WITHDRAWN | RESUBMITTED | PAID`
- `operatorId`
- `note`
- `createdAt`

### 8.2 新增附件

新增 `FinanceAttachment`：

- `id`
- `storeId`
- `applicationType`
- `applicationId`
- `category`: `INVOICE | CONTRACT | PAYMENT_PROOF | OTHER`
- `fileUrl`
- `fileName`
- `contentType`
- `fileSize`
- `uploadedById`
- `createdAt`

### 8.3 扩展资金流水

`PaymentRecord` 新增：

- `direction`: `INCOME | EXPENSE`
- `occurredAt`

金额始终保存正整数分值，方向由 `direction` 表达。历史数据迁移规则：

- `ORDER_PAYMENT` 为 `INCOME`。
- `EXPENSE`、`REIMBURSEMENT`、`REBATE` 为 `EXPENSE`。
- `OTHER` 根据原金额正负推断，迁移后金额取绝对值。

### 8.4 单据扩展字段

费用申请新增：

- `applicationNo`
- `currentNode`
- `submittedAt`

报销申请新增：

- `applicationNo`
- `currentNode`
- `payeeName`
- `payeeAccount`
- `paymentAccountId`
- `paidAt`
- `paymentRecordId`
- `exceptionReason`

### 8.5 业务单号

- 新单号使用 `FIN-EXP-yyyyMMdd-XXXXXXXX` 或 `FIN-RMB-yyyyMMdd-XXXXXXXX`，末段取随机 UUID 的前 8 位大写十六进制字符。
- 创建时依赖唯一索引并最多重试 3 次；连续冲突返回服务端错误，不回退为数据库主键。
- 历史数据迁移使用 `FIN-EXP-HIS-${UPPER(id)}` 和 `FIN-RMB-HIS-${UPPER(id)}`，确保确定性与唯一性。

### 8.6 附件约束

- 单文件最大 10 MiB。
- 允许 `application/pdf`、`image/jpeg`、`image/png`、`image/webp`。
- 文件名必须清理路径字符，OSS key 使用 `finance/{applicationId}/{uuid}-{safeFileName}`。
- 只有申请人本人或拥有同店审核权限的角色可以查看；上传仅允许申请人本人在可编辑状态下执行。

## 10. 关键事务与幂等性

确认付款必须在同一事务中：

1. 锁定报销申请并确认状态为 `APPROVED`。
2. 创建一条 `direction=EXPENSE` 的资金流水。
3. 写入付款审批记录。
4. 将报销状态更新为 `PAID` 并关联资金流水。

重复付款请求返回现有付款结果，不创建第二条流水。

审批、撤回和重新提交都需要校验当前状态，非法状态转换返回明确业务错误。

## 11. 错误与空状态

- 无申请记录：显示“暂无费用申请”，并保留新建入口。
- 无审批权限：不渲染审批按钮；直接调用接口返回 `403` 和明确错误信息。
- 附件上传失败：已填写表单不得丢失，支持单个附件重试。
- 付款账户停用：付款前阻止提交，并提示重新选择账户。
- 重复付款：返回“该报销已付款”及关联流水信息。
- 关联费用额度不足：明确显示批准金额、已占用金额和剩余额度。

## 12. 测试与验收

### 12.1 API 测试

- 申请人只能查询自己的申请。
- 店长、财务和管理员按权限查询全店单据。
- 店长可以审批费用，不能确认报销付款。
- 财务可以审核和付款，不能代替店长完成费用业务审批。
- 费用申请不允许写入 `PAID`。
- 报销审核通过不生成流水，确认付款后只生成一条支出流水。
- 重复付款、重复审批和非法状态跳转被拒绝或幂等返回。
- 附件上传与详情读取保留持久 URL。

### 12.2 Web 测试

- 财务首页不再默认显示创建表单。
- 费用和报销列表是各自页面的第一屏主体。
- 提交成功后跳转或定位到新单据详情。
- 角色和状态决定可见操作。
- 抽屉关闭后保留列表筛选与分页。
- 移动端显示单据卡片和全屏操作抽屉。

### 12.3 业务验收

1. 采购提交费用申请，刷新后仍可在“我的申请”查看。
2. 店长批准费用，申请人看到状态变为已批准。
3. 申请人基于费用创建报销并上传发票。
4. 财务审核后单据进入待付款，不产生流水。
5. 财务选择付款账户并确认付款，单据变为已付款，生成一条支出流水。
6. 重复点击付款不会产生第二条流水。
7. 店长、财务、申请人分别只看到属于自己的操作入口。

## 13. 迁移与兼容

- 保留现有 API 路径，并通过新增查询参数和详情接口扩展能力。
- 现有 `PENDING/APPROVED/REJECTED/PAID/CANCELLED` 数据继续有效。
- 为历史单据生成业务单号；历史审批字段迁移为一条审批记录。
- 历史流水补齐 `direction` 后，前端停止使用金额正负判断方向。
- 数据迁移完成前保留旧字段读取兼容；验证完成后再删除冗余展示逻辑。

## 14. 实施顺序

1. 数据模型、迁移和共享类型。
2. 权限、查询范围和费用审批。
3. 报销审核、独立付款和流水方向。
4. 附件上传与审批记录。
5. 前端路由和财务总览。
6. 费用列表/详情/创建抽屉。
7. 报销列表/详情/审批/付款。
8. 账户和流水页面整理。
9. 全量回归、迁移验证和真实业务验收。
